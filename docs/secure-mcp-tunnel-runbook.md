# Secure MCP Tunnel 로컬 MCP 전환 런북

## 목적

이 문서는 로컬 컴퓨터나 사설 네트워크에서 실행되는 MCP 서버를 OpenAI 제품에 연결할 때, 느리거나 불투명한 원격 중계 경로를 Secure MCP Tunnel로 교체하는 과정을 재사용 가능한 형태로 정리한다.

특정 MCP 구현, 프로젝트, 컴퓨터 경로에 종속된 설치 기록이 아니다. stdio 또는 사설 HTTP로 접근 가능한 로컬 MCP를 대상으로 다음을 다룬다.

- 기존 경로의 실제 병목 확인
- 아웃바운드 전용 터널 구조 설계
- 권한과 비밀값 관리
- 독립적인 로컬 런타임 구성
- 기능 및 성능 검증
- 재부팅, 업데이트, 제거와 롤백
- 전송 지연과 모델 처리 지연의 분리

OpenAI의 현재 제품 화면, 명령 옵션과 배포 파일은 바뀔 수 있다. 실제 구축 시에는 [Secure MCP Tunnel 공식 문서](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)와 현재 `tunnel-client` 도움말을 우선한다.

## 적용 범위

다음 조건에 적합하다.

- MCP 서버가 개발자 PC, 사내망, 온프레미스 또는 방화벽 뒤에 있다.
- MCP 서버를 공개 인터넷에 직접 노출하지 않으려 한다.
- 터널 호스트가 OpenAI 제어 평면으로 아웃바운드 HTTPS 연결을 만들 수 있다.
- 터널 호스트에서 로컬 MCP 서버를 stdio 명령 또는 사설 HTTP 주소로 호출할 수 있다.
- ChatGPT, Codex 또는 지원되는 OpenAI API 표면에서 비공개 MCP를 사용하려 한다.

다음 목적에는 그대로 적용되지 않는다.

- 공개 플러그인 배포
- 누구나 접근해야 하는 공개 MCP 엔드포인트 제공
- OpenAI 제품과 무관한 범용 VPN 또는 임의 TCP 터널
- MCP가 아닌 임의 네트워크 서비스를 그대로 공개하는 용도

## 목표 구조

```text
OpenAI 제품
    |
    v
OpenAI 호스팅 터널 엔드포인트
    ^
    | 아웃바운드 HTTPS 폴링 및 응답
    |
tunnel-client
    |
    +-- stdio 명령 ------> 로컬 MCP 프로세스
    |
    `-- 사설 HTTP -------> 내부 MCP 서버
```

연결은 로컬 네트워크 안의 `tunnel-client`가 시작한다. 외부에서 로컬 컴퓨터로 직접 들어오는 인바운드 포트를 열지 않는다. OpenAI 제품이 터널 엔드포인트에 요청을 보내면 클라이언트가 대기 중인 요청을 받아 로컬 MCP로 전달하고, 결과를 같은 경로로 반환한다.

터널은 전송 계층이다. MCP 서버의 도구 계약, 로컬 권한, 파일 접근 범위와 애플리케이션 수준 인증을 대신 설계해 주지는 않는다.

## 구축 전에 확인할 것

### 1. 기존 경로의 병목을 먼저 분리한다

느리다는 증상만으로 로컬 PC, MCP 서버 또는 네트워크를 원인으로 확정하지 않는다. 최소한 다음 구간을 구분한다.

1. 사용자가 요청한 뒤 모델이 도구 호출을 만들기까지
2. 제품에서 MCP 전송 계층까지
3. 전송 계층에서 로컬 MCP가 요청을 받기까지
4. 로컬 MCP 또는 하위 CLI의 실제 실행
5. 결과 직렬화와 전송
6. 결과가 모델 컨텍스트에 적재되고 최종 답변이 만들어지기까지

로컬 프로세스의 시작·종료 시간만으로 전체 왕복 시간을 설명하지 않는다. 반대로 UI 전체 시간만으로 로컬 MCP가 느리다고 판단하지 않는다.

### 2. MCP의 실행 계약을 확인한다

다음을 실제 실행으로 확인한다.

- stdio인지 HTTP인지
- 실행 명령 또는 내부 주소
- 필요한 작업 디렉터리
- 필수 환경 변수
- 시작 후 준비 완료까지 걸리는 시간
- 종료 및 재시작 방식
- 출력에 비밀값이 포함될 가능성

터널을 붙이기 전에 같은 호스트에서 MCP를 직접 실행해 도구 목록 확인이나 작은 읽기 전용 호출이 성공해야 한다.

### 3. 운영 책임을 정한다

다음 항목의 소유자를 정한다.

- 터널과 조직·워크스페이스 연결
- 런타임 API 키 발급과 폐기
- 로컬 런타임 설치 및 업데이트
- 재부팅 후 시작
- 장애 로그와 상태 확인
- 기존 중계 경로 제거와 롤백

## 권한과 보안

### 권한 계층

터널 제어 권한과 ChatGPT 개발자 모드 권한은 별개다.

- 터널 생성·수정: `Tunnels Read + Manage`
- 런타임 실행 및 터널 선택: `Tunnels Read + Use`
- ChatGPT에서 앱 생성·사용: 해당 워크스페이스의 개발자 모드 및 앱 정책

런타임 키에는 MCP 운영에 필요하지 않은 모델, 파일, 파인튜닝 등의 API 권한을 부여하지 않는다. 가능한 최소 권한과 전용 키를 사용한다.

### 비밀값 관리

- 실제 API 키, 터널 ID와 조직 식별자를 저장소에 커밋하지 않는다.
- 환경 파일을 사용한다면 해당 사용자와 운영 주체만 읽을 수 있게 권한을 제한한다.
- 프로필에는 키 원문보다 환경 변수 참조를 저장한다.
- 실행 명령, 프로세스 목록, 로그와 지원 번들에 키가 노출되지 않는지 확인한다.
- 키가 노출되면 기존 키를 폐기하고 새 키로 교체한다.
- 런타임 키를 복사한 시스템은 동일한 터널 자격으로 접속을 시도할 수 있으므로 컴퓨터 인증 정보처럼 취급한다.

### 인증 계층을 혼동하지 않는다

로컬 MCP가 별도 OAuth를 제공하지 않아 앱 설정에서 MCP 수준 인증을 사용하지 않더라도 터널 전체가 공개 무인증 상태가 되는 것은 아니다. 런타임 키가 터널 클라이언트를 인증하고, 조직·워크스페이스 연결이 OpenAI 쪽 사용 범위를 제한한다.

MCP 자체가 사용자별 OAuth를 요구한다면 그 인증 흐름은 별도로 구성하고 검증한다. 터널은 인증 서버의 공개 접근성까지 자동으로 해결하지 않는다.

## 재사용 가능한 로컬 배치 구조

터널 런타임은 사용자 프로젝트와 오래된 원격 플러그인 설치로부터 분리한다.

```text
local-mcp-connector/
  bin/
    tunnel-client/<version>/
  runtime/
    <mcp-name>/<version>/
  profiles/
  state/
  logs/
  .env
  connect.<platform-script>
```

이 구조의 목적은 다음과 같다.

- MCP 런타임 버전을 의도적으로 고정한다.
- 터널 클라이언트와 MCP 서버의 업데이트를 분리한다.
- 사용자 프로젝트의 패키지 상태에 영향을 주지 않는다.
- 이전 중계 플러그인을 제거해도 새 경로가 유지된다.
- 실행 스크립트, 프로필과 상태 위치를 한곳에서 관리한다.

런북에는 특정 다운로드 버전을 영구 고정하지 않는다. 설치 자동화는 공식 최신 릴리스 위치를 조회하되, 실제 운영 배치에서는 설치한 버전을 기록하고 검증 후 교체한다.

## 전환 절차

### 1. 기준선 수집

기존 경로에서 다음을 기록한다.

- 작은 읽기 전용 도구 호출의 전체 시간
- 로컬 MCP 또는 하위 프로세스의 실제 실행 시간
- 첫 출력까지의 시간
- 반환 결과 크기
- 동일 작업에서 발생한 MCP 호출 횟수

측정 명령은 프로젝트를 변경하지 않는 것으로 선택한다.

### 2. 터널 생성과 연결 범위 설정

OpenAI Platform에서 터널을 생성한다. 이름은 특정 구현 버전보다 연결 대상과 운영 범위를 나타내게 한다.

터널이 사용될 Platform 조직과 ChatGPT 워크스페이스를 연결한다. 터널이 보이지 않을 때는 클라이언트 설치보다 조직·워크스페이스 연결과 `Tunnels Use` 권한을 먼저 확인한다.

### 3. 런타임 API 키 발급

터널 실행 전용 키를 만들고 `Tunnels Read + Use`만 부여한다. 생성·수정 자동화까지 수행해야 하는 별도 운영 주체가 아니라면 `Manage`를 부여하지 않는다.

키는 한 번만 안전한 로컬 비밀 저장소에 기록하고 화면, 채팅, 로그와 저장소에 다시 노출하지 않는다.

### 4. 터널 클라이언트와 MCP 런타임 배치

터널 클라이언트와 MCP 런타임을 독립 디렉터리에 배치한다. 로컬 MCP가 패키지 실행기를 통해 매번 최신 버전을 탐색하거나 임시 설치하지 않도록 실제 실행 파일과 의존성을 확인한다.

다음 값은 설치 환경에 맞게 분리한다.

- 터널 식별자
- 런타임 키 참조
- 프로필 이름
- stdio 실행 명령 또는 사설 HTTP 주소
- 프로필 및 상태 디렉터리
- MCP에 필요한 환경 변수

### 5. 프로필 검증과 연결

공식 클라이언트의 진단 기능으로 프로필, 네트워크, 인증과 로컬 MCP 도달 가능성을 확인한다. 이후 런타임을 시작하고 다음 상태를 확인한다.

- 프로세스가 실행 중이다.
- health 상태가 정상이다.
- ready 상태가 정상이다.
- 터널 ID와 프로필이 의도한 대상이다.
- 로컬 관리 UI와 상태 엔드포인트가 외부 인터페이스에 노출되지 않았다.

관리형 백그라운드 프로세스로 실행하면 터미널 창이 계속 보이지 않는 것이 정상일 수 있다. 창의 존재가 아니라 health, ready와 실제 도구 호출로 판단한다.

### 6. OpenAI 제품에서 앱 연결

개발자 모드 앱 또는 지원되는 제품 설정에서 연결 방식을 Tunnel로 선택하고 생성한 터널을 연결한다.

MCP 수준 인증은 실제 MCP 서버 계약에 맞춘다. 로컬 stdio MCP에 OAuth가 없다는 이유만으로 임의의 OAuth URL을 만들지 않는다.

### 7. 기능 검증

다음 순서로 검증 범위를 넓힌다.

1. 부작용이 없는 작은 도구 한 개
2. 실제 사용 도구 한 개
3. 여러 도구가 필요한 대표 작업
4. 장시간 또는 대량 결과가 발생하는 작업

각 단계에서 로컬 실행 시간과 사용자에게 보이는 전체 시간을 구분한다. 작은 호출이 실패한 상태에서 대규모 작업으로 넘어가지 않는다.

### 8. 수명주기 구성

터널 호출은 런타임이 실행 중일 때만 동작한다. 운영 형태를 명시적으로 선택한다.

- 수동 실행: 개발·시험 환경에 적합
- 로그인 시 자동 시작: 개인 워크스테이션에 적합
- 운영체제 서비스 또는 관리형 배포: 상시 가용성이 필요한 환경에 적합

재부팅, 로그아웃, 프로세스 비정상 종료 후의 재시작 경로를 확인한다. 자동 시작을 구성하지 않았다면 사용자가 실행할 명확한 런처를 제공한다.

## 성능 검증 방법

### 측정 경계

다음 시간은 서로 다른 의미를 가진다.

| 측정 | 증명하는 것 | 증명하지 못하는 것 |
| --- | --- | --- |
| 로컬 명령 실행 시간 | MCP 또는 하위 도구의 실제 처리 시간 | MCP 왕복과 모델 처리 시간 |
| MCP 도구가 보고한 시간 | 도구 구현 내부에서 관측한 구간 | UI 전체 대기 시간 |
| 첫 도구 시작부터 마지막 결과까지 | 여러 호출이 진행된 도구 구간 | 요청 전 계획과 최종 답변 생성 |
| UI 전체 처리 시간 | 사용자가 체감한 전체 시간 | 각 내부 단계의 개별 원인 |

### 통제된 비교

원인을 분리할 때 한 번에 하나의 조건만 바꾼다.

#### 전송 경로 비교

- 동일한 MCP 버전
- 동일한 명령과 결과
- 동일한 호출 횟수
- 기존 중계 경로와 새 터널만 변경

#### 결과 크기 비교

- 동일한 명령
- 동일한 호출 횟수
- 한쪽은 전체 결과, 다른 쪽은 결과를 로컬에서 보유하고 크기·개수만 반환

결과를 한 줄 미리보기로 제한한다고 했을 때 원본이 한 줄짜리 JSON이면 전체 데이터가 반환될 수 있다. 성능 실험에서는 미리보기를 넣지 않고 문자 수나 항목 수만 반환해야 한다.

#### 호출 횟수 비교

- 동일한 명령과 반환 정보
- 한쪽은 여러 MCP 호출
- 다른 쪽은 한 호출 안에서 독립 작업을 처리

여러 호출을 하나로 합쳐도 로컬 시간이 조금만 줄어든다면 기존의 큰 지연을 프로세스 생성 비용으로 설명하지 않는다. 반대로 모델이 중간 결과를 보고 다음 행동을 결정해야 한다면 호출 수를 줄이는 것 자체를 목표로 삼지 않는다.

### 결과 해석

- 로컬 실행은 빠르고 새 터널의 작은 호출도 빠르면 기존 원격 중계 병목은 제거된 것이다.
- 전체 결과를 반환할 때만 느려지면 직렬화, 전송, 컨텍스트 적재와 모델 처리 구간을 추가로 본다.
- 결과가 작아도 호출 수에 따라 시간이 크게 늘면 도구 오케스트레이션 구간을 본다.
- 새 경로에서도 로컬 도구 시작 전 대기가 길면 터널 로그와 요청 수신 시각을 계측한다.
- 성능 문제를 해결하기 위해 도구 사용이나 필요한 결과를 일률적으로 금지하지 않는다. 측정된 병목과 작업 요구를 함께 판단한다.

## 전환 완료와 기존 경로 정리

새 경로에서 대표 작업이 성공하기 전에는 기존 연결을 제거하지 않는다. 검증 후 다음을 구분해서 정리한다.

1. 제품 UI의 이전 앱 또는 플러그인 연결
2. 로컬에서 실행 중인 이전 중계 프로세스
3. 이전 런타임의 자동 시작 항목
4. 더 이상 필요 없는 이전 자격 증명
5. 선택적으로 정리할 패키지 캐시

UI에서 앱을 제거해도 로컬 프로세스가 자동 종료된다고 가정하지 않는다. 반대로 패키지 캐시가 남아 있다는 이유만으로 이전 연결이 활성 상태라고 판단하지 않는다.

롤백 기간이 필요하면 이전 경로를 비활성 상태로 보관하고, 새 경로의 재부팅·재연결 검증 후 완전히 제거한다.

## 업데이트와 유지보수

- 설치된 터널 클라이언트와 MCP 런타임 버전을 각각 기록한다.
- 업데이트 전에 현재 health, ready와 대표 도구 결과를 기준선으로 남긴다.
- 한 번에 한 구성 요소만 업데이트하고 같은 기준선으로 다시 확인한다.
- 프로필과 비밀값은 버전별 실행 파일과 분리한다.
- 터널 클라이언트의 상태 형식이나 명령이 바뀌면 공식 문서와 내장 도움말을 기준으로 런처를 갱신한다.
- 별도 부트스트랩이나 맞춤 지침은 플러그인 업데이트로 자동 갱신되지 않을 수 있으므로 원본 템플릿과의 차이를 관리한다.

## 장애 확인 순서

### 터널이 제품에 보이지 않는다

1. 대상 워크스페이스가 터널에 연결됐는지 확인한다.
2. 운영자에게 `Tunnels Read + Use`가 있는지 확인한다.
3. 제품의 개발자 모드와 앱 정책을 확인한다.

### 도구 목록 또는 호출이 실패한다

1. 터널 런타임 프로세스가 실행 중인지 확인한다.
2. health와 ready 상태를 확인한다.
3. 공식 진단 명령으로 프로필을 확인한다.
4. 터널 호스트에서 로컬 MCP를 직접 실행할 수 있는지 확인한다.
5. 아웃바운드 HTTPS와 로컬 MCP 도달 가능성을 확인한다.

### 재부팅 후 동작하지 않는다

1. 자동 시작이 실제로 구성됐는지 확인한다.
2. 수동 런처로 시작한 뒤 health와 ready를 확인한다.
3. 런처가 비밀값, 프로필과 상태 디렉터리를 같은 위치에서 읽는지 확인한다.

### 여전히 느리다

1. 작은 읽기 전용 호출로 전송 경로를 확인한다.
2. 로컬 실행 시간과 UI 전체 시간을 분리한다.
3. 반환 크기를 기록한다.
4. 호출 횟수와 중간 모델 판단 횟수를 기록한다.
5. 한 번에 한 조건만 바꾼 비교를 수행한다.

## 사례에서 얻은 일반화된 교훈

한 로컬 개발 도구를 기존 원격 중계에서 Secure MCP Tunnel로 전환한 사례에서는 다음이 확인됐다.

- 기존 경로에서는 작은 프로세스 호출도 수 초의 중계 지연을 보였다.
- 새 터널에서는 로컬 명령과 MCP 프로세스 구간이 서브초 수준으로 확인됐다.
- 여러 로컬 명령의 실제 실행 합은 수 초 미만이었지만 UI 전체 시간은 훨씬 길 수 있었다.
- 약 3만 자 규모의 검색 결과를 그대로 반환했을 때와 요약 메타데이터만 반환했을 때 UI 전체 시간에 큰 차이가 있었다.
- 여러 프로세스를 한 번에 묶어서 줄어든 로컬 시간은 전체 지연을 설명할 만큼 크지 않았다.

따라서 전환 성공과 이후 작업 최적화를 구분해야 한다. 중계 경로를 교체해 전송 병목을 제거한 뒤에도 결과 크기와 모델 오케스트레이션 비용은 별도 작업 특성으로 남을 수 있다. 이를 이유로 모든 작업의 결과나 도구 호출을 제한해서는 안 된다.

## 완료 체크리스트

- [ ] 로컬 MCP를 터널 없이 직접 실행해 기능을 확인했다.
- [ ] 기존 경로의 로컬 실행 시간과 전체 시간을 구분해 기록했다.
- [ ] 터널이 올바른 조직과 워크스페이스에 연결됐다.
- [ ] 런타임 키에 필요한 최소 터널 권한만 부여했다.
- [ ] 비밀값이 저장소, 로그와 프로세스 인자에 노출되지 않는다.
- [ ] 터널 클라이언트와 MCP 런타임을 독립적으로 배치했다.
- [ ] health와 ready가 정상이다.
- [ ] 작은 도구와 대표 작업을 새 경로에서 실행했다.
- [ ] 재부팅 또는 재시작 절차를 확인했다.
- [ ] 이전 UI 연결과 로컬 프로세스를 별도로 정리했다.
- [ ] 업데이트와 키 교체 절차를 기록했다.
