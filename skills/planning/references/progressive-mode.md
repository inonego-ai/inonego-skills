# 점진적 계획 모드

복잡한 계획을 한 번에 확정하지 않고, `planning`의 기본 규칙 위에서 레이어별 초안, 질문, 정제, 확정 과정을 반복한다.

## 적용 조건

다음 중 하나 이상에 해당하면 사용한다.

- 시스템 규모가 크고 여러 하위 영역이 얽혀 있다.
- 요구사항, 범위, 성공 조건이 충분히 고정되지 않았다.
- 사용자의 선택을 받아야 하는 설계 분기점이 많다.
- 상위 방향을 확정하지 않으면 하위 작업을 안정적으로 나눌 수 없다.
- 한 번에 계획을 쓰면 추측이나 임의 결정이 많이 섞일 가능성이 높다.

단순한 계획, 이미 범위가 명확한 작업, 바로 실행 가능한 작은 작업에는 사용하지 않는다.

## 질문 체계

`asqu:guide`가 현재 환경에 설치되어 있고 사용 가능한 경우에는 그 질문 대기열을 사용한다.
사용할 수 없으면 현재 에이전트 환경이 제공하는 사용자 입력 수단을 사용하며, 점진적 계획만을 위해 별도 플러그인 설치를 요구하지 않는다.
`asqu:deep-dive`는 사용자가 deep dive나 계속 질문하는 방식을 명시적으로 요청한 경우에만 적용한다.

질문은 한 번에 너무 많이 던지지 말고, 다음 조건 중 하나를 만족할 때만 한다.

- 계획의 방향이나 범위를 바꾸는 결정이다.
- 중요한 가정이나 제약을 확정해야 한다.
- 사용자 선호나 tradeoff라서 파일, 코드, 문서 탐색으로 알 수 없다.

선택지가 있는 질문은 각 선택지의 차이를 설명한다.
추상적인 선택지는 가능한 경우 짧은 예시를 붙인다.
질문에는 왜 이 결정을 묻는지 맥락을 함께 제공한다.

## 의도와 범위 정렬

목적, 문제, 성공 조건, 범위가 흔들리면 먼저 정렬한다.

필요한 경우 WHAT과 WHY를 구분해 확인한다.

- WHAT: 무엇을 만들거나 바꾸려는가
- WHY: 어떤 문제를 해결하려는가

WHAT/WHY 확인은 항상 강제하지 않는다.
대화 맥락이나 기존 자료만으로 충분히 분명하면 다시 묻지 않는다.

범위가 흔들리거나 우선순위가 섞이면 MoSCoW 분류를 선택적으로 사용한다.

| 레벨 | 의미 |
|---|---|
| MUST | 반드시 포함 |
| SHOULD | 포함이 바람직함 |
| COULD | 여건이 허락하면 포함 |
| WON'T | 이번 범위에서 제외 |

MoSCoW는 모든 계획에 강제하지 않는다.
범위 협의가 필요한 복잡한 계획에서만 사용한다.

구현, 리팩터링, 기능 추가, 기존 동작 변경 계획이면 목표 상태와 현재 상태를 구분한다.
현재 구조에 가능한 수정안이나 사용자가 제시한 아이디어를 바로 계획의 기준으로 확정하지 않는다.

필요한 경우 다음 항목을 레이어 초안에 포함한다.

- 목표 상태: 요구가 처음부터 시스템에 포함되어 있었다면 자연스러운 구조나 동작
- 확인된 현재 상태: 실제 코드, 문서, 데이터, 설정에서 확인한 현재 구조
- 차이: 목표 상태와 현재 상태 사이의 책임, 흐름, 상태, 검증 경계 차이
- 이번 범위: 이번 계획에서 해소할 차이
- 남기는 차이: 이번 계획에서 해소하지 않는 차이와 이유

## 진행 순서

### 1. 주제와 레이어 결정

주제나 목표가 대화에서 이미 분명하면 그대로 시작한다.
불분명하면 현재 사용 가능한 사용자 입력 수단으로 목표를 확인한다.

토픽의 복잡도와 성격에 맞춰 레이어를 즉석으로 정한다.

- 단순한 주제는 3개 내외의 레이어로 둔다.
- 복잡한 주제는 더 세분화한다.
- 레이어 이름은 주제에 맞게 정한다.
- 예: 목표/구조/세부, 방향/설계/구현, 큰 그림/구성요소/세부 명세

레이어 구조가 계획 방향에 큰 영향을 주면 사용자에게 확인한다.

### 2. 기존 자료와 현재 상태 확인

사용자가 경로, 문서, 코드, 기존 계획을 제공했으면 먼저 확인한다.
제공된 자료가 없고 기존 자료 존재 여부가 계획에 중요하면 사용자에게 확인한다.

탐색은 계획 수립에 필요한 범위로 제한한다.
전체 코드를 무작정 훑지 말고, 레이어 판단과 리스크 식별에 필요한 자료를 우선 확인한다.

구현 계획을 최종 산출물로 만들려면 구현 방향을 바꿀 수 있는 핵심 전제를 확인한다.
확인하지 못한 전제가 크면 최종 산출물을 구현 계획으로 부르지 말고 조사 계획이나 설계 초안으로 낮춘다.

### 3. 레이어별 진행

각 레이어는 같은 흐름으로 진행한다.

| 단계 | 처리 |
|---|---|
| 초안 제시 | 레이어 목적에 맞는 초안을 작성한다. |
| 대안 제시 | 중요한 분기점이 있으면 대안, 장단점, 권장안을 제시한다. |
| 질문 | 확정이 필요한 결정만 현재 사용 가능한 입력 수단으로 묻는다. |
| 정제 | 사용자 응답을 반영하고 무엇이 바뀌었는지 명시한다. |
| 검증 | 상위 레이어와 충돌하지 않는지, 목표 상태와 현재 상태의 차이를 제대로 다루는지, 범위와 성공 조건을 보존하는지 점검한다. |
| 확정 | 문제가 없으면 해당 레이어를 확정하고 다음 레이어로 내려간다. |

상위 레이어가 확정되지 않았으면 하위 레이어를 최종 확정하지 않는다.
하위 레이어에서 상위 결정의 문제가 드러나면 상위 레이어로 되돌아가 최소 범위로 수정한다.

## 피드백 루프

사용자 피드백이나 자체 점검에서 충돌이 발견되면 다음 순서로 처리한다.

1. 충돌 보고: 무엇이 충돌하는지 한 줄로 정리한다.
2. 영향 분석: 영향을 받는 레이어, 범위, 결정 항목을 나열한다.
3. 선택 제시: 해당 항목만 수정할지, 상위 레이어를 수정할지, 열린 이슈로 둘지 제시한다.
4. 수정 실행: 선택된 범위만 수정한다.
5. 재확인: 수정이 다른 확정 항목과 충돌하지 않는지 확인한다.
6. 하위 영향 확인: 이미 정한 하위 레이어는 영향 받는 부분만 재검토한다.

## 하위 계획 위임

진행 중 특정 구성요소가 그 자체로 크고 복잡한 서브시스템이면 별도 하위 계획으로 분리할 수 있다.

분리 조건:

- 별도의 레이어 분해가 필요할 만큼 충분히 크다.
- 연결 지점과 제약만 정의하면 나머지 계획에 직접 영향을 주지 않는다.

분리할 때는 다음을 기록한다.

- 하위 계획 이름
- 담당 범위
- 상위 계획과의 연결 지점
- 유지해야 할 제약
- 나중에 통합할 때 확인할 기준

## 최종 정리

확정된 레이어를 통합해 계획으로 정리한다.

최종 계획에는 `planning`의 문서 형식, 계획 기준 정렬, 작업 분해, 병렬 작업 분해, 검증 계획 규칙을 적용한다.
필요하면 표, 트리 구조, Mermaid 다이어그램, 체크리스트를 사용한다.

코드 프로젝트 계획이면 관련 코드, 문서, 설정과의 정합성을 확인한 뒤 작성한다.
확인하지 못한 내용은 추측으로 확정하지 말고 확인 필요 항목으로 남긴다.
