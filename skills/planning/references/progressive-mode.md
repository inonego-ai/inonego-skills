# 점진적 계획 모드

복잡한 계획을 한 번에 확정하지 않고 `planning`의 기본 규칙 위에서 계층별 초안 → 질문 → 정제 → 확정을 반복한다.

## 적용 조건

시스템이 크고 하위 영역이 얽혀 있거나, 요구·범위·성공 조건이 덜 고정됐거나, 사용자 선택이 필요한 설계 분기점이 많거나, 상위 방향 없이는 하위 작업을 안정적으로 나눌 수 없거나, 한 번에 쓰면 추측이 많이 섞일 때 사용한다. 단순하거나 범위가 명확한 작업에는 사용하지 않는다.

## 질문

- 현재 환경의 사용자 입력 수단을 쓰며 별도 질문 플러그인을 요구하지 않는다.
- 질문 전에 대화와 자료로 확인 가능한 내용을 먼저 확인한다. 질문은 상위 방향·범위를 바꾸는 결정, 해석이 갈리는 중요한 제약·성공 조건, 코드·문서에서 알 수 없는 선호·상충 관계에만 쓴다.
- 비차단성 불확실성은 가장 근거 있는 해석으로 진행하고 가정으로 표시한다. 선택지는 결과 차이와 지금 결정해야 하는 이유를 함께 설명한다.

## 의도와 범위 정렬

- 목적, 문제, 성공 조건, 범위가 흔들릴 때만 무엇(만들거나 바꿀 것)과 이유(해결할 문제)를 구분해 정렬한다. 맥락으로 분명하면 다시 묻지 않는다.
- 우선순위가 섞이면 MoSCoW(필수 / 권장 / 선택 / 제외)를 선택적으로 쓴다. 범위 협의가 필요한 복잡한 계획에만 쓴다.
- 구현·리팩터링·동작 변경 계획은 사용자 아이디어나 현재 구조에 가능한 수정안을 기준으로 바로 확정하지 않고 필요에 따라 목표 상태, 확인된 현재 상태, 차이, 이번 범위, 남기는 차이를 계층 초안에 포함한다.

## 진행 순서

1. **주제와 계층:** 주제가 분명하면 그대로 시작하고 아니면 목표를 확인한다. 복잡도에 맞춰 계층을 즉석으로 정한다(단순하면 3개 내외, 복잡하면 세분화. 예: 목표/구조/세부). 방향에 큰 영향을 주면 사용자에게 확인한다.
2. **자료와 현재 상태:** 사용자가 준 경로·문서·코드·기존 계획을 먼저 확인하고, 탐색은 계층 판단과 위험 식별에 필요한 범위로 제한한다. 구현 방향을 바꿀 핵심 전제를 확인하지 못했으면 구현 계획이 아니라 조사 계획·설계 초안으로 낮춘다.
3. **계층별 진행:** 초안 → (중요 분기점은) 대안·장단점·권장안 → 확정이 필요한 결정만 질문 → 응답 반영과 변경점 명시 → 상위 계층 충돌·목표/현재 차이·범위·성공 조건 점검 → 확정. 상위 계층이 확정되지 않았으면 하위를 확정하지 않고, 하위에서 상위 결정의 문제가 드러나면 상위로 돌아가 최소 범위로 수정한다.

## 피드백 반영

충돌이 발견되면 충돌 한 줄 보고 → 영향받는 계층·범위·결정 나열 → 선택 제시(해당 항목만 수정 / 상위 수정 / 미해결로 둠) → 선택된 범위만 수정 → 다른 확정 항목과의 충돌 재확인 → 하위 계층의 영향 부분만 재검토 순으로 처리한다.

## 하위 계획 위임

구성요소가 별도 계층 분해가 필요할 만큼 크고 연결 지점·제약만 정의하면 나머지에 영향이 없을 때 하위 계획으로 분리한다. 이름, 담당 범위, 상위 계획과의 연결 지점, 유지할 제약, 통합 시 확인 기준을 기록한다.

## 최종 정리

확정된 계층을 통합하고 `planning`의 문서 형식, 작업 분해, 병렬 작업, 검증 계획 규칙을 적용한다. 필요하면 표, 트리, Mermaid, 체크리스트를 쓴다. 코드 프로젝트는 관련 코드·문서·설정과의 정합성을 확인한 뒤 쓰고, 확인하지 못한 내용은 확인 필요 항목으로 남긴다.
