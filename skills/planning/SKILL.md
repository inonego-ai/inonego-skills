# 계획 수립

계획은 실행 완료가 아니다. 목적, 성공 조건, 범위, 제약, 실행 순서와 검증 기준을 정렬하는 산출물이다.

## 시작 기준

먼저 다음을 구분한다.

- 목적: 무엇을 달성하려는가
- 성공 조건: 완료 여부를 어떻게 판단하는가
- 제약: 반드시 지켜야 하는 조건
- 선호: 가능하면 따를 방향
- 아이디어: 아직 검증되지 않은 해결 후보

결과·범위·외부 계약을 실질적으로 바꿀 수 있고 현재 대화, 코드, 문서나 설정으로 해결할 수 없는 불확실성만 사용자에게 확인한다. 그 외에는 가장 근거 있는 해석으로 진행하고 중요한 가정을 표시한다.
사용자가 제안한 구현 아이디어와 에이전트가 떠올린 초안은 목적·성공 조건·제약을 보존하는지 확인하기 전까지 최종 계획으로 확정하지 않는다.

## 계획 종류

| 종류 | 목적 | 필요한 확인 수준 |
|---|---|---|
| 조사 계획 | 무엇을 확인해야 하는지 정리 | 미확인 전제를 조사 항목으로 남길 수 있음 |
| 설계 초안 | 가능한 방향과 구조 후보 비교 | 사실, 가정과 후보를 구분 |
| 구현 계획 | 바로 실행 가능한 순서와 검증 기준 확정 | 구현 방향을 바꿀 핵심 전제를 먼저 확인 |

구현 계획에 필요한 파일, 타입, API, 데이터 구조, UI·씬·프리팹, 테스트 구조를 확인하지 못했고 그 전제가 방향을 바꿀 수 있으면 조사 계획이나 설계 초안으로 낮춘다.

## 목표 상태와 현재 상태

구현, 리팩터링, 기능 추가나 기존 동작 변경 계획에서는 현재 구조에 가능한 최소 수정을 붙이는 방식을 기준으로 삼지 않는다.
요구가 처음부터 시스템에 포함되어 있었다면 자연스러운 구조와 동작을 먼저 정하고 현재 상태와의 차이를 본다.

계획에는 필요에 따라 다음을 구분한다.

- 목표 상태: 목적, 성공 조건과 제약을 만족하는 자연스러운 구조나 동작
- 확인된 현재 상태: 실제 코드, 데이터, 문서, 설정에서 확인한 현재 구조
- 차이: 책임, 상태 소유권, 데이터 흐름, 인터페이스와 검증 경계의 차이
- 이번 범위: 이번 작업에서 해소할 차이
- 남기는 차이: 이번에 해소하지 않는 차이와 이유

책임·상태 소유권·데이터 흐름 재구성이 핵심이면 `target-state-implementation`을 함께 적용한다.
목표 상태가 요청 범위를 넘는다고 목표 자체를 현재 구조에 맞춰 낮추지 말고, 이번 범위와 남기는 차이를 분리한다.

## 범위

포함 범위와 의도적인 제외 범위를 구분한다.
사용자가 빠른 최소 수정이나 특정 제약을 명시하면 그 제약 때문에 목표 상태와 달라지는 부분을 숨기지 않는다.
계획을 진행하며 후속 정정이 생기면 작업 단계만 고치지 말고 범위와 완료 기준도 갱신한다.

## 작업 분해

각 단계는 실행자가 새 설계 결정을 하지 않아도 움직일 수 있는 크기로 나눈다.
가능하면 다음을 포함한다.

- 대상
- 수행할 변경
- 변경 이유
- 완료 판단 기준
- 필요한 검증

신규 구조 작성, 연결, 상태 생명주기와 검증을 한 단계에 과하게 몰아넣지 않는다.
API·데이터 흐름·알고리즘은 구현 방향을 결정할 정도로만 고정하고, 확인되지 않은 private 세부 구현을 계획에서 미리 결정하지 않는다.

## 병렬 작업

서로 독립적인 작업 흐름이 둘 이상이면 병렬 진행 가능성을 검토한다.
다음 조건을 모두 만족할 때 분리할 수 있다.

- 서로 다른 파일·기능·하위 시스템을 다룬다.
- 한 작업의 결과가 다른 작업의 설계 방향을 바꾸지 않는다.
- 같은 상태나 파일을 동시에 수정하지 않는다.
- 성공 조건과 검증 방법을 독립적으로 설명할 수 있다.

공통 원인이나 구조 판단이 먼저 필요한 경우에는 병렬화를 우선하지 않는다. 병렬 결과는 통합 시 충돌, 중복 책임과 전체 정합성을 다시 확인한다.

## 위험 요소

실패 가능성을 단순 경고 목록으로 남기지 않는다. 구현 방향을 바꿀 위험은 선행 조사나 작업 순서로, 결과 검증이 필요한 위험은 검증 계획으로 연결한다.
근거 없는 가능성은 위험 항목을 늘리는 이유로 사용하지 않는다.

## 검증 계획

계획에는 작업 성격에 맞는 허용된 검증 경로를 포함한다.

- 정적 확인과 형식 검사
- 빌드 또는 컴파일
- 기존 테스트 실행
- 실제 실행과 수동 동작 확인
- 시각 결과 비교
- 로그·콘솔 오류 확인
- 변경 차이와 결과물 검토

새 테스트가 필요해 보여도 테스트 변경 권한이 없으면 구현 단계로 넣지 않는다. 검증할 계약과 이유가 중요하면 `테스트 후보`로만 기록한다.
테스트 작업이 승인된 경우에만 `test-design`으로 기대 결과의 근거와 검증 경계를 정한다.
수동 검증 절차가 핵심이면 [검증 가이드](references/verification-guide.md)를 적용해 실행 가능한 절차와 기대 결과를 작성한다.

## 문서 표현

계획의 기본 구조는 작업 성격에 맞춰 선택한다. 형식 자체를 채우는 것이 목적이 아니다.
구조, 비교나 흐름을 시각적으로 표현해야 하면 [계획 문서 표현](references/document-format.md)을 적용한다.

기본적으로 다음 섹션 중 필요한 것만 사용한다.

- 배경 또는 목적
- 목표 상태
- 확인된 현재 상태
- 설계 방향
- 범위 / 범위 외
- 작업 순서
- 검증 계획
- 가정 / 확인 필요

## 점진적 계획

요구가 크고 여러 설계 분기점이 얽혀 있어 상위 방향을 먼저 정해야 하거나 한 번에 확정하면 추측이 많이 섞이는 경우 [점진적 계획 모드](references/progressive-mode.md)를 적용한다.
단순한 계획, 범위가 명확한 작업이나 바로 실행 가능한 작은 작업에는 사용하지 않는다.

## 요구 연결과 종료 기준

여러 단계 작업은 최초 요청과 후속 추가·정정·제외를 요구 목록으로 관리한다.
종료 전에는 계획 단계의 완료 표시가 아니라 각 요구가 실제 작업 단계와 검증 기준에 연결됐는지 확인한다.
필수 요구가 빠졌다면 계획을 보완하고, 확인하지 못한 전제가 남으면 확정 사실처럼 쓰지 않는다.

계획을 완료라고 표현하는 것은 계획 산출물이 준비됐다는 뜻일 뿐 구현 완료를 의미하지 않는다.
