# 계획 수립

계획, 설계, 작업 분해, 실행 전 초안 정리가 필요할 때 사용한다.

계획은 실행 완료가 아니다. 계획은 실행 전에 목적, 범위, 순서, 검증 기준을 정렬하는 산출물이다.

## 기본 원칙

계획은 세부 작업부터 쓰지 않는다. 먼저 계획의 종류, 목적, 성공 조건, 범위, 제약을 정렬한다.

- 목적: 무엇을 달성하려는가
- 성공 조건: 완료 여부를 어떻게 판단하는가
- 범위: 이번 계획에 포함할 것과 제외할 것
- 제약: 반드시 지켜야 하는 조건
- 선호: 가능하면 따를 방향
- 아이디어: 아직 검증되지 않은 해결 후보

목적, 성공 조건, 제약이 불명확하면 계획을 확정하지 말고 사용자에게 확인한다.
사용자의 아이디어나 에이전트가 만든 초안은 최종 계획이 아니라 후보안으로 다룬다.
후보안은 목적, 성공 조건, 제약을 보존하는지 확인한 뒤 계획에 반영한다.

## 계획 종류와 확인 수준

계획을 작성하기 전에 산출물의 성격을 구분한다.
계획 이름과 실제 확인 수준이 맞아야 한다.

| 종류 | 목적 | 확인 수준 |
|---|---|---|
| 조사 계획 | 무엇을 확인해야 하는지 정리한다. | 확인되지 않은 전제가 있어도 된다. 작업은 조사와 판단 중심이다. |
| 설계 초안 | 가능한 방향, 선택지, 구조 후보를 정리한다. | 추정과 아이디어를 포함할 수 있지만 확정 사실과 구분한다. |
| 구현 계획 | 바로 구현할 수 있는 실행 순서와 검증 기준을 정한다. | 구현 방향을 바꿀 수 있는 핵심 전제를 먼저 확인한다. |

구현 계획에서는 관련 파일, 타입, API, 데이터 구조, UI/씬/프리팹, 테스트 구조처럼 구현 방향을 바꿀 수 있는 전제를 확인한 뒤 작성한다.
핵심 전제를 확인하지 못했으면 구현 계획으로 단정하지 말고 조사 계획이나 설계 초안으로 낮춘다.

확인하지 못한 항목을 확정된 구조처럼 쓰지 않는다.
확인 필요 항목은 남길 수 있지만, 구현자가 그 항목을 새로 결정해야 하는 상태라면 구현 계획이 아니다.

## 계획 기준 정렬

구현, 리팩터링, 기능 추가, 기존 동작 변경 계획에서는 요구가 처음부터 시스템에 포함되어 있었다면 어떤 구조와 동작이 자연스러운지 먼저 정리한다.

현재 구조에 가능한 최소 수정을 붙이는 방식, 사용자가 제시한 구현 아이디어, 에이전트가 먼저 떠올린 해결책을 계획의 기준으로 삼지 않는다.

구현 계획에는 가능하면 다음 구분이 드러나야 한다.

- 목표 상태: 목적, 성공 조건, 제약을 만족하는 자연스러운 최종 구조나 동작
- 확인된 현재 상태: 실제 코드, 데이터, 문서, 씬, 설정에서 확인한 현재 구조
- 차이: 목표 상태와 현재 상태 사이의 구조, 책임, 데이터 흐름, 상태, 검증 경계 차이
- 이번 범위: 이번 작업에서 해소할 차이
- 남기는 차이: 이번에 해소하지 않는 차이와 그 이유

목표 상태가 요청 범위를 크게 넘으면 목표 상태 자체를 낮추지 말고 차이를 분리한다.
이번 계획에서 해소할 차이와 남길 차이를 명확히 나누고, 남기는 차이에는 이유를 적는다.
사용자가 빠른 최소 수정이나 특정 제약을 명시했다면 그 제약 때문에 목표 상태와 달라지는 부분을 숨기지 않는다.

## 범위 관리

계획에는 포함 범위와 제외 범위를 분리한다.

`## 범위 외`에는 이번 작업에서 하지 않을 일을 적는다.
범위 외 항목은 계획 누락이 아니라 의도적인 제외임을 알 수 있게 작성한다.

예시:

```markdown
## 범위 외

- 외부 공개 계약 변경은 하지 않는다.
- 기존 데이터 형식 변경은 하지 않는다.
- 별도 인프라 구축은 이번 범위에서 제외한다.
```

## 문서 형식

계획 문서는 가능하면 한글 섹션명을 사용한다.

기본 골격:

```markdown
# {작업명} 계획

## 배경

## 목표 상태

## 확인된 현재 구조

## 설계 방향

## 작업 순서

## 검증 계획
```

필요에 따라 다음 섹션을 추가한다.

- `## 범위`
- `## 범위 외`
- `## 구조`
- `## 변경 대상`
- `## 설계 결정`
- `## 처리 흐름과 주요 규칙`
- `## 주의사항`
- `## 위험 요소와 대응`
- `## 핵심 대상`
- `## 테스트`
- `## 완료 기준`
- `## 가정 / 확인 필요`

영어 섹션명은 기존 문서 스타일을 따라야 하거나 사용자가 요청한 경우에만 사용한다.

## 문서 스타일

계획은 긴 문단만으로 쓰지 않는다. 사용자가 빠르게 스캔할 수 있도록 트리, 표, 단계 제목, 코드블록을 적절히 사용한다.

- 제목은 `# {대상} 계획`, `# {대상} 정리 계획`, `# {대상} 실행 계획`처럼 목적이 바로 보이게 쓴다.
- 큰 섹션은 `##`, 작업 단위는 `###`를 사용한다.
- 작업 제목은 `### 1단계 - {대상} {행위}`처럼 작성한다.
- 순서가 중요한 작업은 단계 번호를 사용한다.
- 독립 작업이면 제목에 `(독립)`을 붙일 수 있다.
- 비교, 이동, 생성/수정/삭제 목록은 표를 사용한다.
- 구조나 관계가 중요하면 트리 구조를 우선한다.

## 구조 표현

구조나 관계가 중요한 계획이면 작업 단계보다 먼저 목표 상태를 보여준다.

```text
Root/
├── ExistingArea/                           ← 기존
│   ├── ExistingItem                        ← 수정
│   └── NewItem                             ← 신규
├── MovedArea/                              ← 이동
│   └── MovedItem                           ← 기존 위치에서 이동
└── RemovedArea/                            ← 삭제 또는 통합
```

트리 작성 규칙:

- 루트 경로 또는 최상위 대상을 첫 줄에 둔다.
- 하위 구조를 실제 배치와 비슷하게 정렬한다.
- 상태 표기는 오른쪽에 `← 신규`, `← 수정`, `← 이동`, `← 삭제`, `← 기존`으로 붙인다.
- 기존 항목을 모두 나열할 필요가 없으면 `(기존 항목들)`, `SubArea/ ...`처럼 생략을 명시한다.
- 파일 구조, 문서 구조, UI 계층, 데이터 구조, 작업 흐름 구조에 모두 사용할 수 있다.
- 구조 변화가 적거나 비교가 핵심이면 표로 대체할 수 있다.

표 예시:

```markdown
| 대상 | 작업 | 내용 |
|---|---|---|
| `기존 대상` | 수정 | 책임 정리 |
| `신규 대상` | 신규 | 새 진입점 |
| `통합 대상` | 삭제 | `신규 대상`으로 흡수 |
```

### Mermaid 사용 기준

파일·폴더 경로와 배치는 텍스트 트리로 표현한다. 구조, 관계, 실행 순서, 상태 전이가 글보다 시각적으로 명확해지는 경우에는 Mermaid 다이어그램을 선택적으로 사용한다.

- `flowchart`: 컴포넌트 관계, 데이터 흐름, 조건 분기, 처리 절차
- `sequenceDiagram`: 컴포넌트·모듈·외부 시스템 사이의 호출과 상호작용 순서
- `classDiagram`: 클래스·타입·인터페이스의 구조적 관계
- `stateDiagram-v2`: 상태와 상태 전이

다이어그램은 관계나 흐름을 실제로 설명할 때만 추가한다. 단순한 파일 구조는 트리를, 단순한 비교나 목록은 표를 우선한다. Mermaid를 사용할 때는 `mermaid` 코드블록을 사용하고, 확인된 현재 구조·목표 구조·신규/수정/이동 대상을 구분해 표시한다. 확인하지 않은 구조나 흐름은 확정된 사실처럼 다이어그램에 넣지 않는다.

## 설계 방향과 처리 흐름

구현 계획은 코드 명세서가 아니다.
API, 데이터 흐름, 알고리즘은 구현자가 방향을 잃지 않을 정도로 작성하되, 기존 코드 패턴에 맞춰 조정할 여지는 남긴다.

다만 구현 결과를 좌우하는 방향은 빠뜨리지 않는다.

- 새 책임이 어느 계층, 컴포넌트, 모듈에 들어가는지
- 외부에 드러나는 API, 설정, 데이터 모델, 이벤트, 파일 포맷, 직렬화 참조가 생기는지
- 데이터가 읽히고 변환되고 소비되는 큰 흐름
- 정렬, 필터링, 그룹핑, 병합, 상태 전환처럼 결과를 좌우하는 처리 규칙
- 실패, 빈 결과, 누락 데이터에 대한 기본 정책
- 기존 계약을 유지해야 하는 부분

구체 이름, 시그니처, 내부 private 메서드, 필드 구성은 확정된 경우에만 고정한다.
확정되지 않은 내부 구현 세부사항을 계획이 과하게 묶지 않도록 한다.

## 작업 분해

작업은 실행자가 바로 움직일 수 있게 나눈다.

각 작업은 가능하면 다음을 포함한다.

- 대상
- 수행할 변경
- 변경 이유
- 완료 판단 기준
- 필요한 검증

위험 요소에 적은 내용 중 구현 실패를 일으킬 수 있는 항목은 작업 순서나 검증 계획으로 승격한다.

작업 단계는 구현자가 새 설계 결정을 하지 않아도 움직일 수 있는 크기로 나눈다.
한 단계에 신규 구조 작성, UI/프리팹 구성, 상태 생명주기, 테스트, 연결 작업을 과하게 몰아넣지 않는다.

작업 예시:

```markdown
### 1단계 - 구조 정리

**대상**
- 이동: `기존 영역/항목` -> `새 영역/항목`
- 수정: `새 영역/설정`

**작업**
- 관련 항목이 한 구조 아래에 모이도록 위치를 정리한다.
- 이동 후 참조나 연결 정보를 갱신한다.

**완료 기준**
- 새 위치에서 정상적으로 참조된다.
- 기존 사용 흐름이 유지된다.
```

구체적인 작업 계획이 필요한 경우에는 실제 대상, 명령, 기대 결과를 명확히 적는다.
다만 모든 단계에 코드블록을 강제하지 않는다.

## 병렬 작업 분해

계획에 서로 독립적인 작업 흐름이 2개 이상 있으면 병렬 진행 가능성을 검토한다.

병렬 작업으로 분리할 수 있는 경우:

- 서로 다른 파일, 기능, 하위 시스템, 문서 영역을 다룬다.
- 한 작업의 결과를 알아야 다른 작업을 시작할 필요가 없다.
- 같은 파일이나 같은 상태를 동시에 수정하지 않는다.
- 각 작업의 성공 조건과 검증 방법을 독립적으로 설명할 수 있다.

병렬 작업으로 분리하지 않는 경우:

- 하나의 원인이나 구조 변경이 여러 문제를 함께 해결할 수 있다.
- 전체 시스템 맥락을 먼저 이해해야 한다.
- 여러 작업이 같은 파일, 같은 데이터, 같은 실행 상태를 공유한다.
- 한 작업의 결정이 다른 작업의 설계 방향을 바꿀 수 있다.

병렬 작업을 계획에 포함할 때는 각 작업에 다음을 적는다.

- 독립 범위: 담당할 파일, 기능, 문서, 하위 시스템
- 목표: 무엇을 확인하거나 변경해야 하는지
- 제약: 건드리지 말아야 할 영역, 유지해야 할 동작
- 산출물: 조사 결과, 변경 요약, 위험 요소, 검증 결과
- 통합 기준: 결과를 합칠 때 확인해야 할 충돌과 전체 검증

병렬 작업 결과를 통합할 때는 개별 결과만 믿지 말고 전체 관점에서 다시 확인한다.

- 같은 파일이나 같은 책임을 중복 수정했는지 확인한다.
- 개별 작업의 결론이 서로 충돌하지 않는지 확인한다.
- 전체 빌드, 테스트, 수동 검증 중 이번 요청에서 허용된 통합 후 검증 경로만 실행한다.
- 병렬 작업자가 놓칠 수 있는 공통 원인이나 구조적 문제를 다시 점검한다.

## 검증 계획

사용자가 테스트를 만들거나 추가하라고 명시하기 전에는 새 테스트 작성 단계를 계획에 넣지 않는다.
테스트가 필요해 보여도 승인 전에는 검증할 계약과 이유를 `테스트 후보`로만 기록한다.
테스트 실행, 컴파일, 실제 실행, 수동·시각 확인은 각각 별도 검증 범위로 표시한다.
계획에는 요청과 작업 성격에 맞는 허용된 검증 경로를 반드시 포함한다.

검증은 작업 성격에 맞게 선택한다.

- 자동 테스트
- 빌드 또는 컴파일 확인
- 린트/포맷 확인
- 수동 동작 확인
- 기존 동작 회귀 확인
- 로그/콘솔 에러 확인
- 결과물 검토
- 사용자 확인

사용자가 테스트 작업을 명시적으로 요청했고 테스트의 필요성, 테스트 후보, 테스트 추가/수정/삭제, 테스트 품질, 회귀 테스트, 자동 테스트 범위를 판단해야 하면 먼저 `test-design` 스킬을 사용한다.
사용자가 테스트 관련 누락, 보강, 품질, 회귀 검증, 자동 검증에 대해 피드백하면 이를 테스트 판단 상황으로 보고 `test-design`을 먼저 사용한다.

테스트 작업 권한을 확인한 뒤 `test-design` 판단 결과에 따라 다음 중 하나로 계획에 반영한다.

- 테스트를 추가하거나 수정한다.
- 기존 테스트 또는 다른 검증 명령으로 충분하다고 적는다.
- 테스트보다 빌드, 정적 검사, 수동 검증, 로그 확인 등 다른 검증 경로가 적절하다고 적는다.
- 근거가 부족하면 확인 필요 항목으로 남긴다.

테스트 계획은 "테스트 파일을 추가한다"는 작업 목록이 아니라, `test-design` 기준으로 어떤 관찰 가능한 계약을 검증할지 정리하는 항목이다.

## 요구 연결과 완료 대조

여러 단계 작업은 최초 요청과 이후 추가·정정·제외를 요구 목록으로 관리한다.
사용자가 요구를 바꾸면 작업 단계만 수정하지 말고 요구 목록도 함께 갱신한다.

| 요구 항목 | 출처 | 연결된 단계 | 상태 | 실제 결과 | 근거 |
|---|---|---|---|---|---|
| 최초 요청 또는 후속 요구 | 최초 요청 / 후속 메시지 | 단계 번호 | 완료 / 부분 완료 / 미완료 / 확인 불가 / 사용자 제외 | 산출물 또는 남은 일 | 파일, 변경 차이, 실행 결과 등 |

종료 전에는 계획 단계의 완료 표시가 아니라 요구 목록을 기준으로 빠진 항목을 확인한다.
계획 자체가 최초 요청이나 후속 정정을 누락했을 가능성도 확인한다.
필수 요구가 남아 있으면 계획 또는 구현을 계속하고, 실제 장애가 있을 때만 부분 완료와 이유를 적는다.

수동 검증이 포함되면 `수동 확인`처럼 적지 말고, 실행자가 그대로 따라 할 수 있는 수동 검증 매뉴얼을 작성한다.

수동 검증 매뉴얼에는 가능하면 다음을 포함한다.

- 준비 상태: 필요한 화면, 데이터, 계정, 환경, 설정
- 실행 절차: 어떤 순서로 무엇을 조작할지
- 기대 결과: 각 절차 후 무엇이 보여야 하거나 유지되어야 하는지
- 실패 신호: 어떤 상태가 나오면 실패로 볼지
- 회귀 확인: 기존에 유지되어야 하는 동작이 있으면 확인 절차

검증 예시:

```markdown
## 검증 계획

1. 자동 검증 또는 빌드가 통과하는지 확인
2. 수동 검증 매뉴얼에 따라 대표 사용 흐름을 확인
3. 기존 동작이 유지되는지 확인
4. 오류 로그가 없는지 확인

### 수동 검증 매뉴얼

**준비 상태**
- 검증 대상 결과물을 실행하거나 연다.
- 검증에 필요한 기본 데이터와 환경이 준비되어 있는지 확인한다.

**실행 절차**
1. 검증 대상 위치로 이동한다.
2. 주요 동작을 실행한다.
3. 결과 상태를 확인한다.
4. 되돌리기, 재실행, 반복 실행이 필요한 경우 함께 확인한다.

**기대 결과**
- 의도한 결과가 표시되거나 생성된다.
- 기존 상태가 불필요하게 깨지지 않는다.
- 새 오류 메시지나 로그가 발생하지 않는다.

**실패 신호**
- 결과가 표시되지 않거나 잘못 표시된다.
- 기존 사용 흐름이 막힌다.
- 예외, 오류 로그, 비정상 종료가 발생한다.
```

## 위험 요소와 대응

위험 요소는 단순 경고 목록으로 끝내지 않는다.
각 위험은 대응 작업, 확인 필요 항목, 검증 항목 중 하나로 연결한다.

예시:

```markdown
| 위험 요소 | 대응 |
|---|---|
| 기존 UI 컴포넌트가 특정 화면 상태에 강하게 의존할 수 있음 | 재사용 가능 여부를 먼저 확인하고, 불가능하면 전용 표시 컴포넌트로 분리 |
| 씬 참조 누락은 컴파일로 잡히지 않음 | 수동 검증 매뉴얼에 씬 참조 확인 절차 포함 |
```

## 점진적 계획 모드

요구사항이 크거나 불명확하고 한 번의 계획으로 확정하기 어려우면 점진적 계획 모드를 사용한다.

점진적 계획 모드는 `planning`의 기본 원칙, 문서 형식, 작업 분해, 검증 기준 위에 레이어별 초안, 질문, 정제, 확정 루프를 얹는 방식이다.

다음 경우에는 [progressive-mode.md](references/progressive-mode.md)를 읽고 적용한다.

- 시스템 규모가 크고 여러 하위 영역이 얽혀 있다.
- 사용자의 선택을 받아야 하는 설계 분기점이 많다.
- 요구사항, 범위, 성공 조건이 아직 충분히 고정되지 않았다.
- 한 번에 계획을 쓰면 추측이 많이 섞일 가능성이 높다.
- 상위 방향을 확정한 뒤 하위 세부 계획을 나눠야 한다.

단순 계획에는 점진적 계획 모드를 사용하지 않는다.

## 자체 점검

계획을 제시하기 전에 확인한다.

- 계획 종류와 제목이 실제 확인 수준과 맞는가
- 목적과 성공 조건이 드러나는가
- 포함 범위와 제외 범위가 구분되는가
- 후보안을 최종 계획으로 착각하지 않았는가
- 목표 상태, 확인된 현재 상태, 차이, 이번 범위가 구분되는가
- 현재 구조에 맞춘 타협안을 계획의 기준으로 삼지 않았는가
- 확인하지 않은 파일, 타입, API, 데이터 구조, 씬 오브젝트를 확정된 사실처럼 쓰지 않았는가
- 구현 방향을 좌우하는 API, 데이터 흐름, 처리 규칙이 빠지지 않았는가
- 확정되지 않은 내부 구현 세부사항을 과하게 고정하지 않았는가
- 작업 순서가 자연스러운가
- 각 단계가 실행 가능한가
- 위험 요소가 대응 작업이나 검증 항목으로 반영되었는가
- 병렬 가능한 작업과 순차 진행해야 할 작업이 구분되는가
- 검증 경로가 있는가
- 명시적 요청 없이 새 테스트 작성 단계를 넣지 않았는가
- 테스트 생성, 테스트 실행, 컴파일, 실제 실행, 수동·시각 확인을 구분했는가
- 수동 검증이 있다면 따라 할 수 있는 매뉴얼이 있는가
- 추측이 계획에 섞였으면 확인 필요 항목으로 표시했는가
- 최초 요청과 후속 추가·정정·제외가 요구 목록에 모두 들어 있는가
- 계획의 완료 표시와 사용자 요청의 완료를 구분했는가
