# 계획 수립

계획은 실행 완료가 아니라 목적, 성공 조건, 범위, 제약, 실행 순서, 검증 기준을 정렬하는 산출물이다. 계획이 준비됐다는 말은 구현 완료를 뜻하지 않는다.

## 시작 기준

- 목적, 성공 조건, 제약(필수), 선호(가능하면), 아이디어(미검증 후보)를 구분한다.
- 결과·범위·외부 계약을 바꾸고 현재 자료로 풀 수 없는 불확실성만 사용자에게 확인한다. 그 외에는 가장 근거 있는 해석으로 진행하고 중요한 가정을 표시한다.
- 사용자의 구현 아이디어와 에이전트의 초안은 목적·성공 조건·제약을 보존하는지 확인하기 전에는 최종 계획으로 확정하지 않는다.

## 계획 종류

| 종류 | 목적 | 확인 수준 |
|---|---|---|
| 조사 계획 | 확인할 것을 정리 | 미확인 전제를 조사 항목으로 남길 수 있음 |
| 설계 초안 | 방향과 구조 후보 비교 | 사실, 가정, 후보를 구분 |
| 구현 계획 | 실행 순서와 검증 기준 확정 | 방향을 바꿀 핵심 전제를 먼저 확인 |

구현 계획에 필요한 파일, 타입, API, 데이터 구조, UI·씬·프리팹, 테스트 구조를 확인하지 못했고 그 전제가 방향을 바꿀 수 있으면 조사 계획이나 설계 초안으로 낮춘다.

## 목표 상태와 범위

- 구현·리팩터링·동작 변경 계획은 요구가 처음부터 있었다면 자연스러운 구조를 목표 상태로 두고 현재 상태와의 차이를 본다. 필요에 따라 목표 상태, 확인된 현재 상태, 핵심 차이, 이번 범위, 남기는 차이를 구분한다.
- 구조 판단 자체를 반복해 정의하지 않고 실행자가 움직일 범위, 순서, 의존성, 검증 기준으로 연결한다. 목표가 요청 범위를 넘어도 목표를 현재 구조에 맞춰 낮추지 말고 이번 범위와 남기는 차이를 분리한다.
- 포함 범위와 의도적 제외 범위를 구분한다. 사용자의 최소 수정·제약 때문에 목표 상태와 달라지는 부분은 숨기지 않는다. 후속 정정이 생기면 단계뿐 아니라 범위와 완료 기준도 갱신한다.

## 작업 분해

- 각 단계는 실행자가 새 설계 결정을 하지 않아도 움직일 크기로 나누고, 가능하면 대상, 변경, 이유, 완료 기준, 필요한 검증을 포함한다.
- 신규 구조 작성, 연결, 상태 생명주기, 검증을 한 단계에 몰아넣지 않는다. API·데이터 흐름·알고리즘은 방향을 정할 정도로만 고정하고 확인되지 않은 private 세부 구현은 미리 정하지 않는다.
- 서로 다른 파일·기능을 다루고, 한 결과가 다른 작업의 설계를 바꾸지 않고, 같은 상태·파일을 동시에 수정하지 않고, 성공 조건이 독립적일 때만 병렬화한다. 공통 원인이나 구조 판단이 먼저면 병렬화하지 않으며 결과 통합 시 충돌과 중복 책임을 확인한다.
- 위험은 경고 목록이 아니라 선행 조사, 작업 순서, 검증 계획으로 연결하고 근거 없는 가능성은 항목으로 늘리지 않는다.

## 검증 계획

- 작업 성격에 맞는 허용된 경로(정적·형식 검사, 빌드·컴파일, 기존 테스트, 실제 실행·수동 확인, 시각 비교, 로그·콘솔 확인, 변경 차이 검토)를 포함한다.
- 새 테스트가 필요해 보여도 테스트 변경 권한이 없으면 구현 단계에 넣지 않고 `테스트 후보`로만 기록한다. 승인된 경우에만 실제 계약과 회귀 위험으로 검증 경계를 정한다.
- 수동 검증 절차가 핵심이면 [검증 가이드](references/verification-guide.md)를 적용한다.

## 문서 표현

- 구조는 작업 성격에 맞춰 선택하고 필요한 섹션만 쓴다: 배경·목적, 목표 상태, 확인된 현재 상태, 설계 방향, 범위/범위 외, 작업 순서, 검증 계획, 가정/확인 필요.
- 구조·비교·흐름을 시각적으로 표현해야 하면 [계획 문서 표현](references/document-format.md)을 적용한다.
- 요구가 크고 설계 분기점이 얽혀 상위 방향을 먼저 정해야 하거나 한 번에 확정하면 추측이 많이 섞일 때만 [점진적 계획 모드](references/progressive-mode.md)를 적용한다.

## 종료 기준

여러 단계 작업은 최초 요청과 후속 추가·정정·제외를 요구 목록으로 관리하고, 종료 전에 각 요구가 작업 단계와 검증 기준에 연결됐는지 확인한다. 빠진 요구는 보완하고 확인하지 못한 전제는 확정 사실처럼 쓰지 않는다.
