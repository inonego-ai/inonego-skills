# 정렬 모드

명시적으로 호출된 현재 요청에만 적용한다. 실제 적용 시 응답 첫 줄은 `정렬 모드 적용`으로 시작한다.
이후에는 별도 모드 설명이나 형식적인 체크리스트를 반복하지 않는다.
현재 요청의 권한과 범위를 유지한다. 검토 요청은 읽기 전용이며, 구현 요청에서는 허용된 범위만 수정한다.

## 목표 상태와 근본 원인

- 요구가 처음부터 존재했다면 어떤 구조가 자연스러웠을지, 현재 구현을 정답으로 가정하지 않고 도출한다.
- 요구사항·성공 조건과 사용자가 제시한 구현 아이디어를 구분한다.
- 실제 호출자·소비자, 책임 경계, 상태 소유권, 데이터 흐름, 의존성 및 생성·종료 수명을 확인한다.
- 목표와 현재 구현의 차이를 해소한다. 구조가 원인이면 인터페이스·상태 모델·호출 구조까지 바꾼다.
- 증상 차단용 조건문, 보정 플래그, 임시 우회나 반복적인 예외 처리를 최종 설계로 남기지 않는다.
- 같은 접근이 반복 실패하면 기존 가정과 실제 실행 경로를 다시 검토한다.

## 전환과 단순화

- 기본은 이전 구현과의 호환성 유지가 아니라 목표 구조로의 전환이다.
- 사용자가 명시적으로 요구하지 않은 구형 API, 호환 계층, 어댑터, 폴백·마이그레이션 분기를 만들거나 남기지 않는다.
- 새 구조가 대체한 경로·상태·호출부·내부 구현과 해당 레거시 테스트를 관련 범위에서 정리한다.
- 다만 현재 요구된 기능, 사용자 데이터 보존 의무와 명시적으로 유지할 계약까지 임의로 폐기하지 않는다.
- 불필요한 추상화, 도달 불가능한 방어 경로, 근거 없는 복구·재시도와 요청 밖 리팩터링을 만들지 않는다.
- 책임과 실제 계약이 명확한 가장 단순한 구조를 선택한다.

## 검증

- 새 테스트 작성은 기본 산출물이 아니다. 실제 계약과 회귀 위험이 확인된 경우에만 필요성을 판단한다.
- 기존 실험의 성공 조건, 코드, 로그와 검증 결과를 먼저 참고한다.
- 단순 일대일 대응이나 중복, 과도하게 분리된 테스트를 경계한다.
- 실제 제품 경로가 아닌 테스트 전용 구현만 검증하는 테스트는 충분한 증거로 보지 않는다.
- 무관한 예외나 잘못된 준비 상태로 통과하는 테스트를 확인한다.
- 변경된 계약에 직접 관련된 기존 테스트는 갱신하고, 사라진 계약의 테스트는 정리한다.
- 테스트 실행과 파일 변경 권한을 구분하며, 테스트 통과만으로 구조적 완료를 선언하지 않는다.

## Unity 조건부 규칙

유니티 C# 코드에서는 `dev-unity`와 `programmer`의 C# 컨벤션 문서를 적용한다.
XML summary, region의 책임별 구성과 명명·형식 누락을 확인하며 형식적 구성은 강제하지 않는다.

## 최종 감사

선택한 범위의 목표 상태와 실제 결과를 다시 비교한다.
책임·소유권·호출 관계, 초기화·상태 전이·콜백·실패·종료 경계와 대체된 레거시를 확인한다.
필요성이 없는 구조가 남거나 검증이 부족하면 완료라고 선언하지 않고 차이와 근거를 보고한다.
