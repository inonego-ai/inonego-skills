# 리팩토링

동작을 바꾸지 않고 내부 구조를 개선하는 단계.  
**한 번에 하나씩** 변환하고, 변환 직후마다 동작 보존을 확인한다.

> **기능 추가와 리팩토링을 동시에 하지 않는다.** 둘을 섞으면 회귀의 원인이 어느 쪽인지 판별할 수 없다.  
> 리팩토링 중 새 요구사항이 발견되면 별도 작업으로 기록하고 현재 리팩토링을 끝낸 뒤에 처리한다.

---

## 원칙: 사용자 검토는 상시 수행

리팩토링은 여러 결정 지점이 있고, 어떤 스멜을 고치고 어떤 기법을 적용할지에 따라 결과가 크게 달라진다. 각 단계의 결정을 확정하기 전에 사용자와 정렬한다.

- §1 범위 레벨(코드/아키텍처)이 갈릴 때 사용자에게 확인
- §3 우선순위 목록을 제시해 이번에 처리할 항목을 확정
- §4 변환 기법 선택에 트레이드오프가 있을 때 대안 제시
- 변환 중 예상치 못한 영향이 드러나면 즉시 사용자에게 알리고 진행 여부 확인

---

## 단계 체크리스트

순서대로 수행한다. 이전 단계의 출력이 없으면 다음 단계로 진행하지 않는다.

- [ ] **1.** 리팩토링 범위 결정 (코드 레벨 / 아키텍처 레벨)
- [ ] **2.** 대상 식별 (스멜 감지)
- [ ] **3.** 우선순위 결정
- [ ] **4.** 점진적 변환
- [ ] **5.** 동작 보존 검증 및 결과 보고

---

## 1. 리팩토링 범위 결정

**입력**: 탐색 결과 + 사용자 요청

리팩토링은 범위에 따라 기법이 다르다. 먼저 어느 레벨인지 확정한다.

| 레벨 | 대상 | 기법 범주 |
|------|------|----------|
| **코드 레벨** | 함수·클래스·파일 내부 | 추출·인라인·이름 변경·조건 단순화·중복 제거 |
| **아키텍처 레벨** | 모듈·레이어·의존성 구조 | 레이어 경계 복구·의존성 역전·컴포넌트 분리·경계 이동 |

불명확하면 사용자에게 확인한다. 코드 레벨 작업 중 아키텍처 문제가 드러나면 현재 작업을 마친 뒤 별도 작업으로 아키텍처 리팩토링을 진행한다 (동시 진행 금지).

---

## 2. 대상 식별 — 스멜 감지

**입력**: 1단계 범위

### 2-1. 코드 레벨 스멜

아래 증상은 절대 기준이 아니라 **신호**다. 상황에 따라 괜찮을 수 있으니 맥락을 함께 본다.

| 증상 | 내용 |
|------|------|
| 비대해짐 | 함수·클래스·파일이 한눈에 들어오지 않을 만큼 크다 |
| 긴 파라미터 | 함수가 받는 인자가 너무 많거나 연관성이 흩어져 있다 |
| 조건 분기 과잉 | 타입·플래그로 분기하는 긴 switch·if-else, 깊은 중첩 |
| 중복 | 같은 개념을 같은 방식으로 여러 곳에서 반복 |
| 데드 코드 | 쓰이지 않는 필드·파라미터·분기, 주석으로만 설명되는 코드 |
| 결합도 과다 | 다른 클래스 내부를 깊게 파고드는 호출, 과한 중개자 |
| 변경 전파 | 하나의 변경이 여러 클래스에 산발적으로 퍼진다 |
| 책임 혼재 | 한 단위가 여러 이유로 바뀐다 |

### 2-2. 아키텍처 레벨 스멜

| 증상 | 내용 |
|------|------|
| 레이어 경계 위반 | 안쪽 계층이 바깥쪽 계층에 의존 |
| I/O 누수 | 비즈니스 로직 안에서 DB·파일·네트워크를 직접 호출 |
| 순환 참조 | 모듈 간 상호 의존 |
| 계약 위반 | 인터페이스 뒤에 있어야 할 구현 세부가 외부에 노출 |
| 책임 비대 | 하나의 모듈이 여러 도메인 책임을 가짐 |
| 결합도 과다 | 한 컴포넌트 수정이 많은 곳에 파급된다 |

---

## 3. 우선순위 결정

**입력**: 스멜 목록

모든 스멜을 한 번에 고치지 않는다. 영향·위험·비용을 종합해 상대 순위를 매기고 가장 높은 것부터 처리한다.

- **영향** — 고쳤을 때의 개선 폭
- **위험** — 이 코드가 버그·변경 실패의 원인이 될 가능성
- **비용** — 고치는 데 드는 부담 (큰 비용은 순위를 낮춘다)

**MUST**: `asqu` 또는 `AskUserQuestion`으로 우선순위 목록을 사용자에게 제시하고 어떤 항목을 이번에 처리할지 확정한다. 임의로 범위를 넓히지 않는다.

---

## 4. 점진적 변환

**입력**: 3단계에서 확정한 대상

### 원칙

- **한 번에 하나씩** — 변환 단위를 작게 유지
- **각 변환 직후 동작 보존 검증** — 기존 테스트 실행, 실패 시 즉시 롤백
- **안전망 우선** — 기존 테스트가 빈약하면 먼저 얇은 특성 테스트(characterization test)부터 확보

### 코드 레벨 기법 예시

- 의미 단위로 함수를 잘라 이름 있는 함수로 분리
- 관련 파라미터를 객체로 묶어 전달
- 조건을 분해하고 가드 절로 빠르게 종료
- 타입·플래그 분기를 다형성으로 치환 (해당 시)
- 공통 **개념**만 공통 단위로 추출 (구조만 같은 중복은 분리 유지)
- 책임 혼재는 이유별로 단위를 분리

### 아키텍처 레벨 기법 예시

- 인터페이스 소유권을 안쪽으로 옮기고 바깥쪽이 구현을 제공
- I/O를 경계 모듈로 격리하고 안쪽 로직은 순수하게
- 순환 참조를 공통 의존 추출로 해소하고 방향 통일
- 도메인 경계 기준으로 비대한 단위 분해

---

## 5. 동작 보존 검증 및 결과 보고

**입력**: 4단계의 각 변환 직후

리팩토링의 정의는 "동작 보존". 매 변환마다 아래를 수행한다.

- 기존 테스트 스위트 실행 → 전부 통과해야 함
- 탐색 단계에서 식별한 주요 시나리오를 end-to-end로 재확인
- 실패가 나오면 **즉시 롤백**하고 원인을 분석한 뒤 다시 시도

> 테스트가 없어서 "동작 보존"을 확인할 수 없으면 리팩토링하지 않는다. 먼저 최소한의 특성 테스트를 확보한다.

회귀 범위를 넓게 돌려야 할 경우 [검증 워크플로우](validation.md)의 회귀 테스트 절차를 적용한다.

### 출력

```
리팩토링 범위:
- 레벨: 코드 / 아키텍처
- 대상 스멜: [항목]

처리 결과:
- [스멜] → [적용한 변환] → [동작 보존 확인 여부]

보류:
- [처리하지 않은 스멜] — [이유: 우선순위·비용·다음 작업]

검증:
- 회귀 테스트 결과
- 동작 변화 없음 확인
```
