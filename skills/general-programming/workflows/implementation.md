# 구현

설계 블루프린트를 실제 코드로 만드는 단계.  
작성 원칙을 지키고, AI 코드 특유 안티패턴을 피하며, 완료 선언 전까지 모든 함수가 **실제 구현**인지 확인한다.

> **이 단계 진입 전에 설계 블루프린트가 확정되어 있어야 한다.**  
> 즉흥 설계는 구현 중에 들어가지 않는다. 블루프린트를 다시 손봐야 하면 설계 단계로 돌아간다.

---

## 단계 체크리스트

순서대로 수행한다. 이전 단계의 출력이 없으면 다음 단계로 진행하지 않는다.

- [ ] **1.** 언어·프로젝트 컨벤션 로드
- [ ] **2.** 인터페이스 먼저
- [ ] **3.** 구현
- [ ] **4.** 완료 자가 검증

---

## 작성 원칙 (모든 단계 내내 적용)

작성하는 모든 코드는 아래 속성을 지킨다.

### 완성도
작성한 코드는 실제로 동작해야 한다. 자리만 차지하는 코드는 남기지 않는다.

- 빈 구현·더미 반환·미구현 예외를 남기지 않는다
- `TODO`·`sleep` 등으로 복잡한 로직을 회피하지 않는다

### 책임 분리

각 단위는 하나의 이유로만 변경된다.

- 함수·클래스·모듈은 하나의 책임만 가진다
- 같은 **개념**이 여러 곳에 있을 때만 한 곳으로 모은다 — 구조만 비슷하고 개념이 다르면 분리 유지
- 인터페이스는 사용하는 쪽 기준으로 정의

### 교체 가능성

구현을 교체할 수 있는 구조로 작성한다 (테스트·모킹 포함).

- 구체 타입이 아닌 인터페이스·추상에 의존
- 외부 의존성(DB·파일·API·시간·난수)은 경계 뒤에 격리
- 직접 생성 대신 주입받는다
- 전역 변수·공유 상태 금지 — 테스트 격리를 깬다
- 같은 입력이면 같은 출력이 나오는 순수한 단위를 선호

### 확장성

기존 코드를 수정하지 않고 확장할 수 있는 구조를 유지한다.

- 새 케이스마다 기존 코드를 열어 조건을 덧붙이는 구조 지양
- 서브클래스·구현체는 부모·인터페이스의 계약을 깨지 않는다

---

## 1. 언어·프로젝트 컨벤션 로드

언어·프레임워크별 코딩 컨벤션이 별도 스킬로 존재하면 이 시점에 로드한다.

- C# / Unity → `inonego-skills:csharp-conventions` 스킬
- 프로젝트 `CLAUDE.md` 규칙 — 프로젝트 루트 및 관련 하위 디렉토리

이 단계는 **건너뛰지 않는다**. 컨벤션을 모르고 작성한 코드는 이후 리뷰에서 통째로 다시 써야 할 수 있다.

---

## 2. 인터페이스 먼저

**입력**: 설계 블루프린트의 "인터페이스·계약" 섹션

- 공개 API 시그니처, 타입, 데이터 구조를 먼저 확정해 파일에 반영
- 내부 구현은 비워두되, **빈 스텁을 남긴 채 커밋하지 않는다** — 이 단계는 즉시 구현으로 연결
- 블루프린트의 컴포넌트 간 계약을 지킨다

> **인터페이스가 확정되지 않은 상태로 구현 진행 금지.**

---

## 3. 구현

**입력**: 2단계 인터페이스 + 설계 블루프린트 전체 (계약·실패 동작·허용 입력 범위 포함)

블루프린트의 계약을 그대로 코드로 옮긴다. 이 단계는 **판단이 아니라 번역**이다.

**전제 조건**: 블루프린트에 실패 동작과 허용 입력 범위가 정의되어 있어야 한다. 빠져 있으면 구현을 시작하지 말고 설계로 되돌아가 보완한다. 즉흥 결정은 구현 중에 들어가지 않는다.

### 원칙

- **한 번에 한 컴포넌트씩** — 여러 파일을 동시에 반쯤 구현하고 돌아다니지 않는다
- **블루프린트 계약 그대로 반영** — 임의 추가·삭제 금지. 실패 동작·허용 입력 범위도 명세 그대로
- **선제 추상화 금지** — 반복이 실제로 드러난 뒤에만 공통화
- **"혹시 쓸지도" 분기 금지** — 블루프린트에 있는 흐름만
- **예외 삼키기·가드 제거 금지** — 빈 catch, "이미 괜찮아 보여서" 검증 제거는 회귀 원인
- **현재 작성 중인 단위가 완결된 뒤 다음 단위로** 이동

### 새 실패 조건이 발견되면

구현 중 블루프린트가 예상하지 못한 실패 조건이 드러나면 **즉시 멈추고** 설계로 되돌아간다.  
구현 단계에서 임의로 정책을 만들지 않는다. 설계를 보완하고 돌아와 구현을 계속한다.

---

## 4. 완료 자가 검증

**"완료"를 선언하기 전** 반드시 수행한다. 하나라도 걸리면 완료 아님.

### 4-1. 정적 오류 확인

가장 먼저 한다. 컴파일·타입·린트가 깨진 상태에서는 나머지 검증이 의미 없다.

**검사 범위는 이번 작업과 관련된 부분으로 한정한다.** 이번 작업이 건드리지 않은 기존 오류·경고는 이번 변경의 책임이 아니므로 넘어간다 (사용자가 따로 요청하지 않는 한 건드리지 않는다).

- [ ] **빌드·컴파일 오류 없음** — 프로젝트 빌드 커맨드 또는 IDE 진단(`ide_diagnostics`) 확인
- [ ] **타입 오류 없음** — 타입 체커 통과
- [ ] **린터 경고 없음** — 프로젝트 린터·포매터 통과
- [ ] **파일 저장 직후 IDE 진단 재확인** — 저장 전 버전으로 체크된 오류가 남아 있을 수 있음

**패스 조건**: 다음은 통과로 본다.

- 이번 작업과 무관한 파일·영역의 기존 오류·경고
- 사용자가 명시적으로 허용한 오류·경고 (예: "이 경고는 알고 있으니 그대로 두라")
- 사용자 의도 안에서 발생하는 경고 (예: 의도된 deprecation, 임시 호환성 유지 등)

> 그 외 경고를 "별거 아니라서" 넘기지 않는다.  
> 억제(suppress)는 근거를 주석이나 설정에 남기되, 이 단계에서 임의 억제는 금지.

### 4-2. 의미 검증

- [ ] 모든 함수가 실제 구현인가 — 스텁·미구현 예외·더미 반환이 남아 있지 않다
- [ ] 블루프린트의 생성/수정 파일 목록이 모두 반영됐나
- [ ] 블루프린트의 공개 인터페이스가 그대로 지켜졌나
- [ ] 요구사항 MoSCoW의 **MUST**가 전부 구현됐나
- [ ] 작성 원칙에 명백히 위반되는 부분이 없나

통과하지 못한 항목은 수정 후 재검증한다. 이 체크리스트를 통과해야 검증(validation) 단계로 넘어갈 수 있다.

---

## 출력

구현 완료 후 다음을 제시한다.

```
구현 요약:
- 생성/수정 파일 목록 (경로만)
- 블루프린트 대비 변경된 점 (있다면 사유 명시)

자가 검증:
- 정적 오류: 빌드/타입/린터 통과 확인
- 스텁·미구현 없음 확인
- 요구사항 MUST 전부 구현 확인
- 그 외 체크리스트 통과 여부

다음 단계:
- 검증(validation) 워크플로우로 진입 — 단위 → 통합 → 인수 → 회귀 테스트
```
