# 요구사항 분석

요청을 구현 가능한 요구사항으로 변환하는 단계.  
요청의 표면 뒤에 있는 **실제 의도**를 파악하고 모호한 부분을 해소한다.  
**이 단계가 끝나기 전까지 파일 수정/명령 실행 금지.**

---

## 단계 체크리스트

순서대로 수행한다. **이전 단계의 출력이 없으면 다음 단계로 진행하지 않는다.**

- [ ] **1.** WHAT/WHY 의도 파악
- [ ] **2.** 모호성 해소
- [ ] **3.** MoSCoW 분류

---

## 1. WHAT/WHY 의도 파악

**출력**: WHAT 한 줄 + WHY 한 줄

| 분류 | 확인 내용 |
|------|---------|
| **WHAT** | 어떤 기능/변경이 필요한가 |
| **WHY** | 어떤 문제를 해결하려는가, 목적이 무엇인가 |

WHY를 모르면 방향이 틀려도 알 수 없다. 표면적 요청만 보고 구현하지 않는다.

> **WHY를 명시하지 않고 2단계로 진행 금지.**

---

## 2. 모호성 해소

**입력**: 1단계의 WHAT/WHY

**해석이 여럿일 때** 조용히 선택하지 않는다.

- 후보를 나열하고 트레이드오프를 제시한 뒤 추천안과 함께 사용자가 선택하게 한다.
- 가정이 있으면 명시적으로 밝히고 시작한다.

```
해석 A: [내용] → 장점: ... / 단점: ...
해석 B: [내용] → 장점: ... / 단점: ...
추천: A (이유: ...)
```

> **해석이 여럿인데 사용자 선택 없이 3단계로 진행 금지.**

---

## 3. MoSCoW 분류

**입력**: 1단계의 WHAT/WHY + 2단계의 확정된 해석

요구사항의 우선순위와 범위를 확정한다.

| 레벨 | 의미 |
|------|------|
| **MUST** | 구현 필수 — 수단 가리지 않음 / 필요시 탐색 및 검색 적극 활용 |
| **SHOULD** | 필수적, MUST보다 구현 비용 낮음 |
| **COULD** | 여건 허락 시 구현 |
| **WON'T** | 금지 항목 |

내용이 불명확하면 구현 시작 전에 반드시 확인한다.
