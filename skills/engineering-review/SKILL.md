# Engineering Review

검토 목적은 기존 코드를 승인하거나 오류 목록을 늘리는 것이 아니라, **목표 계약에 비추어 실제 구조·동작·실패 경로를 검증**하는 것이다. 검토, 검토 결과에 따른 수정, Git Stage 조작은 서로 다른 행위다.

## 적용과 책임 경계

- 코드·설계·공개 API·수명·상태 전이·통합·재검토 요청에 적용한다. Git staged diff나 단계별 검토는 [Stage 워크플로](references/git-stage-workflow.md)를 함께 읽는다.
- 상세 검토 관점과 증거 기준은 [검토 방법론](references/review-methodology.md)을 따른다.
- 계획 수립·Stage 분해는 `planning`, 구현 방식·언어별 코딩 규칙은 `programmer`, Unity 고유 검증은 `dev-unity` 및 프로젝트 지침의 책임이다. 이 스킬은 **검토·결함 판정·검토 결과의 수정 검증**을 담당한다.
- 현재 요청이 **검토**라면 읽기 전용이다. 발견 내용을 수정하지 말고 결과로 보고한다. **검토 결과를 수정하라는 요청**이 있을 때만 승인된 Finding을 실제 코드에 반영한다. Git Index 변경, Commit, Amend, Push는 각각 별도 권한이 필요하다.
- 과거 검토 결과, AI 완료 선언, 계획 문서를 구현 증거로 취급하지 않는다. 실제 저장소·워크트리·HEAD 및 코드와 대조한다.

## 검토 프로토콜

1. **완료 계약:** 최초 요구와 후속 정정, 포함·제외 범위, 성공 조건을 먼저 확인한다. 목표 구조를 현재 구현 방식에 종속시키지 않는다.
2. **계약과 책임 지도:** 공개 계약, 상태·수명 소유자, 데이터·호출 흐름, 실패 시 불변식을 정의하고 현재 구조와 대조한다.
3. **위험 기반 조사:** 구조·동작·실패 반례·API와 복잡성·검증 품질을 서로 다른 관점에서 조사한다. 중요한 결함은 실제 실행·상태 경로로 입증한다.
4. **Finding 판정:** 확정 결함 / 근거가 부족한 의심 / 설계 개선 후보 / 확인 불가를 구분한다. 위치, 위반 계약, 도달 경로, 실제 영향, 근본 원인 및 필요한 수정 경계를 연결한다.
5. **결과 보고:** 검토만 요청됐다면 여기서 종료한다. 수정안을 제시할 수 있으나 코드를 변경하거나 Git Stage를 조작하지 않는다.
6. **검토 결과 기반 수정(요청된 경우에만):** 확인된 원인을 수정할 때 **수정된 계약을 직접 사용하는 동일 라이브러리 내부 코드도 함께 변경**한다. 연결된 내부 호출·생성·등록·바인딩·상태·종료 경로를 동작 일관성에 맞게 갱신하며, staged/unstaged 위치만으로 필요한 수정 범위를 자르지 않는다. 관련 없는 사용자·다른 에이전트 변경은 보존한다. 명시하지 않은 외부 소비처는 수정하지 않는다.
7. **재검증:** 원래 결함과 수정으로 영향을 받는 내부 경로를 다시 검사하고, 새로운 상태·분기·호환성 계층 때문에 복잡성이 증가했는지 확인한다. 정적 검사, 컴파일, 기존 테스트, 실제 실행은 서로 다른 증거로 보고한다. 무의미한 동일 검토 반복은 하지 않는다.

검토의 발견을 이유로 자동 수정하지 않는다. 반대로 **수정 권한을 받은 뒤에는 현재 Finding의 원인만 고치고 직접 연결된 내부 코드를 낡은 계약으로 방치하지 않는다.** 필요한 수정이 사용자의 승인 범위를 실질적으로 넘으면 영향과 남는 불일치를 명시한다.

## Stage 검토의 핵심 기준

Stage는 *작업/검토 단위*이고, Git staged는 *Index에 실제로 올라간 변경*이다. 둘을 혼동하지 않는다. 자세한 절차는 [Stage 워크플로](references/git-stage-workflow.md)를 따른다.

- Stage 범위는 파일 개수가 아니라 **그 단계의 목표 계약과 내부 책임 경계**로 판단한다.
- **검토 중:** staged 변경을 출발점으로 내부 연결 누락까지 판단하고 Finding으로 보고한다. Unstaged의 관련 없는 부분이나 외부 소비처를 검토 범위에 자동 편입하지 않는다.
- **검토 결과를 수정할 때:** 승인된 수정의 직접 내부 의존 경로를 함께 수정한다. 해당 코드가 unstaged여도 제외하지 않는다. 그렇다고 자동으로 모두 Git Stage하지 않는다.
- **Stage 승인:** 해당 단계의 목표 계약 및 단계에 속한 내부 연결이 정합적이면 가능하다. 외부 소비처의 구 API 사용과 그로 인한 전체 프로젝트 컴파일 실패는 Stage 결함이 아니다. 후속 내부 Stage가 맡기로 한 독립 작업은 명시적인 의존성으로 기록한다.
- **최종 통합 승인:** 모든 Stage를 결합한 **대상 라이브러리 내부**의 계약·연결·컴파일·필요한 회귀가 충족되어야 한다. 외부 소비처의 전환이나 빌드 성공은 별도 요청 없이는 완료 기준에 넣지 않는다.
- 실제 실패를 성공이라고 보고하지 않는다. 내부/외부 오류 귀속을 입증하지 못하면 Stage 승인 근거도 미확인으로 남긴다.

## 보고와 종료 기준

규모에 맞게 간결하게 작성하되 **검토 대상과 제외 범위, 목표 계약, 발견 사항과 근거, 실제 검증 수준, 미확인 영역, 판정**을 구분한다. Stage 모드에서는 Stage별 상태와 전체 라이브러리 통합 판정을 별도 표시한다.

- `통과`: 정의된 범위와 검증 수준에서 필수 계약을 만족.
- `수정 필요`: 도달 가능한 결함 또는 필수 내부 연결 누락이 확인됨.
- `확인 불가/조건부`: 중요한 근거가 부족하거나 별도 Stage의 의존성이 남음.

컴파일·테스트 통과만으로 아키텍처·기능의 무결함을 주장하지 않는다. 검토 완료는 **확인한 범위의 검토가 종료됐다**는 뜻이지 결함이 전혀 없다는 보증이 아니다.
