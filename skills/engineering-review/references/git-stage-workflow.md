# Git Stage 기반 검토와 수정

Stage의 **목표 계약과 내부 책임 경계**를 우선한다. Git staged 파일은 검토의 출발점이지 라이브러리 내부 의존성의 경계를 정의하지 않는다. 이 문서는 검토·수정·Index 조작을 별도로 다룬다.

## 1. 구분할 단위

- **논리적 Stage:** 책임·기능·선행 계약으로 나눈 작업 단위. Stage 수와 파일 수를 고정하지 않는다.
- **Git staged 변경:** 현재 Index에 올라간 diff. 논리적 Stage와 일치하는지 확인해야 한다.
- **현재 Stage의 내부 연결:** 그 Stage가 변경하는 타입·API·상태 계약을 **같은 라이브러리 안에서 직접 사용하거나 구성하는 코드**. Staged/unstaged 여부와 무관하다.
- **독립된 후속 Stage:** 현재 Stage의 완결된 계약을 소비하지만, 별도 목표·책임·검증으로 분리하기로 계획된 내부 작업.
- **외부 소비처:** 해당 라이브러리 밖에서 이를 사용하는 게임·애플리케이션·별도 소비 프로젝트. 별도 요청 없으면 검토·수정·호환성 보존 대상에서 제외한다.

## 2. Stage 계획과 변경 출처 확인

Stage별로 **목표 계약 / 포함 변경 / 직접 내부 연결 / 후속 단계 의존성 / 검증 / 승인 조건**을 정한다. 하나의 변경 목표를 필요 이상으로 쪼개 직접 연결된 내부 경로를 다른 Stage로 떠넘기지 않는다.

실제 Git 작업 트리를 확인한다.

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short --branch
git diff --name-status
git diff --cached --name-status
git ls-files --others --exclude-standard
```

사용자·다른 에이전트의 staged/unstaged 변경, 이번 작업의 변경을 구별한다. HEAD·Index가 외부에서 바뀌면 조작 전 상태를 다시 확인한다.

## 3. 검토만 요청된 경우

1. `git diff --cached`를 우선 읽어 Stage의 실제 변경을 확정하고 목표 계약과 비교한다.
2. 해당 계약의 **내부 호출·생성·등록·바인딩·상태·종료 경로**를 추적한다. 직접 연결된 unstaged 내부 코드의 누락은 Finding으로 적되 수정하거나 자동으로 Index에 추가하지 않는다. 관련 없는 unstaged 코드는 검토 대상으로 확장하지 않는다.
3. [검토 방법론](review-methodology.md)으로 구조·동작·실패 반례·복잡성을 조사한다.
4. 내부 연결 불일치가 현재 Stage의 필수 계약을 깨는지, 실제로 독립된 후속 Stage에 속하는지 판단한다. 단순히 unstaged이므로 후속 단계라고 판정하지 않는다.
5. 허용된 검증을 수행하고 실패 원인을 **현재 Stage 내부 / 독립된 후속 내부 Stage / 외부 소비처 / 미확인**으로 분리한다.
6. Stage의 승인·보류와 전체 라이브러리 통합 상태를 따로 보고한다. **읽기 전용 검토는 Git 상태도 변경하지 않는다.**

### 승인 기준

| 발견한 상태 | Stage 판정 |
| --- | --- |
| 현재 Stage 계약과 직접 연결된 내부 구현이 모두 정합적 | Stage 승인 가능 |
| 현재 Stage의 코드나 직접 연결된 unstaged 내부 호출·이벤트·소유권이 옛 계약에 머무름 | 승인 보류, Finding에 수정 대상 경로 명시 |
| 독립적인 후속 내부 Stage의 변경이 미완료이지만 현재 Stage의 계약은 충족 | 후속 의존성 명시 후 Stage 승인 가능 |
| 외부 소비처가 구 API를 호출하여 전체 프로젝트 컴파일 실패 | Stage 결함 아님; 호환성 코드를 요구하지 않음 |
| 실패 원인을 내부/외부 또는 현재/후속 Stage로 귀속할 수 없음 | 판정 보류/확인 불가. 성공으로 보고하지 않음 |

**Stage 승인에 외부 소비처까지 포함하는 전체 빌드 성공을 요구하지 않는다.** 그러나 직접 연결된 내부 코드의 불일치를 컴파일 실패 허용 규칙으로 덮지 않는다. 실행되지 못한 검증은 검증 공백으로 기록한다.

## 4. 검토 결과를 수정하라는 요청이 있는 경우

검토 자체에 수정 권한을 소급 적용하지 않는다. 수정 요청을 받으면:

1. 확인된 Finding의 원인·대상 계약·내부 의존 경로를 확정한다.
2. 원인 코드를 바꾸면서 **그 변경을 직접 참조하거나 연결하는 라이브러리 내부 코드도 같은 수정 작업에서 함께 고친다.** 내부 연결이 unstaged 파일에 있어도 고쳐야 한다면 제외하지 않는다. 다만 해당 파일의 관련 없는 변경은 건드리지 않는다.
3. 별개로 계획된 후속 내부 Stage에 속하는 변경은 그 경계를 보존하되, 현재 Stage의 필수 연결까지 후속으로 미루지는 않는다.
4. 외부 소비처는 수정하지 않고, 기존 소비처 때문에 불필요한 호환 API·레거시 분기를 만들지 않는다.
5. 변경 후 관련 내부 경로와 반례를 재검증하고, 현재 diff와 검토 결과를 다시 대조한다.

**코드 수정 권한이 곧 Git Index 변경 권한은 아니다.** 자동 `git add` 없이 working tree의 정합성을 먼저 확보한다. 실제 Stage 조작을 요청받았을 때만 계획한 부분을 Index에 반영한다.

## 5. Git Index·Commit/Amend 보호

- Stage 조작 권한이 있을 때도 `git diff --cached`와 `git diff`를 비교해 포함·제외할 변경 구간을 확인한다.
- 해당 작업 변경만 파일/변경 구간 단위로 Stage한다. `git add -A`나 기존 staged 변경의 일괄 해제는 금지한다.
- 다른 에이전트의 동시 쓰기와 같은 파일·Index 조작을 겹치지 않게 관리한다.
- Commit, Amend, Push는 사용자에게 명시적으로 승인된 경우에만 실행한다. Amend 전에 대상 HEAD 및 이미 공유된 커밋인지 확인한다.

## 6. 최종 라이브러리 통합 검토

모든 Stage가 승인된 다음에도 **Stage 간 내부 연결**과 중복 책임, 상태 소유권, 공개 계약, 레거시 잔재 및 실패 경로를 별도로 점검한다. 대상 라이브러리의 컴파일과 필요한 회귀 검증을 수행할 수 없다면 최종 판정을 보류하거나 검증 공백을 명시한다.

외부 소비처의 전환·빌드 성공은 별도 요청이 없다면 최종 완료 조건에서 제외한다. Stage 검토 통과를 전체 라이브러리 검토 통과로 대체하지 않는다.

## 보고 예

```text
Stage S2 — Activation/Cost
- 검토 계약: Activation 실패 원자성과 Cost 상태 전이
- 현재 Stage 내부 연결: AbilityActivation → Cost/State Binding
- 발견: 내부 Binding이 구 계약을 호출함 (unstaged 파일)
- 검토 판정: 승인 보류. 수정 허가 없이 파일 변경 없음
- 수정 요청 시 범위: 원인 코드 + 내부 Binding 연결을 같은 작업에서 수정
- 외부 소비처: 검토·수정 범위 밖
- 검증: 내부 경로 정적 확인 완료 / 전체 빌드 미통과(외부 구 API 호출)
- 전체 라이브러리: 최종 통합 미검증
```
