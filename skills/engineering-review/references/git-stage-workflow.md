# Git Stage 기반 검토와 수정

Stage의 **목표 계약과 내부 책임 경계**를 우선한다. Git staged 파일은 검토의 출발점일 뿐 라이브러리 내부 의존성의 경계가 아니다.

## 1. 구분할 단위

- **논리적 Stage:** 책임·기능·선행 계약으로 나눈 작업 단위(수와 파일 수는 고정하지 않음).
- **Git staged 변경:** 현재 Index의 diff. 논리적 Stage와 일치하는지 확인한다.
- **현재 Stage의 내부 연결:** 그 Stage가 바꾸는 타입·API·상태 계약을 같은 라이브러리 안에서 직접 사용·구성하는 코드(staged 여부 무관).
- **독립된 후속 Stage:** 현재 Stage의 완결된 계약을 소비하지만 별도 목표·책임·검증으로 분리하기로 계획된 내부 작업.
- **외부 소비처:** 라이브러리 밖의 게임·앱·소비 프로젝트. 별도 요청이 없으면 검토·수정·호환성 보존 대상이 아니다.

## 2. Stage 계획과 변경 출처

Stage별로 목표 계약 / 포함 변경 / 직접 내부 연결 / 후속 의존성 / 검증 / 승인 조건을 정한다. 직접 연결된 내부 경로를 다른 Stage로 떠넘기려고 목표를 필요 이상 쪼개지 않는다.

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short --branch
git diff --name-status
git diff --cached --name-status
git ls-files --others --exclude-standard
```

사용자·다른 에이전트의 변경과 이번 작업의 변경을 구별하고, HEAD·Index가 외부에서 바뀌었으면 조작 전에 다시 확인한다.

## 3. 검토만 요청된 경우

1. `git diff --cached`로 Stage의 실제 변경을 확정하고 목표 계약과 비교한다.
2. 계약의 내부 호출·생성·등록·바인딩·상태·종료 경로를 추적한다. 직접 연결된 unstaged 내부 코드의 누락은 Finding으로 적되 수정하거나 Index에 추가하지 않는다. 무관한 unstaged 코드는 범위에 넣지 않는다.
3. [검토 방법론](review-methodology.md)으로 구조·동작·실패 반례·복잡성을 조사한다.
4. 내부 연결 불일치가 현재 Stage의 필수 계약을 깨는지, 독립된 후속 Stage에 속하는지 판단한다. unstaged라는 이유만으로 후속 단계로 보지 않는다.
5. 허용된 검증을 수행하고 실패 원인을 현재 Stage 내부 / 독립된 후속 내부 Stage / 외부 소비처 / 미확인으로 분리한다.
6. Stage 승인·보류와 전체 라이브러리 통합 상태를 따로 보고한다. 읽기 전용 검토는 Git 상태도 바꾸지 않는다.

| 발견한 상태 | Stage 판정 |
| --- | --- |
| 현재 계약과 직접 연결된 내부 구현이 모두 정합적 | 승인 가능 |
| 현재 Stage 코드나 직접 연결된 unstaged 내부 호출·이벤트·소유권이 옛 계약에 머묾 | 승인 보류, 수정 대상 경로 명시 |
| 독립 후속 내부 Stage가 미완료지만 현재 계약은 충족 | 후속 의존성 명시 후 승인 가능 |
| 외부 소비처의 구 API 호출로 전체 컴파일 실패 | Stage 결함 아님, 호환 코드 요구 안 함 |
| 실패 원인을 내부/외부·현재/후속으로 귀속 못 함 | 판정 보류/확인 불가, 성공으로 보고 안 함 |

Stage 승인에 외부 소비처까지 포함한 전체 빌드 성공을 요구하지 않는다. 그러나 직접 연결된 내부 불일치를 컴파일 실패 허용 규칙으로 덮지 않으며, 실행하지 못한 검증은 검증 공백으로 기록한다.

## 4. 검토 결과를 수정하라는 요청이 있는 경우

수정 권한을 검토에 소급 적용하지 않는다. 수정 요청을 받으면 다음을 따른다.

1. Finding의 원인·대상 계약·내부 의존 경로를 확정한다.
2. 원인 코드와 함께 그 변경을 직접 참조·연결하는 라이브러리 내부 코드를 같은 작업에서 고친다. unstaged 파일이어도 제외하지 않되 해당 파일의 무관한 변경은 건드리지 않는다.
3. 별개로 계획된 후속 내부 Stage의 경계는 보존하되 현재 Stage의 필수 연결을 후속으로 미루지 않는다.
4. 외부 소비처는 수정하지 않고, 소비처 때문에 호환 API·레거시 분기를 만들지 않는다.
5. 관련 내부 경로와 반례를 재검증하고 현재 diff와 검토 결과를 다시 대조한다.

코드 수정 권한은 Git Index 변경 권한이 아니다. 자동 `git add` 없이 working tree 정합성을 먼저 확보하고, 실제 Stage 조작을 요청받았을 때만 계획한 부분을 Index에 반영한다.

## 5. Git Index·Commit/Amend 보호

- Stage 조작 시 `git diff --cached`와 `git diff`를 비교해 포함·제외할 구간을 확인하고, 이번 작업 변경만 파일/구간 단위로 Stage한다. `git add -A`와 기존 staged 변경의 일괄 해제는 금지한다.
- 다른 에이전트의 동시 쓰기와 같은 파일·Index 조작이 겹치지 않게 한다.
- Commit, Amend, Push는 명시적으로 승인된 경우에만 실행한다. Amend 전에 대상 HEAD와 이미 공유된 커밋인지 확인한다.

## 6. 최종 라이브러리 통합 검토

모든 Stage 승인 뒤에도 Stage 간 내부 연결, 중복 책임, 상태 소유권, 공개 계약, 레거시 잔재, 실패 경로를 따로 점검한다. 대상 라이브러리의 컴파일과 필요한 회귀 검증을 못 했으면 최종 판정을 보류하거나 검증 공백을 명시한다. 외부 소비처 전환·빌드 성공은 별도 요청이 없으면 완료 조건이 아니며, Stage 통과를 전체 통과로 대체하지 않는다.

## 보고 예

```text
Stage S2 — Activation/Cost
- 검토 계약: Activation 실패 원자성과 Cost 상태 전이
- 현재 Stage 내부 연결: AbilityActivation → Cost/State Binding
- 발견: 내부 Binding이 구 계약을 호출함 (unstaged 파일)
- 검토 판정: 승인 보류. 수정 허가 없이 파일 변경 없음
- 수정 요청 시 범위: 원인 코드 + 내부 Binding 연결을 같은 작업에서 수정
- 외부 소비처: 검토·수정 범위 밖
- 검증: 내부 경로 정적 확인 완료 / 전체 빌드 미통과(외부 구 API 호출)
- 전체 라이브러리: 최종 통합 미검증
```
