# 목표 계약 기반 검토 방법론

이 문서는 **검토 단계의 결함 탐색과 증거 판정**을 상세화한다. 검토만 요청됐다면 이후의 수정 절차를 실행하지 않는다.

## 1. 목표 상태와 실제 책임

요구가 처음부터 있었다면 자연스러운 책임·상태·공개 API가 무엇이었을지 정의하되, 기존 구현에 없는 기능을 임의로 요구하지 않는다. 실제 코드에서 선언 → 생성 → 등록 → 사용 → 종료의 경로를 따라간다.

| 관점 | 핵심 질문 |
| --- | --- |
| 계약과 계층 | 공개 API가 약속한 동작과 실제 구현이 일치하는가? 정책과 인프라가 혼재하는가? |
| 소유권 | 상태와 자원을 생성·변경·해제할 최종 책임자가 유일하고 일관되는가? |
| 상태 전이 | 성공·실패·취소·복구 후 관찰 가능한 상태가 유효한가? |
| 조합·통합 | 독립 기능을 조합했을 때 모듈 간 책임·이벤트·데이터 흐름이 유지되는가? |
| 복잡성 | 중복 상태, 레거시, 임시 호환 API, 과잉 추상화·방어가 필요한 계약에 비례하는가? |
| 테스트 | 검사기·테스트가 실제 계약과 재현 가능한 실패를 검출하는가? |

검토 범위를 실제 변경·요구와 관련된 책임 경계로 제한한다. 추상화가 다르다는 사실만으로 설계 결함을 주장하지 않는다.

## 2. 반례 중심 결함 탐색

주요 작업의 **입력 → 선행 조건 → 상태 변경 → 외부 콜백/부작용 → 확정/종료**를 실제 코드로 추적한다. 아래에서 도달 가능한 위험만 선택한다.

| 위험 | 반례 |
| --- | --- |
| 경계값 | 0, 최대·최소값, 빈 집합, 중복 ID, 큰 시간 Delta |
| 재진입 | 이벤트에서 같은 객체 재호출·Dispose·등록 변경 |
| 순서 | Cancel 직전 완료, 종료 중 새로운 시작, 역순 알림 |
| 부분 실패 | 자원 일부 획득 후 예외, Rollback 중 실패 |
| 경로 차이 | 관찰자 유무, 최적화 경로, 큰 Tick과 작은 Tick의 결과 차이 |
| 공유 | 복수 소유자·중복 이벤트·객체 재사용·복제 시 상태 혼선 |
| 지속성 | Save/Load·복원 뒤 바인딩 및 일시 상태 재구성 |
| 통합 | 개별 모듈은 통과하지만 함께 호출할 때 불변식 위반 |

반례마다 **전제 조건, 도달 경로, 깨지는 불변식, 결과**를 확인한다. 가상 가능성은 확정 결함으로 표시하지 않는다.

### 시스템별 적용 예

- **Unity UI:** Window/Screen/Modal/Focus의 소유권, UGUI·UITK 구현 간 계약 차이, 종료·재진입, Hierarchy 이동, 런타임/시각 검증의 공백.
- **Ability:** State/Activation/Cost/Execution의 책임, Charge/Cooldown 전이, 중첩 실행·상태 복구, Persistence, 복제·소유권, 서로 다른 게임 메커니즘의 조합 가능성.
- 예시 게임이나 UI 소비 코드는 범용 계약의 설계 반례로 사용할 수 있으나, **Stage 검토에서 외부 소비처를 수정·호환성 유지 대상으로 삼지 않는다.**

## 3. Finding의 증거

결함을 단순히 '문제'라고 나열하지 않는다.

- **확정 결함:** 파일/행, 재현 가능한 입력·실행 경로, 위반 계약, 증명 가능한 영향.
- **의심:** 아직 입증되지 않은 전제와 확인 방법.
- **설계 개선 후보:** 구조적 비용과 개선 이익. 기능 결함과 구분.
- **확인 불가:** 환경·권한·실행 공백. 수행하지 않은 검증을 통과했다고 쓰지 않음.

오류의 근본 원인과 수정할 책임 경계를 지정한다. 불필요한 대규모 재설계나 검토 관점의 취향을 결함으로 포장하지 않는다.

## 4. 검토 결과에 따른 수정의 재검증

**사용자가 수정을 요청한 경우에만** 적용한다.

1. Finding의 근본 원인과 수정해야 할 계약을 다시 확인한다.
2. 수정 사항에 **직접 의존하는 같은 라이브러리의 내부 호출·생성·등록·이벤트·상태·수명 경로**를 찾아 실제 변경과 함께 정합하게 수정한다. 어느 쪽이 staged인지로 범위를 자르지 않는다.
3. 관련 없는 파일이나 사용자·다른 에이전트의 변경은 보존한다. 외부 소비처는 요청되지 않았다면 수정·레거시 호환 대상이 아니다.
4. 새 플래그·복구 경로·추상화가 필요 최소한인지 확인한다. 실패를 막기 위한 새 버그 가능성도 검토한다.
5. 원래 결함의 재현 경로와 해당 내부 경계의 인접 회귀를 검증하고, 수정으로 새로 깨지는 계약이 없는지 다른 관점에서 재감사한다.

테스트 작성은 자동 의무가 아니다. 기존 테스트의 목적은 보존하고, 필요한 경우 승인된 범위 내에서만 갱신한다.

## 5. 검증 수준과 종료

정적 코드 감사 / 컨벤션 검사 / 컴파일 / 기존 테스트 / 런타임 / Unity 시각 확인은 **서로 다른 근거**다. 실행하지 않았거나 다른 영역의 오류로 수행할 수 없었던 검증을 명시한다.

완료 시 최초 요구와 후속 정정, Finding의 조치 상태, 미검증 경계, 관련 내부 호출 경로의 정합성을 확인한다. 같은 검사를 끝없이 반복하지 말고 새로운 가정이나 결함 신호가 있을 때 필요한 관점으로 검토를 확장한다.
