# 목표 상태 기반 구현

요구가 처음부터 시스템에 포함되어 있었다면 자연스러운 목표 상태가 무엇인지 정하고, 현재 상태와의 차이를 기준으로 구현 범위를 선택한다.
평범한 국소 수정에 형식적인 구조 분석을 강제하지 않는다.

## 적용 조건

다음 중 하나가 실제로 성립할 때 적용한다.

- 사용자가 `target state`, `땜빵 금지`, `최종 구조`, `전체 구조`를 명시한다.
- 책임, 상태 소유권, 데이터 흐름이나 실패 경계를 재구성해야 한다.
- 현재 구조에 요구를 넣으면 특별 분기·보정 상태·복구 코드가 계속 늘어난다.
- 같은 문제를 같은 접근으로 두 번 이상 수정했지만 해결되지 않았다.
- 기존 확장 지점이 요구를 자연스럽게 표현하지 못하고 구조적 판단이 필요하다.

단순한 값 변경, 명백한 국소 결함, 기존 책임 안의 작은 확장은 `programmer`의 일반 판단으로 충분하면 이 스킬을 추가하지 않는다.

## 판단 산출물

구조 판단이 핵심이면 구현 전에 최소한 다음을 구분한다.

- 목적과 성공 조건
- 목표 상태
- 확인된 현재 상태
- 핵심 차이
- 이번 범위와 남기는 차이
- 검증 경계

필요한 경우 정렬 상태를 `정렬됨 / 부분 정렬 / 어긋남`으로 설명할 수 있지만, 분류 자체가 목적은 아니다.

## 판단 절차

1. 사용자 입력에서 목적, 성공 조건, 제약과 구현 아이디어를 분리한다.
2. 현재 구조와 독립적으로 자연스러운 목표 상태를 도출한다.
3. 실제 구현, 호출 흐름, 상태 소유권, 데이터 흐름과 실패 경계를 확인한다.
4. 목표 상태와 현재 상태의 핵심 차이를 식별한다.
5. 이번 요청에서 해소할 차이와 남길 차이를 정한다.
6. 선택한 범위 안에서 구현하고 책임 경계에 맞춰 검증한다.

사용자 아이디어가 하나의 해결 후보일 뿐이면 그대로 목표 상태로 부르지 않는다.
결과를 실질적으로 바꾸는 제약이 불명확하고 현재 자료로 해결할 수 없을 때만 사용자에게 확인한다. 비차단성 세부사항은 근거 있는 해석으로 진행한다.

## 구현 범위

- `전체 목표`: 이번 작업에서 목표 상태와의 차이를 모두 해소한다.
- `범위 한정 목표`: 목표 상태는 유지하되 현재 요청과 직접 관련된 차이를 해소한다.
- `제약 기반`: 명시적 제약 때문에 목표 상태의 일부를 이번 범위에서 구현하지 않는다.
- `최소 수정`: 사용자가 빠른 최소 수정 자체를 명시적으로 요구한 경우에만 증상 차단을 우선한다.

구조가 어긋났다는 이유만으로 전면 개편하지 않는다. 목표 상태와 요청 범위의 차이를 분리하고 이번 작업에 필요한 변경만 선택한다.
현재 사용처가 없다는 이유만으로 이미 정당한 책임과 계약을 가진 확장 지점을 제거하지 않고, 미래 가능성만으로 새 계약이나 상태 모델을 선제 추가하지도 않는다.
새 계약이 실제로 필요하면 사용 주체, 책임 소유자, 시작·종료 조건과 실패 전달 방식을 확인한다.

## 구조 판단

구조 변경 방식은 미리 정하지 않는다. 확인한 책임과 계약에 따라 유지, 분리, 통합, 이동, 인터페이스 변경, 상태 모델 변경이나 의존 방향 변경을 선택한다.

- 변경 이유, 생명주기, 데이터 소유권과 검증 단위가 갈라지면 분리를 검토한다.
- 항상 함께 변하고 같은 상태를 공유하면 통합을 검토한다.
- 책임이 다른 계층이나 모듈에 더 자연스러우면 이동을 검토한다.
- 호출자가 알아야 할 계약이 달라지면 인터페이스 변경을 검토한다.
- 중복 상태, 파생 상태와 호출 순서 의존이 문제를 만들면 상태 모델 변경을 검토한다.
- 구현 세부사항이 상위 정책을 끌고 가면 의존 방향을 다시 본다.

검증은 계약의 진입점과 통제 밖에서 상태가 바뀌는 경계에 둔다.
정상 흐름에서 이미 보장된 내부 불변식을 반복 검증하거나 도달 불가능한 상태를 가정해 복구 경로를 추가하지 않는다.
오류 처리, 실패 정리, 복구나 재시도가 구조 판단의 핵심이면 [실패 경계와 정리](references/failure-boundaries.md)를 적용한다.

## 과잉 구현 감사

추가하려는 구조, 분기, 오류 처리, 복구 경로마다 다음을 확인한다.

1. 지원하는 진입점에서 실제로 도달하는 경로가 있는가.
2. 보호할 계약, 불변식, 소유권이나 외부 관찰 동작이 구체적인가.
3. 기존 책임 경계와 처리 경로로 해결할 수 없는가.

근거가 없으면 추가하지 않는다. `혹시`, `나중에`, 가상의 커스텀 구현만으로 새 공개 계약, 상태 모델, 자동 복구나 재시도를 만들지 않는다.
한 위치의 요구를 이름이나 형태가 비슷한 모든 시스템에 기계적으로 확장하지 않고 목적·소유권·실패 경계가 같은 범위에만 적용한다.
기존 구조가 이미 목표 계약을 표현한다면 새 추상화보다 이름, 책임, 호출·해제 순서를 정돈하는 쪽을 우선한다.

## 반복 실패

같은 위치나 같은 접근으로 두 번 이상 수정했는데 문제가 해결되지 않으면 세 번째 수정 전에 문제 공간을 넓힌다.

- 지금까지 시도한 수정과 설명하지 못한 점
- 틀렸을 수 있는 최초 가정
- 새로 확인할 호출 흐름, 데이터 흐름, 상태 소유권과 외부 의존
- 기존 방어 분기가 대응하는 실제 계약과 재현 경로
- 다음 접근이 이전 시도와 다른 이유

증상 위치에 조건·예외·보정 플래그를 계속 쌓지 않는다.

## 완료 기준

완료라고 말하려면 선택한 범위의 실제 변경과 그 수준에 맞는 검증이 있어야 한다.
최종 검토에서 다음을 확인한다.

- 목표 상태와 현재 상태를 섞지 않았는가
- 사용자 아이디어를 목표 상태로 이름만 바꾸지 않았는가
- 남긴 차이와 이유가 명확한가
- 추가한 구조와 분기마다 실제 경로와 보호할 계약이 있는가
- 검증이 실제 책임 경계와 사용자 권한에 맞는가
- 반복 실패 상황이면 문제 공간을 넓혔는가
