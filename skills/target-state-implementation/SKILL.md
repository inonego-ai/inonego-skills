# Target-State Implementation

## 역할

요구가 처음부터 시스템에 포함되어 있었다면 자연스러운 목표 상태가 무엇인지 도출하고, 현재 상태와의 차이를 기준으로 이번 작업의 구현 범위와 완료 조건을 정한다.

`Target State`는 사용자 아이디어, 에이전트 계획, 현재 구조, 최소 수정안과 다르다.
이 스킬을 적용했다면 목표 상태, 현재 상태, 차이, 이번 범위가 구분되어야 한다.

## 필수 판정 산출물

명시적으로 `target state`, `땜빵 금지`, `최종 단계 최적 구현`, `전체 구조 보고`가 언급되었거나 구조 판단이 핵심이면, 구현 전에 아래 판정이 응답이나 작업 메모에 드러나야 한다.

```markdown
## Target State 판정

- 목적:
- 성공 조건:
- 제약:
- 아이디어/선호:
- 오해/불확실성:
- 목표 상태:
- 현재 상태:
- 정렬 상태: Aligned / Partially Aligned / Misaligned
- 차이:
- 이번 범위:
- 남기는 차이:
- 검증:
```

위 항목을 구분하지 못했으면 target state로 판단한 것이 아니다.
현재 위치에 가능한 최소 수정, 사용자가 제시한 구현 아이디어, 에이전트가 먼저 떠올린 계획을 목표 상태로 부르지 않는다.

## 판단 절차

아래 순서를 건너뛰지 않는다.

1. 사용자 입력을 목적, 성공 조건, 제약, 선호, 아이디어, 오해/불확실성으로 분리한다.
2. 목적, 성공 조건, 제약을 보존한 목표 상태를 현재 구조와 독립적으로 도출한다.
3. 현재 구현, 호출 흐름, 상태 소유권, 데이터 흐름, 검증 구조와 실패 경계를 확인한다.
4. 현재 상태가 목표 상태와 얼마나 맞는지 판정한다.
5. 목표 상태와 현재 상태의 차이를 식별한다.
6. 이번 작업에서 해소할 차이와 남겨둘 차이를 정한다.
7. 선택한 범위 안에서 구현하고 검증한다.

목적, 성공 조건, 제약이 불명확하거나 사용자의 아이디어가 목표 상태와 충돌하면 구현 전에 확인한다.
검증은 계약의 진입점과 통제 밖에서 상태가 바뀔 수 있는 경계에 둔다.
정상 흐름에서 이미 보장된 내부 불변식을 반복 검증하거나 계약을 위반한 구현의 상태까지 추측해 복구하지 않는다.

## 정렬 상태

- `Aligned`: 현재 구조가 목표 상태에 가깝다. 기존 확장 지점에 구현해도 목표 상태를 해치지 않는다.
- `Partially Aligned`: 큰 방향은 맞지만 일부 책임, 인터페이스, 데이터 흐름, 상태 소유권 조정이 필요하다.
- `Misaligned`: 현재 구조가 요구를 억지로 끼우게 만든다. 경계, 책임, 데이터 흐름, 상태 모델 재구성을 검토한다.

정렬 상태는 구현 범위가 아니다.
`Misaligned`라고 해서 항상 전면 개편하는 것도 아니고, `Aligned`라고 해서 검증 없이 구현하는 것도 아니다.

## 구현 범위

구현 범위는 목표 상태와 현재 상태의 차이를 이번 작업에서 어디까지 해소할지 정하는 선택이다.

- `Full Target`: 이번 작업에서 목표 상태와 현재 상태의 차이를 모두 해소한다.
- `Scoped Target`: 목표 상태는 유지하되, 현재 요청과 직접 관련된 차이만 해소한다.
- `Constraint-Based`: 사용자가 명시한 제약 때문에 목표 상태와 다른 범위로 구현한다.
- `Minimum Patch`: 목표 상태와 어긋남을 알고도 사용자가 명시적으로 빠른 최소 수정을 원해 증상만 막는다.

목표 상태가 요청 범위를 크게 넘으면 차이를 분리해서 설명하고, 이번 범위를 명확히 정한다.
사용자 선호를 추측해 자동으로 범위를 낮추지 않는다.
현재 사용처가 없다는 이유만으로 정당한 확장 지점을 제거하지 않고, 미래 가능성만으로 새로운 계약이나 상태 모델을 선제 추가하지도 않는다.
새 계약이 필요하다면 사용 주체, 책임 소유자, 시작과 종료 조건, 실패가 전달되는 방식을 먼저 설명한다.

## 구조 판단 기준

구조 변경 방식은 미리 정하지 않는다. 목표 상태에 맞춰 유지, 분리, 통합, 이동, 인터페이스 변경, 상태 모델 변경, 의존 방향 변경, 테스트 경계 변경 중 선택한다.

판단 기준:

- 변경 이유, 생명주기, 데이터 소유권, 검증 단위가 갈라지면 분리를 검토한다.
- 항상 함께 변하고 같은 상태를 공유하면 통합을 검토한다.
- 책임이 현재 위치보다 다른 계층이나 모듈에 더 자연스러우면 이동을 검토한다.
- 호출자가 알아야 할 계약이 달라지면 인터페이스 변경을 검토한다.
- 중복 상태, 파생 상태, 호출 순서 의존이 문제를 만들면 상태 모델 변경을 검토한다.
- 불안정한 구현 세부사항이 상위 정책을 끌고 가면 의존 방향 변경을 검토한다.
- 기존 검증 단위가 책임 경계를 반영하지 못하면 테스트 경계 변경을 검토한다.
- 현실적으로 발생 가능한 계약 위반은 상태 변경 전에 해당 책임의 경계에서 검증한다.
- 통제 밖에서 상태가 바뀔 수 있는 경계를 지난 뒤에는 그 경계가 바꿀 수 있는 조건만 다시 검증한다.
- 정상 내부 흐름에서 발생할 수 없는 상태를 가정해 조건 분기, 전용 오류, 복구 상태를 추가하지 않는다. 발생 가능성이 확인되면 먼저 불변식을 깨는 실제 경로와 책임 경계를 찾는다.
- 여러 독립 계약이 동시에 깨져야 발생하는 상황은 실제 요구나 재현 근거 없이 선제 대응하지 않는다.
- 실패 정리는 현재 작업이 직접 만들었고 아직 책임지고 있는 미완료 상태만 다룬다. 되돌릴 수 없는 변경까지 원상복구하려 하거나, 현재 상태를 추측해 다른 영역을 보정하지 않는다.
- 정리 후에도 최초 오류를 호출자가 관측할 수 있게 한다. 정리도 실패하면 최초 오류와 정리 오류를 모두 보존하고, 로그만 남긴 채 성공으로 반환하지 않는다.
- 여러 후속 처리를 끝까지 실행해야 일관성을 보존할 수 있으면 각 실패를 수집하고 필수 처리를 마친 뒤 함께 전달한다.
- 미완료된 상태, 자원, 소유권은 책임 주체가 계속 관리한다. 자동 복구·재시도는 재시도 단위, 중복 실행 의미, 종료 조건, 실패 보고 방식이 계약으로 정해진 경우에만 추가한다.

파일, 클래스, 모듈의 크기만으로 분리하지 않는다.
코드 모양이 비슷하다는 이유만으로 통합하지 않는다.

## 과잉 구현 감사

구현 전과 최종 검토에서 추가한 구조, 분기, 예외 처리, 복구 경로, 테스트마다 다음 근거를 확인한다.

1. 지원하는 진입점에서 해당 경로에 도달하는 실제 호출 흐름이 있는가.
2. 보호해야 할 계약, 불변식, 소유권, 외부 관측 동작이 구체적인가.
3. 기존 책임 경계와 처리 경로로 해결할 수 없는가.

근거가 하나라도 없으면 추가하지 않거나 제거한다.

- 지원하는 공개·내부 계약으로 도달할 수 없거나 여러 독립 계약이 동시에 깨져야 하는 경로를 위한 분기, 상태, 오류 형식, 복구를 만들지 않는다.
- 인터페이스가 허용한다는 이유만으로 가상의 커스텀 구현 실패까지 방어하지 않는다. 현재 계약과 실제 구현이 보장해야 하는 범위만 처리한다.
- 특정 구현 수단을 일률적으로 금지하거나 권장하지 않는다. 확인한 호출 흐름과 계약을 만족하는 가장 단순한 구조를 선택한다.
- 외부에서 관찰할 수 없는 방어 분기, 지원 계약으로 만들 수 없는 상태, 구현 세부사항의 당연한 동작만 검증하는 테스트를 추가하지 않는다.
- 한 위치의 요구를 같은 이름이나 형태를 가진 모든 시스템에 기계적으로 확장하지 않는다. 목적, 실패 경계, 소유권이 같은 범위에만 적용한다.
- 기존 구조가 이미 목표 계약을 표현하면 새 추상화보다 이름, 책임, 호출 순서, 해제 순서를 정돈한다.
- `"혹시"`, `"나중에"`, `"커스텀 구현이라면"`만으로 공개 API나 복구 계약을 확장하지 않는다.
- 주석은 제거한 과거 구현이나 패치 이력을 경고하지 않는다. 현재 구조에서 비자명한 선택이 필요한 이유와 지원하지 않는 계약만 설명한다.

## 반복 실패 시 문제 공간 확장

버그 수정에서 같은 위치나 같은 접근으로 두 번 이상 실패하면 세 번째 수정 전에 문제 공간을 넓힌다.

증상 위치를 원인 위치로 확정하지 않는다.
현재 파일/함수에 조건문, 예외 처리, 우회 로직을 계속 쌓기 전에 원인 후보를 다시 정렬한다.

다음 경우에는 문제 공간을 넓힌다.

- 같은 파일/함수에서 수정했지만 문제가 해결되지 않는다.
- 수정이 증상만 바꾸고 원인을 설명하지 못한다.
- 테스트, 로그, 재현 흐름이 예상과 다른 경로를 가리킨다.
- 호출자, 데이터 생성 지점, 상태 소유자, 초기화 순서, 캐시, 이벤트 구독, 외부 설정이 관련될 수 있다.
- 수정할수록 전용 오류, 보정 플래그, 임시 대기열, 특별 분기, 자동 복구·재시도 경로가 생긴다.

세 번째 수정 전에는 반드시 다음을 정리한다.

- 지금까지 시도한 수정
- 각 수정이 실패한 이유 또는 설명하지 못한 점
- 틀렸을 수 있는 최초 가정
- 새로 확인할 호출 흐름, 데이터 흐름, 상태 소유권, 외부 의존
- 각 방어 분기가 대응하는 실제 계약, 재현 경로, 깨질 수 있는 불변식
- 다음 수정이 이전 접근과 다른 이유

## 완료 기준

완료라고 말하려면 선택한 구현 범위에 맞는 실제 변경과 검증이 있어야 한다.
계획, 선택지, 설계 설명만 있으면 완료가 아니다.

최종 응답 전에 확인한다.

- 목적, 성공 조건, 제약, 선호, 아이디어, 오해/불확실성을 구분했는가.
- 목표 상태, 현재 상태, 차이, 이번 범위를 구분했는가.
- 현재 구조에 맞춘 타협안을 목표 상태로 부르지 않았는가.
- 정렬 상태와 구현 범위를 섞어 말하지 않았는가.
- 남겨둔 차이가 있다면 이유를 설명했는가.
- 검증을 실제 책임 경계에 두고 이미 보장된 내부 불변식에 별도 예외·복구 분기를 추가하지 않았는가.
- 실패 정리가 이번 작업이 직접 만들고 아직 책임지는 미완료 상태로 한정되며, 되돌릴 수 없는 변경이나 다른 책임 영역까지 보정하지 않는가.
- 상태와 소유권을 보존하면서 최초 오류와 정리 오류를 숨기지 않는가.
- 실제 계약 없이 자동 복구·재시도나 새로운 공개 계약을 추가하지 않았는가.
- 추가한 구조, 분기, 예외 처리, 테스트마다 도달 가능한 호출 흐름과 보호할 계약이 있는가.
- 주석이 과거 변경 이력이 아니라 현재 구조의 이유와 계약을 설명하는가.
- 반복 실패 상황이면 문제 공간을 넓혔는가.
- 구현 범위와 사용자 권한에 맞는 검증을 수행했는가.
