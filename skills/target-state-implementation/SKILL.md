# Target-State Implementation

## 역할

이 스킬은 변경을 크게 만들거나 작게 만들기 위한 스킬이 아니다.
요구가 처음부터 시스템에 포함되어 있었다면 자연스러운 목표 구조가 무엇인지 도출하고, 현재 구조와의 차이를 기준으로 이번 작업의 구현 범위와 완료 조건을 결정하게 하는 스킬이다.

`Target State`는 목표 구조다.
사용자 아이디어, 에이전트 계획, 현재 구조, 구현 범위는 모두 `Target State`와 다른 개념이다.

## 핵심 원칙

- 사용자 입력은 목적, 성공 조건, 제약, 선호, 아이디어가 섞인 입력이다.
- 에이전트가 만든 계획은 `Target State`가 아니라 후보안이다.
- 현재 구조는 목표 상태 도출을 위한 입력이지 변경 불가능한 기준이 아니다.
- 구조 변경 방식은 분리, 통합, 이동, 유지 중 하나로 미리 정하지 않는다.
- 계획, 선택지, 설계 설명은 완료가 아니다.

## 실패 모드

다음은 이 스킬을 적용하지 못한 상태다.

- 입력 해석 실패: 목적, 성공 조건, 제약, 선호, 아이디어를 구분하지 못한다.
- 후보안 검증 실패: 사용자 방향성이나 에이전트 계획을 검증 없이 `Target State`로 확정한다.
- 목표 상태 도출 실패: 현재 구조에 맞춘 타협안이나 특정 해결책을 목표 상태로 착각한다.
- 정렬 판정 실패: 현재 구조와 목표 상태의 관계를 진단하지 않고 바로 구현 범위를 정한다.
- 구현 범위 혼동: 정렬 상태, 목표 구조, 이번 작업 범위를 섞어 말한다.
- 구조 변경 오판: 필요한 변화가 무엇인지 판단하지 않고 특정 방식으로 몰아간다.
- 설계 원칙 오용: SOLID, DRY, YAGNI를 판단 도구가 아니라 결론의 근거로 사용한다.
- 완료 오판: 계획, 선택지, 설명을 실제 구현과 검증 완료로 착각한다.
- 범위 책임 전가: 목표 상태와 요청 범위의 차이를 정리하지 않고 사용자에게 판단 부담을 넘긴다.

## 결정 절차

아래 순서를 건너뛰지 않는다.

1. 사용자 입력을 목적, 성공 조건, 제약, 선호, 아이디어로 분리한다.
2. 사용자 방향성과 에이전트 계획을 `Target State` 후보로 검증한다.
3. 필요한 경우 사용자에게 목적, 제약, 방향성을 확인한다.
4. 현재 구조와 독립적으로 목표 상태를 도출한다.
5. 현재 구조와 관련 구현을 탐색한다.
6. 현재 구조와 목표 상태의 정렬 상태를 판정한다.
7. 목표 상태와 현재 구조 사이의 차이를 식별한다.
8. 이번 작업에서 해소할 차이를 구현 범위로 정한다.
9. 선택한 범위 안에서 실제 구현과 검증을 끝낸다.

## 입력과 후보안 검증

사용자 입력은 `Target State`의 결론이 아니다.
에이전트가 만든 계획도 `Target State`의 결론이 아니다.

먼저 다음을 구분한다.

- `목적`: 사용자가 달성하려는 결과
- `성공 조건`: 완료 여부를 판단할 기준
- `제약`: 반드시 지켜야 하는 조건
- `선호`: 가능하면 따르고 싶은 방향
- `아이디어`: 사용자 또는 에이전트가 제안한 해결 후보
- `오해`: 현재 구조나 문제 원인에 대한 잘못된 가정

`목적`, `성공 조건`, `제약`은 우선 보존한다.
`선호`와 `아이디어`는 목표 상태와 비교한다.
`오해`는 정정하고, 필요한 경우 사용자에게 확인한다.

다음 경우에는 구현 전에 묻는다.

- 생성한 계획이 사용자의 목적이나 성공 조건을 보존하는지 불명확하다.
- 사용자 방향성이나 에이전트 계획이 목적 또는 성공 조건과 충돌한다.
- 더 나은 목표 상태 후보가 있지만 사용자의 선호와 다르다.
- 사용자가 제시한 방향성이 필수 제약인지 아이디어인지 불명확하다.

## 목표 상태 도출

항상 아래 질문에서 출발한다.

> 이 요구가 나중에 붙은 추가 요구사항이 아니라, 전체 시스템을 처음 설계할 때부터 포함된 요구였다면 어떻게 구현했을까?

이 질문은 시작점이지 자동 결론이 아니다.
에이전트는 이 질문을 바탕으로 책임 경계, 의존 방향, 데이터 흐름, 상태 모델, 검증 구조를 도출한다.

현재 구현, 기존 인터페이스, 기존 책임 분리, 호출 흐름, 테스트는 반드시 탐색한다.
다만 현재 구조를 변경 불가능한 제약으로 취급하지 않는다.

## 정렬 판정

정렬 상태는 현재 구조와 `Target State`의 관계를 진단한다.
정렬 상태는 구현 범위와 다른 개념이다.

- `Aligned`: 현재 구조가 목표 상태에 가깝다. 기존 확장 지점에 구현해도 목표 상태를 해치지 않는다.
- `Partially Aligned`: 큰 방향은 맞지만 일부 책임, 인터페이스, 데이터 흐름 조정이 필요하다.
- `Misaligned`: 현재 구조가 요구를 억지로 끼우게 만든다. 경계, 책임, 데이터 흐름 재구성을 검토한다.

정렬 판정에는 다음을 함께 밝힌다.

- 현재 구조와 독립적으로 도출한 목표 상태
- 현재 구조의 정렬 상태
- 목표 상태와 현재 구조 사이의 차이
- 이번 작업에서 해소할 차이와 남겨둘 차이

## 구현 범위

구현 범위는 목표 상태와 현재 구조의 차이를 이번 작업에서 어디까지 해소할지 정하는 선택이다.

- `Full Target`: 목표 상태와 현재 구조의 차이를 이번 작업에서 모두 해소한다.
- `Scoped Target`: 목표 상태는 유지하되, 현재 요청과 직접 관련된 차이만 해소한다.
- `Constraint-Based`: 검증된 목표 상태와 다른 제약을 사용자가 명시적으로 유지하라고 해서 그 제약 안에서 구현한다.
- `Minimum Patch`: 목표 상태와 어긋나는 것을 알지만, 사용자가 명시적으로 빠른 최소 수정을 원해 당장 증상만 막는다.

에이전트가 사용자 선호를 추측해 자동으로 범위를 낮추지 않는다.
목표 상태가 요청 범위를 크게 넘으면 차이를 분리해 선택지를 제시한다.
선택지 제시는 완료가 아니며, 선택된 범위 안에서 구현과 검증까지 진행한다.

## 구조 변경 품질 기준

`Target State`는 특정 구조 변경 방식이 아니다.
목표는 책임 경계, 의존 방향, 데이터 흐름, 상태 소유권, 검증 단위가 자연스럽게 맞는 구조를 만드는 것이다.

구조 변경은 다음 중 하나일 수 있다.

- `유지`: 현재 구조가 이미 목표 상태와 정렬되어 있을 때
- `분리`: 변경 이유, 생명주기, 데이터 소유권, 테스트 단위가 갈라질 때
- `통합`: 나뉜 단위들이 항상 함께 변하고 같은 상태를 공유할 때
- `이동`: 책임이 현재 위치보다 다른 계층이나 모듈에 더 자연스러울 때
- `인터페이스 변경`: 호출자가 알아야 할 계약이 달라질 때
- `상태 모델 변경`: 중복 상태, 파생 상태, 호출 순서 의존이 문제를 만들 때
- `의존 방향 변경`: 불안정한 구현 세부사항이 상위 정책을 끌고 갈 때
- `테스트 경계 변경`: 기존 검증 단위가 목표 구조의 책임 경계를 반영하지 못할 때

큰 파일, 클래스, 모듈을 나눌 때도 크기 자체를 기준으로 삼지 않는다.
단순히 파일이 크거나 메서드가 많다는 이유만으로 쪼개지 않는다.

## 흔한 실패 신호

다음 신호가 보이면 구조 변경 방식을 다시 검토한다.

- 생성자 인자, 전달 객체, 조립 코드가 늘어난다.
- 같은 상태 객체나 서비스가 여러 단위에 반복 주입된다.
- 하나의 변경을 위해 더 많은 파일을 동시에 수정해야 한다.
- 데이터는 한곳에 있고 동작만 여러 조각으로 흩어진다.
- 새 단위가 독립적으로 이해되거나 테스트되지 않는다.
- 새 인터페이스가 소비자 계약이 아니라 구현 편의만 반영한다.
- 중복 제거 후 서로 다른 정책이나 변경 이유가 하나로 묶인다.
- 구조 변경 후 호출자가 더 많은 내부 절차를 알아야 한다.
- 테스트나 검증 없이 계획만 제시한다.

이 신호는 자동 결론이 아니다.
신호가 보이면 유지, 분리, 통합, 이동, 인터페이스 변경, 상태 모델 변경, 의존 방향 변경, 테스트 경계 변경 중 어느 방식이 목표 상태에 맞는지 다시 판단한다.

## 설계 원칙 사용 방식

SOLID와 DRY는 결론이 아니라 판단 도구다.

- SRP: 작게 나누라는 뜻이 아니라 변경 이유를 맞추라는 뜻이다.
- DIP: 의존성을 많이 주입하라는 뜻이 아니라 안정적인 경계에 의존하라는 뜻이다.
- ISP: 인터페이스를 늘리라는 뜻이 아니라 소비자가 실제로 쓰는 계약만 노출하라는 뜻이다.
- DRY: 코드 모양이 비슷하다고 합치라는 뜻이 아니라 같은 정책과 규칙이 흩어지지 않게 하라는 뜻이다.
- YAGNI: 목표 상태 도출을 포기하라는 뜻이 아니라 이번 구현 범위에 포함되지 않는 차이를 명시하라는 뜻이다.

설계 원칙은 이미 정한 방향을 사후 정당화하는 데 사용하지 않는다.

## 사용자 표현 해석

사용자가 특정 결과물이나 설명을 가리키며 이 스킬명 또는 `target state` 관련 표현으로 질문하면, 스킬 사용 여부를 묻는 말로만 해석하지 않는다.

그 질문은 대개 대상이 `Target State`인지, 또는 `Target State`에 정렬된 결과인지 판정해 달라는 의미다.
먼저 대상이 목표 구조, 후보안, 구현 범위, 현재 구조에 맞춘 타협안 중 무엇인지 구분해 답한다.

## 명시 호출 강화

사용자가 `/target-state-implementation`, `$target-state-implementation`, `target state`, `땜빵 금지`, `최종 단계 최적 구현`, `전체 구조 보고`처럼 명시하면 다음을 생략하지 않는다.

- 입력과 후보안 검증
- 목표 상태 도출
- 현재 구조 탐색
- 현재 구조와의 정렬 판정
- 구현 범위 선택
- 선택한 범위의 구현과 검증

## 완료 기준

완료라고 말하려면 선택한 구현 범위에 맞는 실제 변경과 검증이 있어야 한다.
계획, 선택지, 설계 설명만 있으면 완료가 아니다.

최종 응답 전에 확인한다.

- 사용자 입력에서 목적, 성공 조건, 제약, 선호, 아이디어를 구분했는가.
- 에이전트가 만든 계획을 목표 상태 후보로 검증했는가.
- 현재 구조와 독립적으로 목표 상태를 도출했는가.
- 현재 구조와 목표 상태의 정렬 상태를 판정했는가.
- 정렬 상태와 구현 범위를 섞어 말하지 않았는가.
- 선택한 구현 범위가 `Full Target`, `Scoped Target`, `Constraint-Based`, `Minimum Patch` 중 무엇인지 명확한가.
- 목표 상태에서 남겨둔 차이가 있다면 이유를 밝혔는가.
- 구조 변경 방식이 목표 상태에 맞는가.
- 흔한 실패 신호가 보이면 구조 변경 방식을 다시 검토했는가.
- 같은 구조의 다른 코드가 방치되어 재발하지 않는가.
- 테스트 또는 검증이 변경 범위에 맞게 수행되었는가.
- 실제 구현이 없으면 완료가 아니라 계획 또는 부분 구현으로 표현했는가.
