# C# 코드 스타일 규칙

Unity C#.

이 문서는 실제 적용할 C# 규칙의 기준이다.
짧은 예시는 규칙을 설명하기 위해 포함하고, 전체 적용 형태가 필요할 때만 별도 참조 예시를 참고한다.
예시의 숫자나 우연한 구현보다 명시된 규칙을 우선한다.

## 규칙 설명

### 최우선 적용

- 이 문서의 규칙은 C# 일반 관습, IDE 자동 정리, 포매터와 정적 분석기 제안보다 우선한다.
- C# 파일을 수정한 뒤 최종 응답 전 `using`, XML 요약 주석 구분선, `<br/>`, 실행 코드 내부 주석, `#region` 구성을 다시 확인한다.
- 예시로 나온 패턴과 같은 구조는 파일 전체에 동일하게 적용한다.

### using

using 그룹은 다음 순서로 배치한다.

| 순서 | 그룹 |
| ---: | --- |
| 1 | `System` |
| 2 | `Unity` |
| 3 | 외부 라이브러리 |
| 4 | 프로젝트 네임스페이스 |

서로 다른 최상위 그룹 사이에는 빈 줄을 한 줄 둔다.

- 하위 네임스페이스를 선언하면 실제로 존재하는 상위 네임스페이스를 중간 단계까지 모두 함께 선언한다.
- `A.B.C`를 선언하면 `A` → `A.B` → `A.B.C` 순서로 배치한다.
- 이 계층 규칙은 일반 네임스페이스 `using`에 적용하고, 별칭·`using static`·`global using`에는 적용하지 않는다.
- 순차 선언을 위해 포함한 상위·중간 네임스페이스는 해당 파일에서 형식을 직접 사용하지 않더라도 제거하지 않는다.
- IDE 자동 정리, 포매터, 정적 분석기의 미사용 `using` 제거 제안보다 순차 선언 규칙을 우선한다.
- 이 규칙을 `System.Collections` 한 사례에만 적용하지 않고 모든 네임스페이스 계층에 동일하게 적용한다.
- 같은 프로젝트의 하위 네임스페이스는 namespace 블록 내부에서 상대 이름으로 선언할 수 있다.

```csharp
using System;
using System.Collections;
using System.Collections.Generic;
using System.Collections.ObjectModel;

using UnityEngine;
using UnityEngine.EventSystems;

using inonego;
using inonego.Xeri;
using inonego.Xeri.UI;
```

위 예시는 직접 사용하는 using만 추린 최소 목록이 아니라, 하위 네임스페이스까지 이어지는 계층을 상위 단계부터 선언하는 형식을 보여준다.

### 중괄호와 들여쓰기

- 중괄호는 BSD 스타일(Allman)을 사용한다.
- 여는 중괄호는 새 줄에 둔다.
- 기본 들여쓰기는 공백 4칸이다. 탭 문자로 들여쓰기나 열 정렬을 만들지 않는다.
- 블록형 `namespace` 내부의 `using`과 형식 선언은 namespace보다 한 단계인 공백 4칸을 들여쓴다. 파일 범위 namespace는 추가 들여쓰기를 만들지 않는다.
- 형식 내부 멤버, 실행 블록 내부 문장, 여러 줄 인수·매개변수와 초기화자 요소도 각 소유 구조보다 한 단계씩 들여쓴다.
- XML summary와 일반 주석은 설명하는 선언·문장과 같은 구조 깊이를 따른다.
- 제네릭 제약 조건은 클래스/메서드 선언과 같은 들여쓰기 레벨에 둔다.
- 같은 문법 구조가 반복되어 줄 사이의 차이를 비교하는 것이 핵심이면 공백으로 같은 역할의 연산자·식별자·대응 값의 열을 맞출 수 있다.
- 시각 정렬은 비교를 쉽게 만드는 범위에서만 사용한다. 서로 다른 책임을 억지로 맞추거나 작은 수정 때문에 넓은 범위를 다시 정렬하지 않는다.

### 실행 블록 경계

- 실행 스코프 안에서 중괄호 블록을 가진 문장이 `}`로 끝나고 같은 스코프의 다음 독립 문장이 이어지면 그 사이에는 빈 줄을 정확히 한 줄 둔다.
- 중첩 깊이와 관계없이 같은 기준을 적용한다. `if`, `foreach`, `for`, `while`, `switch`, `try`처럼 어떤 문법이 블록을 만들었는지가 아니라 닫힌 블록 뒤에 같은 깊이의 다음 실행 단계가 이어지는지를 본다.
- `else`, `catch`, `finally`처럼 앞 블록과 한 문법 구조를 이루는 절은 분리하지 않는다.
- 다음 토큰이 바깥 스코프의 `}`라면 새 실행 단계가 아니므로 빈 줄을 강제하지 않는다. 여러 닫는 중괄호가 연속되는 경우도 같은 이유로 예외다.
- 다음 실행 단계 앞에 흐름 주석이 있으면 `}`와 그 주석 사이에 빈 줄을 한 줄 둔다. 주석은 다음 문장과 붙여 그 단계의 의도를 설명한다.
- 객체·컬렉션 초기화자처럼 실행 스코프를 닫는 중괄호가 아닌 경우에는 이 규칙을 적용하지 않는다.

### 빈 스코프

- 중괄호가 선언·실행 스코프를 만들고 그 안에 선언이나 실행 문장이 없으면 완전히 비워 두지 않고 `// NONE`을 작성한다.
- `// NONE`은 실제 선언·실행 내용이 없음을 뜻하며, 구현 생략이나 동작 설명을 나타내는 일반 주석 뒤에 붙이지 않는다.
- 한 줄 `{ }`로 축약하지 않는다.
- 객체·컬렉션 초기화자처럼 선언·실행 스코프가 아닌 중괄호에는 적용하지 않는다.
- 람다 block은 호출부 가독성을 우선하는 별도 예외로 두며, `// NONE`과 한 줄 빈 block 금지를 기계적으로 강제하지 않는다.

```csharp
public interface IExampleValue
{
    // NONE
}

private void Execute()
{
    // NONE
}
```

### 주석과 XML summary

- XML `<summary>`는 모든 선언에 일률적으로 요구하지 않는다. 공개 계약, 수명주기·소유권, 비자명한 동작처럼 이름과 선언만으로 역할이 충분히 드러나지 않는 경우에 작성한다.
- 단순 DTO·데이터 선언, 자명한 private helper처럼 별도 설명이 실질적인 정보를 더하지 않으면 생략할 수 있다.
- `<summary>`를 작성한 경우에는 접근 수준과 관계없이 아래 형식 규칙을 적용한다.
- `<summary>`와 `</summary>` 태그는 각각 독립된 `///` 줄에 둔다. `/// <summary>설명</summary>`처럼 태그 줄에 설명을 함께 쓰는 축약형은 사용하지 않는다.
- 실제 설명은 두 태그 사이의 별도 `/// ...` 줄에 작성한다.
- `<summary>` 앞뒤에는 같은 길이의 구분선을 둔다.
- 형식 선언 구분선은 `=`를 사용하고, 멤버 선언 구분선은 `-`를 사용한다.
- 구분선 길이는 `// ` 뒤에 반복되는 `=` 또는 `-`의 개수를 뜻하며 60·70·80자 표본 중 하나를 사용한다.
- 코드 들여쓰기는 제외하고 `///`부터 시작하는 설명 줄의 시각적 폭을 계산한다. `/// `, `<br/>`, 공백, 문장 부호는 폭에 포함한다.
- 한글은 한 글자당 1.5칸, 나머지 문자는 한 글자당 1칸으로 계산한다.

구분선 길이는 가장 긴 설명 줄의 시각적 폭에 따라 정한다.

| 가장 긴 설명 줄 | 구분선 |
| --- | --- |
| 60칸 미만 | 60자 |
| 60칸 이상 70칸 미만 | 70자 |
| 70칸 이상 80칸 미만 | 80자 |
| 80칸 이상 | 문장을 나눠 모든 설명 줄을 80칸 미만으로 조정 |

반복 문자를 새로 세지 말고 아래 표본을 그대로 복사하며, 위아래 구분선은 같은 원문을 사용한다.

- summary 설명이 한 줄이면 `<br/>`를 쓰지 않는다.
- summary 설명이 여러 줄이면 첫 줄을 포함한 모든 설명 줄을 `/// <br/>`로 시작한다.
- 주석은 현재 상태의 의도와 작동 방식을 설명한다. 변경 이력이나 작업 기록을 남기지 않는다.

60자 표본:

```csharp
// ============================================================
// ------------------------------------------------------------
```

70자 표본:

```csharp
// ======================================================================
// ----------------------------------------------------------------------
```

80자 표본:

```csharp
// ================================================================================
// --------------------------------------------------------------------------------
```

### 실행 코드 내부 주석

- 메서드, 지역 함수와 접근자의 흐름이 한 번에 읽히지 않으면 의미 단계가 바뀌는 경계에 필요한 만큼 `//` 주석을 둔다.
- 주석은 문법을 읽어 주기보다 해당 단계의 이유, 전제, 상태 전환이나 앞뒤 단계의 관계를 설명한다.
- 반복·분기·조기 반환·상태 변경·리소스 수명·외부 호출처럼 처리 목적이 바뀌는 지점은 주석을 우선 검토한다. 연속된 반복도 목적이 다르면 각 묶음의 역할을 구분하고, 목적이 같으면 하나의 주석으로 묶을 수 있다.
- 긴 조건식·LINQ·중첩 호출을 주석 하나로 덮지 말고 의미 있는 중간 변수나 helper로 먼저 풀어낸다.
- 한 메서드에 여러 책임 단계가 이어지면 주석만 늘리기보다 helper 분리가 더 자연스러운지 검토한다.
- 단순 대입·반환·짧고 자명한 흐름에는 주석을 강제하지 않으며, 순서 번호나 문법을 그대로 읽는 주석은 쓰지 않는다.

### 파일 블록 머리말

C# 파일에 쓰기 작업이 발생하면 다음 블록 머리말을 유지한다.

- 블록 머리말이 없으면 추가한다.
- 파일의 역할이나 제약이 달라졌으면 설명과 수정일을 현재 상태에 맞게 갱신한다.
- 변경 이력을 적지 않고 현재 파일의 역할과 실제 제약만 설명한다.
- 읽기 전용 작업에서는 추가하거나 수정하지 않는다.

```csharp
/* BLOCK_HEADER_BEGIN =======================================================================
파일명 : FileName.cs
수정일 : YYYY-MM-DD

# 설명
파일이 맡는 현재 역할을 설명한다.

# 특이사항, 제약사항
현재 구조에서 유지해야 할 제약을 설명한다.
========================================================================= BLOCK_HEADER_END */
```

### region

- 기본 배치 순서는 내부 데이터 → 필드 → 이벤트 → 생성자 → 복제 → 메서드 → 이벤트 핸들러 → 인터페이스 구현 → 기타다.
- 단순한 클래스는 기본 배치 순서를 따른다.
- region은 단순히 코드를 접기 위한 표시가 아니라, 파일 안에서 함께 변경·관리되는 책임 단위를 드러내도록 사용한다.
- 클래스가 크거나 기능 경계가 명확하면 책임과 기능별 region으로 세분화할 수 있다.
- 각 region은 서로 응집된 하나의 책임을 담되, 파일 전체를 몇 개의 지나치게 큰 region으로 뭉치지 않는다.
- region 제목은 한글을 우선한다. 단순한 클래스에서는 `필드`, `생성자`, `메서드`, `이벤트`, `기타`, `유틸`처럼 멤버 종류를 나타내는 일반 제목도 사용할 수 있다.
- 클래스가 커지거나 기능 경계가 분명해지면 일반 제목을 유지하기보다 실제 책임과 기능이 드러나는 region으로 세분화한다.
- 개별 메서드마다 region을 만들지 않는다.
- `Bind–Unbind`, `Init–Release`, `Subscribe–Unsubscribe`처럼 생명주기나 동작이 대응되는 멤버는 같은 책임 region 안에서 대칭 관계가 드러나도록 배치한다.
- 특정 공개 메서드만을 지원하는 헬퍼는 해당 공개 메서드의 책임 region 안에 배치한다. 여러 책임에서 공유하는 헬퍼만 별도의 내부 처리 region으로 분리한다.
- 기능별 region 내부에서도 가능한 범위에서 기본 배치 순서를 유지한다.
- region을 먼저 만들고 멤버를 억지로 끼워 넣지 않는다. 멤버의 책임이 region과 맞지 않으면 클래스의 책임과 멤버 위치를 함께 다시 검토한다.
- `#region`과 `#endregion`은 둘러싼 형식 선언과 그 형식의 여는·닫는 중괄호와 같은 들여쓰기에 둔다.
- region 내부 멤버는 형식 내부 멤버의 일반 들여쓰기를 유지한다. region 때문에 추가로 들여쓰지 않는다.

region 경계의 빈 줄은 다음과 같이 고정한다.

| 경계 | 빈 줄 |
| --- | ---: |
| 형식의 여는 중괄호 → 첫 `#region` | 1줄 |
| `#region` → 첫 내용 | 1줄 |
| 마지막 내용 → `#endregion` | 1줄 |
| `#endregion` → 다음 region 또는 코드 | 1줄 |
| 마지막 `#endregion` → 형식의 닫는 중괄호 | 1줄 |

위 경계에 빈 줄이 없거나 두 줄 이상 연속되면 규칙 위반으로 본다. 내용이 없는 region은 선언하지 않는다.

### 명명

이름의 의미와 변경 범위는 `programmer`의 명명 판단 절차로 정한 뒤 C# 표기를 적용한다. 모든 식별자는 `_`를 위치와 개수에 관계없이 포함할 수 있고, casing 판정에서는 `_`를 제외한 이름 본체를 평가한다.

| 대상 | 기본 표기 | `_` 사용 |
| --- | --- | --- |
| 형식, 구조체, 열거형과 그 멤버, 대리자, 프로퍼티, 이벤트, 메서드, 지역 함수 | PascalCase | 위치 무관 허용 |
| 인터페이스 | `I` + PascalCase | 위치 무관 허용 |
| 매개변수, 지역 변수 | camelCase | 위치 무관 허용 |
| private 필드 | camelCase | 위치 무관 허용 |
| protected / internal / protected internal / private protected 필드 | camelCase 또는 PascalCase | 위치 무관 허용 |
| public 필드 | PascalCase | 위치 무관 허용 |
| `const` 필드 | 접근 수준별 필드 표기 또는 SCREAMING_SNAKE_CASE | 위치 무관 허용 |

`_` 자체는 casing 위반으로 보지 않는다. `_`를 모두 제외한 이름이 대상의 기본 표기를 만족하면 허용하며, `_` 또는 `__`처럼 밑줄만으로 구성된 식별자도 casing 오류로 진단하지 않는다. `const`는 접근 수준별 일반 필드 표기 외에 SCREAMING_SNAKE_CASE도 허용하며, `static readonly`는 일반 필드 규칙을 따른다. 식별자의 역할 적합성은 별도 의미 판단으로 검토한다.

- 형식 이름은 도메인의 대상과 역할을, 메서드 이름은 실제 동작을, bool 이름은 상태나 질의를 드러낸다.
- 비동기 메서드의 `Async` 접미사는 실제 의미와 외부 계약을 보고 결정한다. 반환형 이름만으로 자동 강제하지 않는다.
- 프로젝트에 같은 개념을 표현하는 용어가 있으면 그 용어와 표기를 이어간다.
- 외부 기반 형식의 `override` 멤버와 명시적 인터페이스 구현은 대상 API의 이름 계약을 그대로 따른다. 외부 계약 때문에 정해진 casing이나 `Async` 접미사는 이 프로젝트 명명 규칙으로 바꾸지 않는다.

### 타입과 멤버 배치

- MonoBehaviour가 아닌 클래스는 `[Serializable]` 사용을 권장한다.
- 클래스 내부 구조체/열거형은 전용 타입으로, 클래스 외부 구조체/열거형은 공용 타입으로 둔다.
- 프로퍼티와 대응 필드는 하나의 배치 단위로 보고 서로 붙여 둔다.
- 자동 배치 판정은 하나의 private 필드를 하나의 프로퍼티가 직접 반환하는 1:1 관계가 확정될 때만 적용한다. 여러 프로퍼티가 같은 필드를 공유하면 단일 backing pair로 단정하지 않고 수동으로 책임을 판단한다.
- 대응 필드가 private이면 해당 프로퍼티 바로 아래에 두며, 다른 private 필드와 묶기 위해 분리하지 않는다.
- 독립 멤버는 접근 수준을 기계적으로 정렬하기보다 책임, 생명주기, 호출 흐름과 함께 읽히는 응집도를 우선해 배치한다.
- 프로퍼티와 대응 필드의 인접 배치는 다른 멤버 정렬보다 우선한다.
- 직렬화 대상 private 필드는 `[SerializeField]` 또는 `[SerializeReference]`를 사용한다. initializer는 기본값 의도를 명확히 하는 데 도움이 될 때 권장하지만 강제하지 않는다.

### 프로퍼티와 메서드

- 읽기 전용 프로퍼티와 값 반환 메서드는 한 식으로 자연스럽게 읽히고 상태 변경이나 여러 실행 단계가 없으면 `=>`를 사용할 수 있다.
- 단순 비교·논리 조합·null 판정·멤버 접근·짧은 계산이나 helper 호출처럼 결과가 바로 드러나는 식은 `=>` 사용 범위에 포함한다.
- 대입·증감처럼 현재 expression body 자체에서 상태를 직접 변경하거나 여러 실행 단계를 읽어야 하는 경우에는 블록 본문을 사용한다.
- 새 객체의 initializer에서 값을 지정하는 구문이나 반환되는 람다 내부의 동작은 바깥 expression body 자체의 상태 변경으로 보지 않는다.
- 선택적 매개변수 기본값은 허용한다.

### 생성자

- 생성자 initializer는 실제로 생성자 체이닝이나 특정 base 생성자 호출이 필요할 때만 사용한다.
- 의미 없는 `: base()` 표기를 강제하지 않는다.

### 제어문

- `return`, `break`, `continue`만 단문을 허용한다.
- 그 외 제어문은 단일 문장이라도 중괄호를 사용한다.

### 람다와 지역 함수

- 람다식은 호출부에서 바로 읽히는 범위라면 식 본문과 블록 본문을 모두 사용할 수 있다.
- 별도 이름이 책임을 더 잘 드러내거나 같은 처리를 재사용해야 하거나 호출부가 길어지는 경우에는 지역 함수나 별도 메서드로 추출한다.
- 람다 사용 여부는 문장 수, 분기나 대입 존재만으로 기계적으로 결정하지 않고 주변 호출부와 책임을 함께 본다.
- 긴 변수명은 의미가 유지되는 짧은 지역 변수로 할당해 호출부를 단순화할 수 있다.

### 간결한 표현과 줄바꿈

- 줄바꿈은 글자 수나 매개변수·인수 개수만으로 결정하지 않고, 전체 구문이 한 번에 읽히는지와 의미 묶음을 기준으로 판단한다.
- 단순 필드·상수·자동 프로퍼티처럼 선언부와 단일 단순 initializer가 하나의 의미 단위인 선언은 길이만을 이유로 선언과 initializer를 분리하지 않고 한 줄을 유지한다.
- 선언·호출 내부에 자체 구조를 펼쳐 읽을 이유가 있거나 서로 다른 의미 묶음이 명확한 경우에만 자연스러운 구문 경계에서 여러 줄로 나눈다.
- 의미 있는 구조 없이 단순 구성 요소를 형식적으로 분리하거나, 요소를 기계적으로 하나씩 세로로 늘어놓는 줄바꿈은 피한다.
- 개별 매개변수·인수가 단순해도 여러 의미 묶음이 명확하면 그룹 단위로 여러 줄을 사용할 수 있다. 같은 묶음은 가능한 한 같은 줄에 둔다.
- 짧고 단순하며 개별 값 지정·주석·그룹 구분이 필요 없는 작은 enum은 한 줄 compact 표현을 우선하며, 이 경우 enum 중괄호는 Allman 배치의 예외다. 구조를 펼쳐 읽을 이유가 있으면 여러 줄로 작성한다.
- 객체·컬렉션 초기화자나 `switch` 식처럼 자체 구조를 펼쳐 읽는 편이 자연스러운 경우에는 여러 줄을 허용하되 강제하지 않는다.
- 여러 줄 선언이나 호출에서는 `(`와 `)`를 각각 별도 줄에 둔다.
- 대상 형식이 이미 분명하고 반복을 줄이는 편이 읽기 좋으면 target-typed `new(...)` 또는 `new()`를 권장한다. 명시적 형식명이 문맥을 더 분명하게 하면 `new TypeName(...)`도 허용한다.
