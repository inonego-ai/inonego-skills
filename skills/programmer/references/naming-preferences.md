# 명명 취향

이 문서는 특정 이름을 재사용하기 위한 목록이 아니라, 새 이름을 분석하고 선택하기 위한 기준이다. 과거에 선택한 이름과 철자가 비슷하다는 이유만으로 적용하지 말고 현재 대상의 실제 역할과 주변 문맥에서 다시 판단한다.

## 핵심 관점

이름은 대상을 구별하는 표식이면서 구조에 대한 약속이다. 이름에 들어간 도메인, 역할, 범위와 수명 관련 단어는 그 대상이 무엇을 알고 소유하며 어디까지 조정하는지를 암시한다. 따라서 문법적으로 자연스럽거나 흔히 쓰이는 이름이라도 실제 책임보다 넓은 구조, 존재하지 않는 계층이나 패턴, 대상이 소유하지 않는 수명 계약을 암시하면 적합하지 않다.

반대로 이름을 짧게 만드는 것만으로 좋은 이름이 되지는 않는다. 필요한 경계를 지워 다른 개념과 구별되지 않거나 기존 공개 용어와 어긋나면 의미를 복구해야 한다. 목표는 가장 짧은 이름이 아니라, 실제 책임을 가장 적은 불필요한 단어로 정확하게 드러내는 이름이다.

## 분석 순서

### 1. 실제 대상을 먼저 규정한다

- 대상이 표현하는 도메인과 계층을 확인한다.
- 직접 소유하는 상태, 수명과 자원을 확인한다.
- 직접 수행하는 일과 다른 대상에 위임하는 일을 나눈다.
- 하나의 객체, 한 집단, 한 기능 흐름, 전체 시스템 중 실제 조정 범위를 확인한다.
- 현재 구현뿐 아니라 이미 확정된 공개 계약과 프로젝트 용어를 확인한다.

이 단계의 결과를 한두 문장으로 설명하지 못하면 이름 후보부터 만들지 않는다. 구현에서 확인되지 않은 책임을 이름으로 먼저 확정하지 않는다.

### 2. 이름이 만드는 기대를 해석한다

후보의 각 단어가 다음 중 무엇을 암시하는지 확인한다.

- 도메인: 대상이 속한 업무 영역
- 주체: 상태나 동작의 실제 소유자
- 범위: 개별 대상, 집합, 기능 단위 또는 전체 흐름
- 계약: 값, 상태, 요청, 매개변수, 문맥, 서비스와 같은 사용 방식
- 수명: 생성, 유지, 실행, 종료를 누가 책임지는지
- 조정 역할: 관리, 제어, 중재, 표현 중 무엇을 수행하는지

접미사나 역할 단어를 관성적으로 붙이지 않는다. 특정 단어 자체를 피하는 방식으로도 판단하지 않는다. 넓은 조정 범위를 암시하는 단어는 실제로 그 범위를 소유할 때 사용하고, 단순한 데이터나 호출 인자에 독립 명령·수명·실행 주체를 암시하는 이름을 붙이지 않는다.

### 3. 기존 어휘와 개념 경계를 맞춘다

- 같은 프로젝트와 같은 API 영역에서 이미 쓰는 핵심 명사를 우선한다.
- 실제 장면, 자산, 계층과 공개 형식의 정확한 이름을 사용한다.
- 같은 개념에 새 동의어를 추가해 이름을 파편화하지 않는다.
- 비슷해 보여도 책임이나 수명이 다른 개념은 같은 이름 계열로 합치지 않는다.
- 제안 중인 구조나 이름을 이미 확정된 설계처럼 취급하지 않는다.

기존 어휘를 우선하는 이유는 단순한 통일감이 아니다. 같은 단어가 같은 경계와 계약을 계속 가리켜야 코드, 문서와 대화 사이에서 별도의 번역 없이 소유 관계를 추적할 수 있기 때문이다.

### 4. 문맥 중복과 과장된 단어를 걷어낸다

호출 위치, 소유 형식, 네임스페이스나 주변 API가 이미 제공하는 의미를 이름에서 다시 반복하는지 확인한다. 반복 단어는 길이만 늘리는 것이 아니라 대상이 별도의 계층이나 더 넓은 책임을 가진 것처럼 보이게 할 수 있다.

다음 조건을 모두 만족할 때 중복 단어를 제거한다.

- 제거해도 같은 범위에서 다른 개념과 구별된다.
- 계약 종류나 소유권이 흐려지지 않는다.
- 검색성과 공개 API의 일관성이 나빠지지 않는다.
- 직렬화 이름, 외부 연동 또는 호환 계약을 깨뜨리지 않는다.

### 5. API 계열 전체의 형태를 비교한다

이름 하나만 보지 말고 함께 사용되는 형식, 메서드, 상태와 이벤트를 나란히 놓는다.

- 같은 역할에는 같은 문법과 시제를 사용한다.
- 시작과 끝의 구조를 맞춰 호출 순서와 상태 관계가 읽히게 한다.
- 한 이름 안의 불필요한 반복은 줄이되, API 계열의 관계를 드러내는 반복은 유지한다.
- 철자가 비슷하다는 이유만으로 의미가 다른 구성원까지 일괄 변경하지 않는다.

형태의 대칭은 장식이 아니라 사용자가 여러 이름을 하나의 계약으로 인식하게 만드는 단서다. 다만 대칭을 맞추기 위해 실제 상태나 시제 차이를 없애지 않는다.

## 사용자의 철자 및 조형 취향

사용자는 이름의 의미뿐 아니라 철자 배열과 글자의 형태를 함께 본다. 대소문자 배치, PascalCase 단어 덩어리의 수와 길이, 접두·접미 부분의 균형, 문자열 전체의 시각적 밀도와 윤곽이 선택에 영향을 준다. 이는 사용자 개인의 명명 취향이며 일반 프로그래밍 규칙이나 언어 컨벤션이 아니다.

- 원형이 여러 대문자로 굳어진 약어는 PascalCase 이름 안에서도 하나의 대문자 덩어리로 유지한다. `Id`, `Sfx`, `Vfx`보다 `ID`, `SFX`, `VFX` 형태를 선호한다.
- 의미와 계약이 비슷한 후보 사이에서는 소문자 `t`, `f`가 적은 철자 형태를 선호한다.
- 소문자 `t`, `f` 선호는 해당 문자의 사용을 금지하거나 대문자 `T`, `F`까지 같은 대상으로 취급한다는 뜻이 아니다.
- 의미를 해치지 않는다면 불필요한 단어 덩어리가 적고 길이의 리듬이 안정적인 이름을 선호한다.
- 개별 이름의 모양뿐 아니라 함께 노출되는 API 이름들의 공통 윤곽과 균형을 본다.

약어의 대문자 형태는 약어가 하나의 의미 단위라는 점과 문자열 안에서의 시각적 경계를 함께 보존한다. 임의로 줄인 단어나 일반 단어를 새 약어처럼 대문자화하지는 않는다. 기존 확정 용어, 외부 API, 직렬화 호환과 공개 계약에 다른 표기가 정해져 있으면 그 계약을 우선한다.

이 취향을 문자 개수 점수나 정적 검사 규칙으로 바꾸지 않는다. 정확한 의미가 우선하며, 먼저 의미상 유효한 후보만 남긴 뒤 철자와 조형을 최종 선택 기준으로 사용한다.

## 후보를 제시하는 방식

이름을 제안하거나 검토할 때는 단순히 과거 선택과 닮았다고 설명하지 않는다. 다음 내용을 현재 대상에 근거해 함께 제시한다.

1. 대상의 실제 책임과 소유 범위
2. 후보가 암시하는 도메인, 계약과 수명
3. 기존 프로젝트 어휘 및 인접 API와의 관계
4. 제거하거나 유지한 단어의 이유
5. 의미가 동등할 때 적용한 철자와 조형 판단

사용자가 정확한 이름이나 표기를 직접 지정했다면 그 결정을 우선한다. 질문, 비교 요청이나 후보 언급만으로 이름 변경이 승인됐다고 해석하지 않는다.
