# 명명 취향

특정 이름을 재사용하기 위한 목록이 아니라 새 이름을 분석·선택하는 기준이다. 과거 이름과 철자가 비슷하다는 이유로 적용하지 말고 현재 대상의 실제 역할과 문맥에서 다시 판단한다.

## 핵심 관점

이름은 대상을 구별하는 표식이자 구조에 대한 약속이다. 도메인, 역할, 범위, 수명 단어는 대상이 무엇을 알고 소유하며 어디까지 조정하는지를 암시한다. 실제 책임보다 넓은 구조, 없는 계층·패턴, 소유하지 않는 수명 계약을 암시하면 흔한 이름이라도 부적합하다. 반대로 짧게 만드는 것이 목표는 아니며, 필요한 경계를 지워 다른 개념과 구별되지 않거나 공개 용어와 어긋나면 복구한다. 실제 책임을 가장 적은 불필요한 단어로 정확하게 드러내는 이름을 고른다.

## 분석 순서

### 1. 실제 대상 규정

도메인과 계층, 직접 소유하는 상태·수명·자원, 직접 수행하는 일과 위임하는 일, 실제 조정 범위(객체 하나 / 집단 / 기능 흐름 / 전체), 확정된 공개 계약과 프로젝트 용어를 확인한다. 한두 문장으로 설명하지 못하면 후보부터 만들지 않으며, 구현에서 확인되지 않은 책임을 이름으로 먼저 확정하지 않는다.

### 2. 이름이 만드는 기대 해석

각 단어가 도메인, 주체(소유자), 범위, 계약(값·상태·요청·매개변수·문맥·서비스), 수명(생성·유지·실행·종료 책임자), 조정 역할(관리·제어·중재·표현) 중 무엇을 암시하는지 확인한다. 접미사·역할 단어를 관성적으로 붙이지 않고 특정 단어를 기계적으로 피하지도 않는다. 넓은 범위를 암시하는 단어는 실제로 그 범위를 소유할 때만 쓰고, 단순 데이터·호출 인자에 독립 명령·수명·실행 주체를 암시하는 이름을 붙이지 않는다.

### 3. 기존 어휘와 개념 경계

- 같은 프로젝트·API 영역의 핵심 명사를 우선하고 실제 장면·자산·계층·공개 형식의 정확한 이름을 쓴다.
- 같은 개념에 새 동의어를 추가하지 않고, 책임·수명이 다른 개념은 같은 이름 계열로 합치지 않는다.
- 제안 중인 구조나 이름을 확정된 설계처럼 취급하지 않는다. 기존 어휘를 우선하는 이유는 같은 단어가 같은 경계와 계약을 가리켜야 소유 관계를 번역 없이 추적할 수 있기 때문이다.

### 4. 문맥 중복과 과장 제거

호출 위치, 소유 형식, 네임스페이스, 주변 API가 이미 주는 의미를 이름에서 반복하면 길이만 늘고 별도 계층·더 넓은 책임처럼 보인다. 다음을 모두 만족할 때 중복 단어를 제거한다.

- 같은 범위에서 다른 개념과 여전히 구별된다.
- 계약 종류와 소유권이 흐려지지 않는다.
- 검색성과 공개 API 일관성이 나빠지지 않는다.
- 직렬화 이름·외부 연동·호환 계약을 깨지 않는다.

### 5. API 계열 전체 비교

함께 쓰이는 형식, 메서드, 상태, 이벤트를 나란히 놓고 같은 역할에는 같은 문법과 시제를 쓴다. 시작과 끝의 구조를 맞춰 호출 순서와 상태 관계가 읽히게 하고, 이름 안의 불필요한 반복은 줄이되 계열의 관계를 드러내는 반복은 유지한다. 대칭을 위해 실제 상태·시제 차이를 없애지 않으며 철자가 비슷하다는 이유로 의미가 다른 구성원까지 일괄 변경하지 않는다.

## 사용자의 철자 및 조형 취향

사용자는 의미뿐 아니라 철자 배열과 글자 형태도 본다. 개인의 명명 취향이며 일반 규칙이나 언어별 코딩 규칙이 아니다.

- 원형이 여러 대문자로 굳어진 약어는 PascalCase 안에서도 하나의 대문자 덩어리로 유지한다(`Id`, `Sfx`, `Vfx`보다 `ID`, `SFX`, `VFX`).
- 의미와 계약이 비슷한 후보 사이에서는 소문자 `t`, `f`가 적은 철자 형태를 선호한다. 해당 문자의 사용 금지나 대문자 `T`, `F`까지의 확장이 아니다.
- 의미를 해치지 않는 범위에서 단어 덩어리가 적고 길이 리듬이 안정적인 이름을 선호하며, 함께 노출되는 API 이름들의 공통 윤곽과 균형도 본다.
- 임의로 줄인 단어나 일반 단어를 새 약어처럼 대문자화하지 않는다. 확정 용어, 외부 API, 직렬화 호환, 공개 계약이 다른 표기를 정했으면 그 계약을 우선한다.
- 이 취향을 문자 수 점수나 정적 검사 규칙으로 바꾸지 않는다. 의미상 유효한 후보만 남긴 뒤 철자와 조형을 최종 선택 기준으로 쓴다.

## 후보를 제시하는 방식

과거 선택과 닮았다고 설명하지 말고 현재 대상에 근거해 제시한다.

1. 대상의 실제 책임과 소유 범위
2. 후보가 암시하는 도메인, 계약, 수명
3. 기존 프로젝트 어휘와 인접 API와의 관계
4. 제거·유지한 단어의 이유
5. 의미가 동등할 때 적용한 철자·조형 판단

사용자가 정확한 이름이나 표기를 지정했으면 그 결정을 우선한다. 질문, 비교 요청, 후보 언급만으로 이름 변경이 승인된 것으로 해석하지 않는다.
