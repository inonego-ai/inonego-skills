# 설계

요구사항과 탐색 결과를 받아 아키텍처와 구현 블루프린트를 확정하는 단계.  
설계 결과가 **구현 단계의 입력**이 된다. 여기서 정해지지 않은 것은 구현 중에 즉흥 결정되며, 즉흥 결정은 품질을 떨어뜨린다.

---

## 원칙: 사용자 검토는 상시 수행

각 단계에서 결정이 확정되기 전에 사용자와 정렬한다. 판단이 갈리거나 트레이드오프가 있을 때는 `asqu` 스킬로 즉시 확인한다.

- §1 범위·경계·제약이 불명확할 때 사용자에게 확인
- §2 아키텍처 접근 선택지가 갈릴 때 대안·트레이드오프 제시 후 확정
- §3 상세 설계에서 계약·실패 정책·허용 입력 범위가 갈릴 때 사용자 확인
- 사용자 피드백이 상위 단계를 흔들면 즉시 해당 단계로 복귀

---

## 단계 체크리스트

순서대로 수행한다. 이전 단계의 출력이 없으면 다음 단계로 진행하지 않는다.

- [ ] **1.** 설계 범위 확정
- [ ] **2.** 아키텍처 결정
- [ ] **3.** 상세 설계
- [ ] **4.** 설계 검증
- [ ] **5.** 구현 블루프린트 출력

---

## 1. 설계 범위 확정

**입력**: 요구사항 분석 결과 + (있다면) 코드 탐색 결과

| 항목 | 확인 내용 |
|------|----------|
| **설계 대상** | 어떤 컴포넌트·모듈·시스템을 설계하는가 |
| **경계** | 건드리는 것과 건드리지 않는 것 |
| **제약** | 기존 패턴·기술 스택·성능·호환성 제약 |

> **범위·제약이 명확하지 않은 상태로 2단계 진행 금지.**

---

## 2. 아키텍처 결정

**입력**: 1단계 범위 + 제약 (+ 요구사항·탐색 결과)  
**출력**: 고수준 아키텍처 — 접근·컴포넌트 구조·의존성·데이터 흐름·파일 배치

**메인 컨텍스트가 직접 수행한다.**

활용할 입력:

- 요구사항
- 설계 범위·경계·제약
- (있다면) 코드 탐색 결과 — 기존 패턴·관련 파일·주의사항
- 사용자가 선호/비선호하는 방향 (있을 때만)

> 패턴 분석·기존 구현 참조가 더 필요하면 탐색을 먼저 수행한다.  
> 설계 도중 추가 탐색이 필요해지면 탐색으로 돌아갔다가 복귀한다.

### 결정할 것

- 선택한 접근 + 근거 (대안 나열 아님 — **단일 선택**)
- 존재할 컴포넌트와 각자의 책임
- 컴포넌트 간 의존성 방향
- 데이터 흐름 (입력 → 변환 → 출력 개요)
- 파일/디렉토리 배치

### 원칙

- **단일 접근으로 수렴** — 옵션 A/B 나열은 결정이 아니다. 트레이드오프가 정말 갈릴 때만 사용자에게 선택을 돌린다.
- **기존 패턴을 존중** — 탐색 결과에서 드러난 기존 관례와 어긋나는 결정은 명시적 근거 필요
- **고수준에 머무른다** — 이 단계는 "무엇이 어디에 있고 어떻게 엮이는가". 시그니처·계약 상세는 §3로

---

## 3. 상세 설계

**입력**: 2단계 아키텍처  
**출력**: 인터페이스·계약·테스트 전략·빌드 순서 상세

각 컴포넌트의 세부를 확정한다. 구현 단계는 **설계된 것을 번역하는 단계**이므로, 상세 설계에 공백이 남으면 구현 중 임의 결정이 끼어들어 품질을 떨어뜨린다.

### 결정할 것

- **공개 API 시그니처** — 각 컴포넌트의 공개 함수·메서드 시그니처와 타입
- **데이터 구조** — 입출력에 쓰이는 타입·구조
- **컴포넌트 간 계약** — 누가 누구를 호출하고, 무엇을 기대하는가
- **실패 동작** — 각 경계에서 어떤 조건이 실패이고, 어떻게 전파·처리할지
- **허용 입력 범위** — 경계값·빈·허용/비허용 조건에 대한 처리 방침
- **테스트 전략** — 단위·통합·인수 대상
- **빌드 순서** — Phase 분해 + 각 Phase 완료 기준

### 원칙

- **계약은 빠짐없이** — 구현 중 "블루프린트에 없어서 임의로 결정"이 일어나지 않도록
- **실패 동작을 얼버무리지 않는다** — "실패 시 에러 반환"만으로는 부족. 어떤 조건·어떤 에러·누구에게·어떻게 전달되는지까지

---

## 4. 설계 검증

**입력**: 아키텍처 + 상세 설계

상시 수행되는 사용자 검토는 "이 방향이 맞는가"를 묻는 것이고, 설계 검증은 "설계가 스스로 정합한가"를 보는 것이다. 사용자 정렬이 끝나도 설계 내부에 모순이 있을 수 있다.

### 검증 항목

| 항목 | 확인 내용 |
|------|----------|
| **요구사항 커버리지** | MoSCoW의 MUST가 모두 설계에 반영됐는가. 해소된 모호성도 포함 |
| **계약 정합성** | 컴포넌트 A의 출력이 B의 입력으로 맞는가. 인터페이스 간 타입·shape 일치 |
| **실패 전파 일관성** | A에서 발생하는 실패가 B의 계약에 정의되어 있는가. 누락·불일치 없음 |
| **의존성 그래프** | 순환 참조 없음. 컴포넌트 의존 방향이 일관적 |
| **빌드 순서 실행 가능성** | 각 Phase가 이전 Phase의 산출물만으로 진행 가능한가 |
| **테스트 전략 커버리지** | MUST 요구사항을 검증할 수 있는 테스트 경로가 있는가 |

### 실패 시 복귀 경로

| 발견된 문제 | 복귀 단계 |
|-------------|----------|
| 범위·제약 오류 | §1 설계 범위 확정 |
| 의존성 구조·빌드 순서 실행 불가·컴포넌트 구성 문제 | §2 아키텍처 결정 |
| 계약 불일치·테스트 전략 누락·실패 전파 문제 | §3 상세 설계 |
| 요구사항 누락·해석 문제 | 요구사항 분석 워크플로우 |

> **검증을 통과하지 못한 상태로 5단계 진행 금지.**

---

## 5. 구현 블루프린트 출력

**입력**: 검증 통과한 결과

구현 단계로 넘기는 최종 산출물. **새로운 결정을 내리지 않는다** — 앞 단계에서 확정된 것을 아래 구조로 정리만 한다.

```
접근 요약:
- [한 줄 요약]
- 핵심 컴포넌트: [A] — 역할 / [B] — 역할

파일/디렉토리:
- 생성: [경로] — [역할]
- 수정: [경로] — [변경 요약]

인터페이스·계약:
- [API/함수 시그니처]
- [데이터 구조]
- [컴포넌트 간 계약]
- 실패 동작: [경계별 실패 조건 → 전파·처리]
- 허용 입력 범위: [경계값·빈·허용/비허용]

테스트 전략:
- 단위: [...]
- 통합: [...]
- 인수: [요구사항 대응]

빌드 순서:
- Phase 1: [...] — 완료 기준: [...]
- Phase 2: [...] — 완료 기준: [...]
```
