# 검증

구현된 코드가 요구사항을 만족하는지, 기존 동작이 깨지지 않았는지 확인하는 단계.  
**통과하지 못하면 완료 아님.** 실패 시 원인 단계로 되돌아간다 (구현·설계·요구사항 중).

---

## 원칙

- **실패는 숨기지 않는다** — "거의 다 됐다"는 완료가 아니다
- **완화하지 않는다** — 테스트를 느슨하게 고쳐 통과시키는 행위 금지
- **원인 단계로 되돌린다** — 증상만 가리는 수정은 부채를 키운다. 실패가 발견되면 증상 위치(테스트)가 아니라 원인 위치(구현·설계·요구사항)에서 고친다

---

## 단계 체크리스트

순서대로 수행한다. 이전 단계의 출력이 없으면 다음 단계로 진행하지 않는다.

- [ ] **1.** 검증 범위 결정
- [ ] **2.** 단위 테스트
- [ ] **3.** 통합 테스트
- [ ] **4.** 인수 테스트
- [ ] **5.** 회귀 테스트

---

## 1. 검증 범위 결정

**입력**: 작업 유형 + 구현 결과 + 설계 블루프린트의 "테스트 전략"

작업 유형에 따라 실제로 돌려야 할 검증 범위가 다르다.

| 작업 유형 | 필수 검증 |
|-----------|----------|
| 신규 개발 | 단위 + 통합 + 인수 |
| 기능 추가 | 단위(신규) + 통합 + 인수 + 회귀 |
| 버그 수정 | 재현 테스트(실패 → 통과) + 회귀 |
| 리팩토링 | 회귀 (동작 보존 확인) |
| 최적화 | 측정(before/after) + 회귀 |
| 기능 제거 | 회귀 (나머지 동작 보존) |
| 통합 | 통합 + 인수 + 회귀 |
| 의존성 업데이트 | 단위 + 통합 + 회귀 |

범위 결정 후 각 항목의 구체 대상(어떤 함수·경로·시나리오)을 확정한다.

---

## 2. 단위 테스트

**입력**: 1단계에서 확정한 단위 테스트 대상

격리된 단위(함수·클래스·순수 모듈)의 동작을 확인한다.

- **대상**: 격리 가능한 단위 — 순수 함수, 모킹 가능한 의존성을 가진 클래스
- **격리**: 전역 상태·실제 I/O를 쓰지 않는다. 외부 의존성은 주입된 대역으로 대체
- **커버 범주**: 정상 경로 / 경계값 / 에러 경로
- **금지**: 존재하지 않는 동작에 대한 테스트, 테스트를 통과시키기 위해 실제 동작을 허술하게 만드는 것

단위 테스트가 불가능한 구조라면 **교체 가능성 위반**이다. 원인 단계(구현·설계)로 되돌아가 인터페이스 뒤로 의존성을 격리한다.

---

## 3. 통합 테스트

**입력**: 1단계에서 확정한 통합 테스트 대상

실제 I/O(DB·파일·네트워크)를 포함한 경로를 확인한다.

- **대상**: 외부 의존성이 개입하는 실제 경로 — 리포지토리 ↔ DB, 클라이언트 ↔ 서버, 파일 읽기·쓰기
- **환경**: 격리 가능한 실제 환경 (로컬 DB, 테스트 컨테이너, 샌드박스)
- **금지**: 프로덕션 환경 직격, 실제 결제·외부 호출이 부작용을 남기는 행위

통합 테스트가 번거롭다고 생략하면 경계면 버그(API 응답 shape 불일치·트랜잭션 경계 등)를 놓친다.

---

## 4. 인수 테스트

**입력**: 요구사항 분석 결과의 **완료 기준** + 구현 결과

사용자 관점의 "완료"가 실제로 달성됐는지 확인한다.

| 확인 | 방법 |
|------|------|
| MoSCoW의 **MUST** 전부 만족 | 요구사항 항목별로 동작 확인 |
| 해소된 모호성이 반영됨 | 요구사항 분석의 "확정된 해석"이 구현에 반영됐는지 |
| 사용자 시나리오 흐름 | 주요 시나리오를 end-to-end로 실행 |

인수 기준은 **요구사항 단계에서 이미 정의되어 있어야** 한다. 인수 단계에 와서 처음 만드는 기준은 뒤늦은 요구사항이다. 요구사항 분석으로 되돌려 기록한 뒤 재검증한다.

---

## 5. 회귀 테스트

**입력**: 기존 테스트 스위트 + 이번 변경 범위

기존 동작이 깨지지 않았는지 확인한다.

- **기존 테스트 스위트 실행** — 실패 시 이번 변경과의 연관성을 분석한다
- **탐색 단계의 "영향 범위 분석"으로 확인된 호출자** — 같이 돌려본다
- **실패한 테스트가 있으면**: 의도한 동작 변경인지(→ 테스트 업데이트) 버그인지(→ 구현 수정) 판별한다

> 회귀 실패를 "테스트가 오래됐다"고 섣불리 삭제하지 않는다. 테스트가 보호하려던 원래 의도를 확인한 뒤 판단한다.

---

## 출력

검증 완료 후 다음을 제시한다.

```
검증 범위:
- 단위: [대상]
- 통합: [대상]
- 인수: [요구사항 대응]
- 회귀: [기존 테스트 + 영향 범위]

결과:
- 통과: [개수 / 전체]
- 실패: [항목] — [원인 단계: 요구사항·설계·구현]

조치:
- [실패 항목] → [되돌아갈 단계] → [수정 계획]

완료 판정:
- [ ] 모든 범주 통과 → 작업 완료
- [ ] 실패 존재 → 원인 단계로 되돌아가 재진행
```
