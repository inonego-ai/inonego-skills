# 범용 코드 작업

코드 작업의 공통 판단 기준이다.

## 적용 절차

- 코드 파일을 읽거나 쓰기 시작할 때 이 스킬을 적용한다.
- 코드 쓰기에는 현재 언어에 대응하는 코딩 규칙 문서가 있으면 적용한다. 해당 규칙 문서를 사용할 수 없으면 임의 스타일로 대체하지 않고 적용할 수 없는 범위를 밝힌다. 별도 규칙 문서가 없는 언어는 기존 프로젝트 스타일과 확인된 로컬 규칙을 따른다.
- 코딩 규칙이 동일한 구조 전체에 적용되는 경우, 수정 지점만 맞추지 말고 같은 범위의 동일 패턴 누락도 확인한다.
- 코드 식별자·파일·폴더 이름을 제안하거나 변경·검토할 때는 [명명 취향](references/naming-preferences.md)을 적용한다.
- 책임, 상태 소유권, 데이터 흐름, 실패 경계의 재구성이 필요하거나 땜빵식 수정 위험이 있으면 `target-state-implementation`을 함께 적용한다.
- 테스트 변경 작업에는 `test-design`을 적용한다.

## 구현 판단

- 증상 위치보다 실제 책임 주체, 호출 흐름과 데이터 생성·소비 경계를 먼저 확인한다.
- 기존 책임 주체와 자연스러운 확장 지점을 우선하고, 도달 가능한 요구 없이 새 추상화·복구 상태·방어 분기를 추가하지 않는다.
- 특정 구현 수단보다 현재 계약과 소유권을 만족하는 가장 단순한 구조를 선택한다.
- 컬렉션 소유권 종료와 일괄 정리 문제가 실제로 등장하면 [소유 컬렉션 일괄 정리](references/owned-collection-cleanup.md)를 적용한다.

## 명명 판단

- 이름을 정하기 전에 대상의 도메인, 책임, 수명, 소유권과 기존 프로젝트 용어를 확인한다.
- 승인된 변경은 철자가 비슷한 모든 심볼로 넓히지 않고 의미와 책임이 같은 참조 범위에 일관되게 적용한다.

## 변경 검토

- 한 변경 뒤 여러 심볼 오류가 연쇄적으로 생기면 개별 증상보다 네임스페이스 가림, 공통 참조, 생성 코드와 어셈블리 경계 같은 공통 원인을 먼저 확인한다.
- 수정 뒤 변경 차이에서 요청 밖 변경, 코딩 규칙 누락, 같은 구조의 적용 누락과 이름·참조 범위를 검토한다.
- 같은 문제에 두 번 이상 수정이 실패했거나 방어 분기가 늘어나면 다음 수정 전에 `target-state-implementation`으로 문제 공간을 다시 정렬한다.
