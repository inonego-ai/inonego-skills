# 테스트 설계

## 역할

이 스킬은 테스트를 많이 만들기 위한 스킬이 아니다.
테스트로 고정할 기대 결과의 근거를 확인하고, 그 기대 결과가 깨졌을 때 실제 문제가 드러나는 경우에만 테스트를 설계하게 하는 스킬이다.

테스트는 구현량을 보여주는 산출물이 아니다.
테스트를 작성하지 않는 것이 더 정확한 경우도 있다.

## 작업 권한 확인

테스트의 가치나 구현 방식을 판단하기 전에 이번 요청의 권한을 먼저 확인한다.

- 사용자가 테스트를 만들거나 추가하라고 명시하지 않았으면 새 테스트 파일·메서드·준비 코드·대역·테스트 데이터·테스트 전용 설정을 만들지 않는다.
- 승인 전에는 필요한 이유, 검증할 계약, 테스트 후보만 제안할 수 있다.
- 테스트 실행은 테스트 생성과 별도 권한이다. 사용자가 실행을 요청했거나 합의된 검증 범위에 포함된 경우에만 실행한다.
- 기존 테스트의 수정·삭제도 테스트 변경이므로 요청 범위에 포함되는지 확인한다.
- 권한이 없으면 이 스킬의 설계 절차를 테스트 구현으로 이어가지 않고, 허용된 다른 검증 방식을 선택한다.

## 핵심 원칙

- 에이전트가 임의로 기대 결과를 만들고 그것을 테스트 근거로 삼지 않는다.
- 테스트는 관찰 가능한 결과를 검증한다.
- 테스트는 실패했을 때 어떤 계약이 깨졌는지 설명할 수 있어야 한다.
- 테스트 수보다 실패 신호의 명확성과 검증 밀도를 우선한다.
- 기존 테스트 스타일은 참고하되, 가치 없는 패턴은 복제하지 않는다.
- 테스트 추가, 수정, 삭제는 모두 같은 수준으로 검토한다.

## 테스트 설계의 목표 상태

테스트는 코드 줄 수, 메서드 개수, 구현 세부사항에 맞춰 작성하지 않는다.
검증 단위는 외부에서 관찰 가능한 계약이어야 한다.

작은 단위 테스트라도 public API 사용자가 의존하는 상태, 출력, 이벤트, 오류 처리, 데이터 보존, 실행 환경 계약을 검증하면 가치가 높다.
반대로 테스트가 작거나 많다는 이유만으로 가치가 생기지는 않는다.

테스트는 작은 구현 단위가 아니라 작은 계약 단위로 작성한다.

## 기대 결과의 근거

테스트로 고정할 기대 결과는 아래 중 하나 이상의 근거가 있어야 한다.

- 사용자 요구: 사용자가 명시한 동작, 제약, 성공 조건
- 기존 외부 동작: 호출자나 사용자가 이미 의존하던 관찰 가능한 결과
- 실제 의존: 다른 코드, 데이터, 설정, 도구, 문서, 운영 흐름이 기대하는 결과
- 회귀 위험: 과거에 깨졌거나 이번 변경으로 깨질 가능성이 높은 조건
- 명시 문서: 사양, 표준, 스키마, 파일 포맷, 공개 API 문서
- 오류 처리 약속: 실패 시 반환, 예외, 상태 보존, 복구 방식

근거가 불명확하면 테스트를 쓰기 전에 기대 결과의 출처를 확인한다.
근거 없는 기대 결과는 테스트로 고정하지 않는다.

## 판단 절차

테스트를 작성하거나 평가하기 전에 아래를 순서대로 판단한다.

1. 테스트 생성·수정·삭제와 실행 권한을 각각 확인한다.
2. 검증하려는 기대 결과를 한 문장으로 쓴다.
3. 그 기대 결과의 근거를 식별한다.
4. 그 기대 결과가 깨졌을 때 생기는 실제 문제를 설명한다.
5. 기존 테스트나 다른 검증이 이미 그 문제를 잡는지 확인한다.
6. 가장 작은 계약 검증 경계를 고른다.
7. 테스트, 기존 테스트 수정, 다른 검증 방식, 테스트 없음 중 하나를 선택한다.
8. 테스트를 작성한다면 실패 이유가 한눈에 드러나게 만든다.

## 우선 검증 대상

다음 계약은 단위 테스트에서도 가치가 높다.

- 상태 전이: 시작, 진행, 완료, 중단, 복구, 재사용
- 값 갱신 규칙: 입력이 public 상태나 출력에 반영되는 방식
- 이벤트와 콜백: 발생 여부, 발생 횟수, 인자, 미발생 조건
- 경계 조건: 최소값, 최대값, 비어 있음, 초과, 누락, 중복, 동일 값 재설정
- 오류 처리: 예외, 실패 반환, 대체 처리, 실패 후 상태 보존
- 데이터 보존: 직렬화, 역직렬화, 데이터 이전, 복제, 참조 독립성, 라운드트립
- 공개 API 계약: 반환값, 조회 실패 방식, 순서, 정렬, 필터링, 선택 상태
- 실행 환경 계약: 필수 자산, 설정, 스키마, UI 구성 요소, 런타임 오브젝트 연결
- 회귀 조건: 과거 결함, 변경 영향이 큰 흐름, 여러 단위가 맞물리는 지점

## 낮은 가치 신호

다음 신호가 보이면 테스트를 추가하지 않거나 더 강한 검증으로 바꾼다.

- 기대 결과의 출처를 설명할 수 없다.
- 생성, 기본값, null 여부만 확인하고 그 값이나 객체가 외부에서 의존하는 계약을 검증하지 않는다.
- 단순 getter/setter의 대입과 반환만 확인한다.
- 언어, 프레임워크, 표준 라이브러리가 이미 보장하는 동작을 다시 확인한다.
- 구현 내부와 같은 계산이나 분기를 테스트 안에서 반복한다.
- `DoesNotThrow`, `Assert.Pass`, `NoCrash`처럼 실패하지 않음만 확인하고 호출 후 결과, 상태, 이벤트, 부작용을 검증하지 않는다.
- 내부 필드, 구현 타입, 파일 구조만 고정하고 관찰 가능한 동작을 검증하지 않는다.
- 테스트 이름은 구체적이지만 검증문은 약해서 실패 원인이 좁혀지지 않는다.
- 이미 다른 테스트가 같은 계약을 더 직접적이고 강하게 검증한다.

낮은 가치 신호는 자동 삭제 사유가 아니다.
기본값, null 여부, 구조, 타입이 실제 public 계약이거나 외부 의존이면 유지할 수 있다.
다만 그 경우에도 가능하면 그 값이 후속 동작에서 어떤 의미를 갖는지 함께 검증한다.

## 검증 방식 선택

검증 방식은 기대 결과와 실패 비용에 맞춘다.

- 계산, 변환, 규칙은 작은 단위 테스트로 검증한다.
- 상태 전이와 순서 의존은 시나리오 단위 테스트로 검증한다.
- 여러 단위의 협력은 통합 경계에서 검증한다.
- 공개 API, 파일 포맷, 메시지, 설정, 자산, 스키마는 근거가 있을 때만 계약성 테스트로 검증한다.
- 시각, 렌더링, 레이아웃, 생성물 품질은 결과 스냅샷, 기준 출력 비교, 렌더 확인, 수동 확인 중 적절한 방식을 고른다.
- 문서, 설정, 단순 구조 변경은 테스트보다 유효성 검사, 차이 확인, 정적 검사, 스키마 검사가 더 적절할 수 있다.
- 비용이 큰 전체 흐름 테스트는 핵심 경로와 대표 실패 경로에만 사용한다.

## 권장 테스트 구성

한 타입이나 모듈의 테스트는 기능 조각별 파일을 늘리기보다, 해당 public API가 제공하는 계약을 응집도 있게 다룬다.

좋은 테스트 파일은 보통 다음 흐름을 포함한다.

- 정상 흐름의 핵심 상태 변화
- 경계 조건과 예외 조건
- 이벤트, 콜백, 부작용
- 직렬화, 복제, 참조 보존 등 데이터 유지 계약
- 회귀 위험이 높은 조합 시나리오

테스트를 쪼갤 때는 기능 이름이 아니라 검증 계약이 분리되는지를 기준으로 한다.
같은 클래스의 public 계약을 여러 파일로 나눠야 한다면 기존 테스트 위치와 중복 여부를 먼저 확인한다.

## 좋은 테스트 기준

좋은 테스트는 다음을 만족한다.

- 기대 결과와 그 근거가 분명하다.
- 테스트 이름이 검증하는 기대 결과를 말한다.
- 준비, 실행, 검증 단계가 구분되어 읽힌다.
- 검증문이 실패 원인을 좁힌다.
- 하나의 테스트가 여러 책임을 과하게 검증하지 않는다.
- 같은 준비 과정이 반복되면 헬퍼로 숨기되, 핵심 조건은 테스트 안에서 보인다.
- 실패 메시지는 디버깅에 필요한 맥락을 준다.
- 테스트가 실제 구현 코드를 재구현하지 않는다.
- 우연한 구현 세부사항보다 관찰 가능한 결과에 묶인다.

## 유지, 수정, 삭제 기준

기존 테스트를 볼 때는 다음으로 판단한다.

- `유지`: 기대 결과의 근거가 있고 실패 원인이 명확하다.
- `수정`: 의도는 맞지만 검증문이 약하거나 준비 과정이 우연에 기대고 있다.
- `통합`: 같은 기대 결과를 여러 테스트가 얕게 반복한다.
- `삭제`: 기대 결과의 근거가 없거나 다른 테스트가 더 직접적으로 검증한다.

테스트 삭제는 검증 공백을 남기지 않는지 확인한다.

## 완료 기준

테스트 작업을 완료하기 전에 확인한다.

- 사용자가 테스트 변경을 명시적으로 요청했는가.
- 테스트 실행이 요청 또는 합의된 검증 범위에 포함됐는가.
- 새 테스트가 필요한 이유를 설명할 수 있는가.
- 테스트할 기대 결과의 출처가 분명한가.
- 테스트가 관찰 가능한 결과를 검증하는가.
- 약한 테스트 패턴을 무비판적으로 추가하지 않았는가.
- 기존 테스트와 중복되지 않는가.
- 테스트를 추가하지 않았다면 다른 검증 방식이 충분한가.
- 실행이 허용된 경우에만 관련 테스트 또는 검증 명령을 실행했는가.
