# 테스트 설계

테스트 수를 늘리는 것이 목적이 아니다. 검증할 기대 결과의 근거와 실패 의미를 확인하고, 실제 계약을 가장 작은 적절한 경계에서 검증한다.

## 핵심 원칙

- 에이전트가 임의로 기대 결과를 만들고 그것을 테스트 근거로 삼지 않는다.
- 테스트는 외부에서 관찰 가능한 결과나 실제 실행 환경 계약을 검증한다.
- 실패했을 때 어떤 계약이 깨졌는지 설명할 수 있어야 한다.
- 테스트 수보다 실패 신호의 명확성과 검증 밀도를 우선한다.
- 기존 테스트 스타일은 참고하되 가치 없는 패턴을 복제하지 않는다.

## 기대 결과의 근거

테스트로 고정할 결과는 하나 이상의 근거가 있어야 한다.

- 사용자 요구와 성공 조건
- 기존 외부 동작과 호환 계약
- 다른 코드·데이터·설정·도구의 실제 의존
- 과거 결함이나 이번 변경의 구체적 회귀 위험
- 명시 사양, 표준, 스키마, 파일 포맷이나 공개 API 문서
- 실패 시 반환·예외·상태 보존과 같은 오류 처리 약속

근거가 불명확하면 테스트를 먼저 만들지 않는다.

## 판단 절차

1. 검증하려는 기대 결과를 한 문장으로 정리한다.
2. 그 기대 결과의 근거를 식별한다.
3. 기대 결과가 깨졌을 때 실제 문제가 무엇인지 설명한다.
4. 기존 테스트나 다른 검증이 이미 그 문제를 잡는지 확인한다.
5. 가장 작은 관찰 가능한 계약 경계를 선택한다.
6. 새 테스트, 기존 테스트 수정, 다른 검증, 테스트 없음 중 하나를 선택한다.
7. 테스트를 작성한다면 실패 이유가 바로 드러나게 만든다.

## 우선 검증 대상

- 상태 전이와 재사용 수명주기
- 입력이 공개 상태·출력에 반영되는 규칙
- 이벤트·콜백의 발생 여부, 횟수와 인자
- 빈 값, 최소·최대, 중복과 동일 값 재설정 같은 경계 조건
- 오류 반환, 예외와 실패 후 상태 보존
- 직렬화·역직렬화·복제와 참조 보존
- 공개 API의 반환값, 순서, 정렬, 필터와 조회 실패 방식
- 필수 자산·설정·스키마·런타임 연결 같은 실행 환경 계약
- 이번 변경이나 과거 결함과 직접 연결된 회귀 조건

## 낮은 가치 신호

다음 경우에는 새 테스트를 추가하지 않거나 더 적절한 검증으로 바꾼다.

- 기대 결과의 출처를 설명할 수 없다.
- 단순 getter/setter 대입과 반환만 반복한다.
- 언어·프레임워크·표준 라이브러리가 보장하는 동작을 다시 확인한다.
- 구현 내부의 계산이나 분기를 테스트 안에서 그대로 재현한다.
- `DoesNotThrow`, `Assert.Pass`, `NoCrash`처럼 결과·상태·부작용을 보지 않는다.
- 내부 필드나 파일 구조만 고정하고 관찰 가능한 계약을 검증하지 않는다.
- 이미 다른 테스트가 같은 계약을 더 직접적으로 검증한다.

구조나 기본값 자체가 외부 계약이면 예외적으로 가치가 있을 수 있다. 그 경우에도 가능하면 후속 동작에서의 의미를 함께 검증한다.

## 검증 방식 선택

- 계산과 변환 규칙은 작은 계약 단위 테스트를 우선한다.
- 상태 전이와 순서 의존은 시나리오 단위에서 검증한다.
- 여러 단위의 협력은 통합 경계에서 검증한다.
- 파일 포맷·메시지·설정·스키마는 근거가 있을 때 계약성 검증을 사용한다.
- 시각·렌더링·레이아웃은 실제 결과 비교나 수동 확인이 더 적절할 수 있다.
- 문서·설정·단순 구조 변경은 테스트보다 유효성 검사와 차이 확인이 적절할 수 있다.
- 비용이 큰 전체 흐름 검증은 핵심 경로와 대표 실패 경로에 한정한다.

## 테스트 구성

한 타입이나 모듈의 테스트는 기능 조각마다 파일을 늘리기보다 그 public API가 제공하는 계약을 응집도 있게 다룬다.
같은 클래스의 테스트를 여러 파일로 나누려면 검증 계약과 준비 환경이 실제로 분리되는지, 기존 테스트와 중복되지 않는지 먼저 확인한다.
정상 흐름, 경계·오류 조건, 이벤트·부작용, 데이터 보존과 회귀 위험이 같은 계약을 설명한다면 한 테스트 영역에서 함께 관리한다.

## 테스트 품질과 유지

좋은 테스트는 준비·실행·검증이 읽히고, 이름과 assertion이 실패 원인을 좁히며, 구현 세부사항보다 외부 계약에 묶인다.
같은 준비가 반복되면 헬퍼로 숨길 수 있지만 핵심 조건은 테스트에서 보이게 한다.

기존 테스트는 다음 기준으로 본다.

- 유지: 근거가 있고 실패 의미가 명확함
- 수정: 의도는 맞지만 검증이 약하거나 우연한 준비에 의존함
- 통합: 같은 계약을 여러 테스트가 얕게 반복함
- 삭제: 근거가 없거나 더 직접적인 검증이 이미 존재함

삭제나 통합은 검증 공백을 남기지 않는지 확인한다.

## 완료 기준

- 기대 결과의 근거가 분명한가
- 실패했을 때 실제 문제가 드러나는가
- 관찰 가능한 계약을 검증하는가
- 기존 검증과 불필요하게 중복되지 않는가
- 선택한 검증 방식이 변경 위험에 비례하는가
