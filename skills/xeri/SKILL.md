# Xeri

Xeri 계열 패키지에서 **이미 있는 기능을 다시 만들지 않고, 기존 계약을 근거 없이 바꾸지 않도록** 하는 공통 절차다. 패키지별 문서 위치와 구성은 [패키지 지도](references/packages.md)에 둔다.

## 적용 수준

- **필수:** 새 시스템 초기 구현, 기존 시스템을 갈아엎는 수준의 재설계, 여러 패키지에 걸친 변경, 새 공개 타입이나 새 저장·시간·컬렉션·수명 구조를 도입하는 변경.
- **가벼움:** 작은 리팩터링·버그 수정은 기능 탐색을 생략할 수 있다. 다만 새 타입·필드·알고리즘이 생기면 검토 관문의 HEAD 대비 확인은 한다.

## 의존 체인

```text
Xeri UI ─────┐
Xeri Fabric ─┼──▶ Xeri Core
Xeri Game ───┴──▶ Xeri UI, Xeri Fabric, Xeri Core
```

화살표는 "의존한다" 방향이다. Xeri Core가 모든 패키지의 기반이다.

1. 작업 대상 패키지의 직접 기반을 [패키지 지도](references/packages.md)에서 확인한다.
2. 기반의 기반을 따라 올라가며 탐색 범위를 만든다. 같은 기반은 한 번만 포함한다.
3. 탐색 범위는 작업 대상 패키지와 그 모든 기반이다. 작업 대상이 Xeri를 쓰는 프로젝트이면 그 프로젝트가 참조하는 Xeri 패키지 전체다.

## 기반 패키지 소스 찾기

1. 작업 중인 Unity 프로젝트의 `Packages/manifest.json`에서 해당 패키지 항목이 `file:` 경로면 그 폴더.
2. `Packages/<패키지 이름>/`에 embedded로 있으면 그 폴더.
3. `Library/PackageCache/<패키지 이름>@*/`.
4. Unity 프로젝트 밖(패키지 저장소 자체)에서 작업 중이면 같은 작업 루트의 형제 checkout과 worktree에서 `<패키지 이름>/package.json`을 찾는다.

후보가 여러 개(여러 worktree·branch)면 작업에 쓰는 Unity 프로젝트 manifest가 가리키는 것을 쓰고, 그것도 없으면 어느 checkout이 기준인지 사용자에게 확인한다. 다른 저장소의 파일은 읽기만 한다.

## 기능 탐색

새로 만들려는 것(타입·필드·저장 구조·시간 계산·정렬·수명 관리·이벤트·식별자 등)마다 탐색 범위 안에 같은 일을 하는 기능이 있는지 아래 순서로 찾는다. 앞 단계에서 판단이 서면 다음 단계로 가지 않는다.

1. **문서:** 각 패키지의 `Documentation~/index.md`와 그 아래 모듈·개념·가이드 문서, `Runtime/**/README.md`.
2. **폴더·파일 이름:** 문서가 없거나 부족하면 `Runtime/` 폴더 구조와 파일·타입 이름으로 후보를 찾는다. Xeri는 폴더와 파일 이름이 책임을 드러내도록 구성돼 있다.
3. **파일 열기:** 그래도 판단이 안 되면 후보 파일을 열어 공개 멤버, `<summary>`, 직렬화 특성, 파일 헤더의 설명·제약을 확인한다.

같은 능력이 여러 패키지에 있으면 작업 대상에 더 가까운(구체적인) 패키지의 것을 우선하되, 그것이 기반 기능을 감싼 것인지 확인한다.

### 에이전트 위임

필수 수준의 작업에서는 기능 탐색을 **읽기 전용 탐색 에이전트**에 맡긴다.

- 모델: 호스트가 자체 서브에이전트와 모델 선택을 제공하면 가벼운 모델(Claude 계열은 Haiku, OpenAI 계열은 Luna 계열)을 쓴다. 쓸 수 없으면 메인 에이전트가 같은 절차를 직접 수행한다.
- 입력: 무엇이 있는지 몰라도 되도록 **새로 만들려는 것**을 준다. 설계 초안, 요구 능력 목록(예: "시간이 지나면 끝나고 일시정지되는 상태", "우선순위 순서가 유지되는 컬렉션"), 또는 구현 diff. 그리고 탐색 범위의 패키지와 각 소스 위치.
- 지시: 기능 탐색 순서(문서 → 폴더·파일 이름 → 파일 열기)를 지키고, 근거 없는 추측으로 후보를 만들지 않는다.
- 출력: 아래 대조표. 채택 판단은 메인 에이전트가 한다.

| 새로 만들려는 것 | 기존 후보(패키지·경로) | 근거(문서 절 또는 file:line) | 그대로 쓸 수 있는가 | 부족한 점 |
| --- | --- | --- | --- | --- |

## 재사용과 교체

- **원본 계약 유지:** 기존 코드를 고치거나 다시 설계할 때 공개 API, 직렬화 특성(`[Serializable]`, `[SerializeField]`), 기본 생성자, 상속 가능성, 저장 방식, 값의 의미, 파일 헤더에 적힌 책임과 "하지 않는 것"을 유지한다.
- **기반 기능 재사용:** 탐색 범위에 있는 기능과 같은 일을 하는 구조(시간 진행, 값 저장소, 정렬 컬렉션, 수명·Lease, 직렬화 컬렉션 등)를 새로 만들지 않는다.
- **교체 관문:** 원본 계약이나 기반 기능을 바꾸거나 대신하려면 다음을 모두 갖춘다.
  1. 요구가 무엇인지.
  2. 기존 것으로 왜 안 되는지의 근거(API 부재, 재현 테스트, 문서의 명시적 제약).
  3. 가능한 최소 변경.
  4. 사용자 승인. 설계 문서 안에 섞어 두지 말고 교체 항목만 표로 따로 보여 승인받는다.
- **기반 확장 제안:** 기반 패키지 기능이 조금 부족하면 의존하는 패키지에서 대체 구현을 만들지 않고 기반 패키지 확장을 제안한다. 다른 저장소 변경이므로 사용자 승인 뒤에만 한다.
- 테스트 이관표, 구현 코드, 위임 에이전트의 보고 안에서 원본 계약을 바꾸는 결정을 내리지 않는다.

## 검토 관문

설계 대비 검토와 별도로, 단계마다 HEAD 대비로 다음을 확인한다.

- 사라진 직렬화 특성·기본 생성자, 새로 붙은 `sealed`, 사라진 기반 패키지 타입 사용.
- 새 공개 타입·필드, 새로 직접 구현한 알고리즘(시간 산술, 정렬, 탐색, 자체 저장소).

각 항목이 교체 관문을 통과한 것인지 대조하고, 통과하지 않은 항목은 결함으로 본다. 필수 수준의 작업이면 이 대조도 탐색 에이전트에 diff를 입력으로 맡길 수 있다.
