# ChatGPT Web 로컬 에이전트 부트스트랩

## 적용 범위

이 문서는 ChatGPT Web에서 연결된 로컬 컴퓨터의 파일, 저장소, 개발 도구, 빌드, 테스트, Unity 프로젝트 또는 기타 로컬 리소스를 실제로 다루는 작업에만 적용한다.
일반 대화, 웹 검색만 필요한 요청, 로컬 리소스와 관계없는 작업에는 적용하지 않는다.
Codex CLI, IDE 에이전트, 기타 로컬 에이전트가 이 파일을 우연히 발견해도 자신의 전역 지침으로 취급하지 않는다.

## 초기화 순서

로컬 작업을 시작할 때 다음 순서로 준비한다.

1. 전역 에이전트 지침 파일이 존재하면 읽는다.
2. 사용자가 지정한 경로 또는 작업 대상에서 프로젝트 루트를 판별한다.
3. 프로젝트 루트의 로컬 지침 파일을 알려진 위치에서 확인하고 존재하는 것만 읽는다.
4. 전역 스킬 루트와 프로젝트 스킬 루트를 확인한다.
5. 스킬 발견 단계에서는 각 `SKILL.md`의 YAML frontmatter만 읽어 `name`, `description`, 필요 시 `user-invocable` 정도의 메타데이터만 확보한다.
6. 현재 작업에 필요한 최소한의 스킬만 선택한다.
7. 선택된 스킬의 `SKILL.md`만 전체 내용을 읽는다.
8. 실제 파일, 저장소, 프로세스, 도구, 빌드 상태를 확인한 뒤 작업한다.
9. 수정 후 요청에서 허용된 빌드, 상태 확인 또는 실제 실행으로 검증한다. 테스트 생성과 실행은 각각 사용자가 명시했거나 합의한 범위에 포함된 경우에만 수행한다.

같은 로컬 작업 세션에서는 부트스트랩 파일이 변경되었거나 작업 프로젝트/컨텍스트가 바뀐 경우가 아니라면 이 초기화를 불필요하게 반복하지 않는다.

## 전역 지침

다음 전역 지침 파일이 존재하면 읽는다.

- `<GLOBAL_AGENT_INSTRUCTIONS>`

전역 지침은 기본 규칙이며, 더 구체적인 프로젝트 로컬 지침과 충돌하면 프로젝트 로컬 지침을 우선한다.

## 프로젝트 루트 판별

사용자가 프로젝트 루트를 직접 지정했다면 해당 경로를 우선 사용한다.
파일 또는 하위 디렉터리만 지정했다면 상위 디렉터리를 탐색해 프로젝트 루트를 찾는다.

다음과 같은 프로젝트 마커를 사용할 수 있다.

- `.git`
- `AGENTS.md`
- `package.json`
- `*.sln`, `*.slnx`, `*.csproj`
- Unity의 경우 `Assets`, `Packages`, `ProjectSettings` 조합

하나의 마커만으로 무조건 판단하지 말고 현재 작업 맥락과 디렉터리 구조를 함께 확인한다.

## 프로젝트 지침 발견

프로젝트 루트에서 다음 알려진 위치만 확인한다.

- `<project>\AGENTS.md`
- `<project>\.agents\AGENTS.md`
- `<project>\.codex\AGENTS.md`
- `<project>\CLAUDE.md`

존재하는 파일만 읽는다.
부트스트랩 단계에서 저장소 전체를 재귀적으로 뒤져 임의의 지침 파일을 수집하지 않는다.

프로젝트 내부의 더 세부적인 하위 지침 계층이 실제로 사용되고 있다는 근거가 있거나 프로젝트 지침이 명시적으로 요구하는 경우에만 추가 탐색한다.

## 전역 스킬 발견

다음 경로가 존재하면 전역 스킬 루트로 사용한다.

- `<GLOBAL_SKILL_ROOT_1>`
- `<GLOBAL_SKILL_ROOT_2>`
- `<GLOBAL_SKILL_ROOT_3>`

각 스킬 루트의 직계 하위 디렉터리만 확인한다.
각 하위 디렉터리에 `SKILL.md`가 있으면 discovery 단계에서는 첫 YAML frontmatter만 읽는다.

`skills` 루트 밖에 보관된 템플릿, 문서, 예제 파일은 스킬이 아니므로 skill discovery 중 로드하지 않는다.

## 프로젝트 스킬 발견

프로젝트 루트에서 다음 경로가 존재하면 프로젝트 스킬 루트로 사용한다.

- `<project>\.agents\skills`
- `<project>\.codex\skills`
- `<project>\.claude\skills`

각 루트의 직계 하위 디렉터리에서 `SKILL.md`를 확인하고, 먼저 frontmatter만 읽는다.
프로젝트 전체에서 임의의 `SKILL.md`를 재귀 검색하지 않는다. `Library`, 캐시, 패키지 복사본, 빌드 산출물 등의 중복 스킬을 등록하지 않기 위해서다.

## 중복 스킬 처리

동일한 `name`의 스킬이 여러 곳에서 발견되면 지침에서 별도로 요구하지 않는 한 하나의 유효 스킬만 등록한다.

우선순위는 다음과 같다.

1. 프로젝트 로컬 스킬이 전역 스킬보다 우선한다.
2. 프로젝트 로컬 내부에서는 `.agents/skills` > `.codex/skills` > `.claude/skills` 순으로 우선한다.
3. 전역 내부에서는 위의 전역 스킬 루트 목록에서 먼저 나열된 루트의 동일 이름 스킬을 우선한다.

동일한 유효 스킬의 중복 복사본을 여러 번 전체 로드하지 않는다.

## 스킬 지연 로드

스킬 발견 단계에서는 전체 `SKILL.md` 본문을 미리 읽지 않는다.
frontmatter의 `name`, `description`을 중심으로 현재 요청과의 관련성을 판단한다.

현재 작업에 실제로 필요한 스킬만 선택하고, 선택된 스킬의 `SKILL.md`를 전체 로드한다.
스킬 내부에서 추가 규칙 파일이나 convention 문서를 읽으라고 명시하는 경우에만 해당 파일을 추가로 읽는다.

여러 영역이 동시에 필요한 작업이면 최소한의 관련 스킬 조합을 선택한다.

## Desktop Commander 성능 및 도구 사용 원칙

Desktop Commander를 사용하는 로컬 작업에서는 정확성을 유지하면서 프로세스 생성 횟수, 도구 왕복 횟수, 파일 탐색 범위, 반환 데이터 양을 최소화한다.

### 전용 도구 우선

셸보다 Desktop Commander 전용 기능을 우선한다.

- 파일 읽기: `read_file`, `read_multiple_files`
- 디렉터리 조회: `list_directory`
- 파일/내용 검색: `start_search`
- 파일 수정: `edit_block`
- 파일 생성/추가: `write_file`
- 실행 중인 명령 출력 확인: `read_process_output`

`Get-Content`, `Get-ChildItem`, `Get-ChildItem -Recurse`, `Select-String`, `Set-Content`, `Add-Content` 등으로 전용 Desktop Commander 기능을 대체하지 않는다.
파일 조회·검색·편집을 위해 셸 프로세스를 만들지 않는다.

### 셸 사용과 선택

`start_process`는 Git, 빌드, 테스트, 패키지 관리자, Unity CLI 등 실제 CLI 프로그램 실행이나 Desktop Commander 전용 도구로 표현하기 어려운 시스템 작업에만 사용한다.

Windows라는 이유만으로 PowerShell을 기본 선택하지 않는다.
단순 CLI 실행은 가능한 경우 `shell: "cmd.exe"`를 명시해 가벼운 셸을 우선한다.

PowerShell 고유 기능이 실제로 필요한 경우에만 PowerShell을 사용한다.
사용자 PowerShell profile에 의존해야 하는 명확한 이유가 없다면 반드시 `-NoProfile`로 실행한다.

```text
powershell.exe -NoProfile -Command "..."
```

자동화 작업에서는 Conda 등 사용자 interactive shell 초기화를 불필요하게 실행하지 않는다.

도구 선택 우선순위는 다음과 같다.

1. Desktop Commander 전용 도구
2. 직접 실행 가능한 CLI 또는 `cmd.exe`
3. `powershell.exe -NoProfile`
4. 사용자 profile이 실제로 필요한 PowerShell

### 프로세스 생성과 도구 왕복 최소화

여러 개의 작은 `start_process` 호출을 연속 생성하지 않는다.
같은 목적의 CLI 상태 확인이나 검증은 오류 처리와 출력이 과도하게 복잡해지지 않는 범위에서 하나의 프로세스 실행으로 묶는다.

여러 파일이 필요하면 개별 `read_file` 반복보다 `read_multiple_files`를 우선한다.
서로 관련된 여러 검색 패턴은 가능하면 한 번의 범위 제한 검색으로 처리한다.

이미 존재하는 interactive process를 안전하게 재사용할 수 있다면 새 프로세스를 반복 생성하지 않는다.
필요 없어진 장기 실행 세션은 방치하지 않는다.

### 탐색 범위 제한

저장소 또는 프로젝트 루트 전체를 기본 검색 범위로 사용하지 않는다.
먼저 예상되는 소스 디렉터리와 파일 형식을 제한한 뒤 검색한다.

Unity 프로젝트의 일반 소스 조사에서는 다음 경로를 재귀 검색하지 않는다.

- `Library`
- `Temp`
- `obj`
- `Logs`
- `Build`
- `Builds`
- `.git`

Unity 작업에서는 필요한 범위에 따라 우선 `Assets`, `Packages`, `ProjectSettings`, `External` 영역을 사용한다.
`Get-ChildItem -Recurse`를 저장소 전체에 실행하지 않는다.

### 무거운 시스템 조회 제한

`Get-CimInstance`, WMI 등 상대적으로 비싼 시스템 전체 조회를 일반적인 상태 확인에 습관적으로 사용하지 않는다.
전용 프로세스·파일 도구나 더 좁은 명령으로 확인할 수 있으면 그것을 우선한다.
시스템 전체 inventory는 실제로 필요한 경우에만 수행한다.

### 반복 조회 방지

작업 중 상태가 변경되지 않았다면 `CHATGPT_WEB_BOOTSTRAP.md`, 전역·프로젝트 `AGENTS.md`, 이미 선택해 로드한 `SKILL.md`, 프로젝트 루트와 기본 구조, 같은 파일의 동일 범위, Desktop Commander config, 동일한 Git 상태를 반복해서 확인하지 않는다.
상태가 변경된 경우나 검증 단계에서 필요한 경우에만 다시 확인한다.

### 파일 읽기와 출력량 최소화

같은 파일을 짧은 범위로 여러 번 반복해서 읽는 패턴을 피한다.
검색으로 위치를 먼저 특정한 뒤 필요한 주변 문맥을 한 번에 읽거나, 처음부터 필요한 범위를 합리적으로 넓게 읽는다.
전체 파일이 필요한 근거가 없으면 큰 파일 전체를 읽지 않는다.

프로세스 목록, 검색 결과, 로그, Git diff 등 대량 데이터를 그대로 반환받지 않는다.
가능하면 로컬에서 먼저 경로, 파일 형식, 검색 조건, 결과 개수, line range를 제한한 뒤 필요한 결과만 반환한다.

### CLI 및 패키지 실행 비용 최소화

이미 설치된 CLI가 있다면 직접 실행한다.
특별한 이유 없이 매 작업마다 `npx <package>@latest`처럼 패키지 탐색·버전 확인·임시 설치가 개입할 수 있는 실행 방식을 사용하지 않는다.

### 검증 범위 단계화

수정 후 검증은 수행하되 매 작은 수정마다 전체 프로젝트 빌드를 반복하지 않는다.
가능하면 대상 파일·참조 확인 → 관련 컴파일 또는 좁은 검사 → 필요한 테스트 → 최종 전체 빌드·실행 순서로 검증 범위를 확대한다.
작은 변경 여러 개를 하는 동안 동일한 전체 빌드를 반복하지 않는다.

### 성능 이상 진단

Desktop Commander 작업이 느릴 때 즉시 로컬 PC 성능 문제라고 판단하지 않는다.
먼저 모델과 도구 사이의 직렬 왕복, Desktop Commander 전용 기능, 셸 프로세스 startup, PowerShell profile startup, 실제 CLI 실행, 파일 시스템 탐색, 대규모 출력 전송, 빌드·테스트 자체 실행 시간을 분리해 판단한다.

짧은 작업에서 `start_process` 호출이 반복된다면 먼저 셸 선택과 프로세스 생성 횟수를 점검한다.

## 작업 원칙

로컬 상태를 추측하지 않는다.
사용자가 언급한 파일, 경로, 브랜치, 도구, 프로세스, Unity 인스턴스 등이 실제로 존재하고 접근 가능한지 확인한다.

기존 사용자 변경 사항을 임의로 덮어쓰거나 삭제하지 않는다.
작업 전 `git status` 등으로 기존 변경을 구분하고, 사용자 작업과 이번 작업의 변경을 분리한다.

수정 후에는 작업 성격과 사용자 권한에 맞는 검증을 수행한다.
예: 빌드, 린트, git diff/status, CLI 실행, Unity 연결 확인, 콘솔 오류 확인.
테스트 생성과 실행은 서로 별도 권한으로 판단하고, 사용자가 명시했거나 합의한 범위에 포함된 경우에만 수행한다.

검증하지 않은 결과를 완료 또는 정상이라고 표현하지 않는다.
